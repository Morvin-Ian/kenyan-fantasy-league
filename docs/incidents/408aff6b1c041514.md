# Production nginx forwards an unvalidated request Host to Django in `docker/production/nginx/nginx.conf`

## Verdict
defect — nginx forwarded the client-controlled `$host` to Django, allowing an unexpected host to reach Django’s host validation.

## What happened
A request with `HTTP_HOST: vmi3526112.contaboserver.net` reached Django’s `CommonMiddleware`, where `request.get_host()` rejected it with `DisallowedHost`. The production nginx API and Guardian proxy locations preserved the incoming host header, so a request that reached either proxy was passed to Django with the unrecognised host. Users of those routes received a failed request while the API emitted an error log entry.

## Root cause
The defect was in `docker/production/nginx/nginx.conf:75-88`. Both application proxy locations used the externally supplied host as the upstream host:

```nginx
location /api/v1 {
    proxy_pass http://api;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Host $host;
```

`$host` is derived from the request host. This assumed that nginx’s virtual-host matching and the HTTPS conditional at `docker/production/nginx/nginx.conf:47-51` would always prevent an unrecognised host from reaching these proxy blocks. The production log proves that assumption did not hold for the running request. Django 4.2.8 is pinned at `requirements.txt:17`; its `request.get_host()` rejection shown in the trace is therefore expected once that host reaches the API.

## How to reproduce
Send a request to the production nginx API route with `Host: vmi3526112.contaboserver.net`, for example:

```http
GET /api/v1/ HTTP/1.1
Host: vmi3526112.contaboserver.net
```

Before this change, an nginx path that selected the application server forwarded that host to Django and Django raised `DisallowedHost`. After this change, nginx forwards its configured server name instead.

## Blast radius
Both `location /api/v1` and `location /guardian` used the same client-host forwarding pattern at `docker/production/nginx/nginx.conf:75-88`; both could generate this error. The local development nginx configuration has analogous `$host` forwarding at `docker/local/nginx/nginx.conf:14-23`, but it is not the production deployment described by the incident.

## Likely cause commit
74fa438 — it is the listed incident-report commit concerning production nginx routing unknown hosts to Django, and the relevant production nginx handling is the code involved; the checked-out source cannot establish whether that commit’s deployment was actually running when this error occurred.

## Applied fix
- `docker/production/nginx/nginx.conf:75-88` now sends `Host $server_name` to Django for `/api/v1` and `/guardian`, rather than forwarding client-controlled `$host`. Django consequently receives `fantasykenya.com`, a host named in `config/settings/production.py:45` and retained in `ALLOWED_HOSTS` at `config/settings/production.py:54`.
- `tests/test_allowed_hosts.py:119-135` now parses both production API proxy blocks and asserts that each uses `$server_name` and does not use `$host`.

Verification: run the production-host regression tests, including `tests/test_allowed_hosts.py`; request `/api/v1` and `/guardian` through nginx with `Host: vmi3526112.contaboserver.net` and confirm Django no longer logs `DisallowedHost`.
