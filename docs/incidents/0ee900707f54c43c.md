# Incident Report: Lineup scraper re-scrapes everything on one persistence error, and reports success when nothing was scraped

**File:** `apps/kpl/tasks/lineups.py` — the `fetch_lineup_for_fixture_task` Celery task (lines 154–162) calls `fetch_lineup_for_fixture` (lines 97–151), which calls `upsert_fixture_lineup` (lines 131–141) with no exception containment inside a loop that re-runs the entire multi-provider Selenium scrape on any error.

## What happened

The lineup-scraping pipeline has two coupled defects that make every scrape either *too aggressive* or *silently empty*:

1. **One persistence error re-runs the whole scrape (up to 5 extra times).** The task is decorated with
   ```python
   @shared_task(
       autoretry_for=(Exception,), retry_backoff=30, retry_backoff_max=300, max_retries=5
   )
   ```
   and the only step that can raise an exception unrelated to page loading — `upsert_fixture_lineup(...)` at lines 131–141 — is not wrapped in `try/except`. A single `IntegrityError`, DB connection drop, or bad value (e.g., a non-numeric `jersey_number`) bubbles out of the provider/side loops, out of `fetch_lineup_for_fixture`, and into the Celery autoretry, which **re-runs the entire scrape from scratch**: a new Selenium session, every provider URL, re-parsing, and re-persisting. If the home lineup had already been saved, it is scraped and rewritten again on every retry.

2. **A scrape that finds nothing is reported as success.** `fetch_lineup_for_fixture` ends with an unconditional `return True, "done"` (line 151). If every provider returned `None` (empty page, new site layout, provider blocking the bot), the function still returns `True`, the task logs `True: done`, and the failure is never retried and never alerted — the opposite failure mode.

## Root cause

In `apps/kpl/tasks/lineups.py`:

```python
# lines 119–149 (abridged)
for attempt, sleep_seconds in _with_backoff_attempts(3):
    result = parse_lineup_from_source(driver, provider, url, side=side)
    if result is None:
        if attempt < 3:
            time.sleep(sleep_seconds)
            continue
        else:
            break

    upsert_fixture_lineup(           # <-- line 131, NO try/except
        fixture=fixture, team=team, side=side, ...
    )
    break

return True, "done"                  # <-- line 151, unconditional
```

- `parse_lineup_from_source` (lines 65–89) is defensive: it catches all exceptions and returns `None`, so page-load and parsing failures are absorbed by the **in-loop** 3-attempt backoff and never reach Celery. Good.
- `upsert_fixture_lineup` has no such guard. Its `transaction.atomic()` block (in `apps/kpl/services.py:160`) rolls back on error but re-raises, and the exception escapes to the `autoretry_for=(Exception,)` decorator.
- Because `autoretry_for` cannot distinguish transient errors from deterministic ones, a permanent bug (bad data, constraint violation) is retried 5 times with backoff up to 300 s, then fails anyway — after hammering external provider sites, which are exactly the services most likely to rate-limit or block a scraper.
- Each retry also re-enters the inner `_with_backoff_attempts(3)` loop, so one failing fixture can hold a Selenium session for many minutes — well past the KO+5 minute grace window that `scan_upcoming_fixtures_for_lineups` (lines 168–272) tries to respect.

## Suggested fix

1. **Contain persistence failures per side.** Wrap the `upsert_fixture_lineup(...)` call in `try/except Exception`, log the error, and `continue` to the next provider/side instead of aborting the whole scrape. The in-loop backoff already handles transient page-load failures; a DB error should not trigger a full re-scrape.
2. **Return a truthful status.** Track whether any lineup was actually persisted; return `(False, reason)` when nothing was saved so `fetch_lineup_for_fixture_task` (and the `scrape_lineup` management command) report failure and the alert webhook (`LINEUPS_ALERT_WEBHOOK`) can fire — instead of silently logging `True: done`.
3. **Narrow the autoretry.** Keep `autoretry_for` only
