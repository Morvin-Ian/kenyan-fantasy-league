# Production nginx exposes the KFL certificate to unknown TLS hosts in `docker/production/nginx/nginx.conf`

## Verdict
defect — although unknown HTTP hosts were rejected, the default TLS server completed a handshake using the `fantasykenya.com` certificate before rejecting the request, including `sso.fantasykenya.com`.

## What happened
A requester connected to the deployment with `Host: sso.fantasykenya.com`, which is not one of the configured application domains. The supplied Django traceback shows that request reached `CommonMiddleware`, where Django correctly rejected it with `DisallowedHost` before any view or data mutation ran. The checked-in edge configuration was intended to stop unknown hosts before Django, but its TLS default server still presented the KFL certificate and then depended on HTTP-level rejection.

## Root cause
`docker/production/nginx/nginx.conf:14-23` previously configured the catch-all TLS virtual host with the production certificate:

```nginx
server {
    listen 443 ssl default_server;
    http2 on;
    server_name _;

    ssl_certificate /etc/letsencrypt/live/fantasykenya.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/fantasykenya.com/privkey.pem;
    return 444;
}
```

The configuration assumed returning `444` after the TLS handshake was sufficient protection for every unknown hostname. That assumption does not hold for a TLS SNI request such as `sso.fantasykenya.com`: nginx completes the handshake and exposes the `fantasykenya.com` certificate before HTTP routing can return `444`. If the running container has not reloaded the currently checked-in HTTP-host guard at `docker/production/nginx/nginx.conf:44-48`, the same request can also reach Django and produce the logged exception.

Django’s host policy is intentional: `config/settings/production.py:45-54` permits only `fantasykenya.com` and `www.fantasykenya.com`. No SSO service, virtual host, or application reference for `sso.fantasykenya.com` exists in the repository.

## How to reproduce
Make a TLS request to the public deployment using SNI and an HTTP host of `sso.fantasykenya.com`, for example:

```http
GET /api/v1/ HTTP/1.1
Host: sso.fantasykenya.com
```

Before the change, the default TLS virtual host selected the KFL certificate; if the deployed nginx configuration lacked the current HTTP guard, `/api/v1` could then be proxied with that host and Django would raise `DisallowedHost`.

## Blast radius
Any unrecognised TLS SNI hostname, including arbitrary scanner names, previously received the KFL certificate from the default TLS listener. All unknown HTTP host headers remain rejected by Django as defense in depth; requests reaching its `/api/v1` or `/guardian` proxy routes can log the same exception only when the production nginx configuration is stale or differs from this repository.

## Likely cause commit
39412aa (`maajun: incident report for Production nginx forwards unrecognised Host headers to Django…`) most plausibly introduced the certificate exposure: it added the default TLS rejection block that deliberately configured the KFL certificate at `docker/production/nginx/nginx.conf:14-23`.

## Applied fix
- `docker/production/nginx/nginx.conf:14-21` now uses `ssl_reject_handshake on;` in the default TLS virtual host instead of loading the `fantasykenya.com` certificate and returning `444` after handshake completion. Unknown TLS SNI names, including `sso.fantasykenya.com`, are rejected before HTTP routing can select a proxying server.
- `tests/test_allowed_hosts.py:57-74` now requires the TLS default listener to use `ssl_reject_handshake on` and asserts that it does not configure an `ssl_certificate`, preventing a later configuration change from restoring certificate exposure.

Verification is to run `tests/test_allowed_hosts.py`, reload the production nginx configuration, and make an SNI request for `sso.fantasykenya.com`; nginx should reject the TLS handshake without presenting the KFL certificate and no corresponding Django `DisallowedHost` entry should be emitted. I could not execute tests or reload nginx because this environment has no command-execution access.
