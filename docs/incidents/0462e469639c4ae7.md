# Incident report: Google OAuth callback leaves JWT tokens in the URL

## What happened

Every successful "Continue with Google" sign-in redirects to `/auth/callback?auth_success=true&tokens=<url-encoded JWT pair>&user=<user data>`. The callback view parses both values out of the URL, stores them, and moves on — the URL itself is never rewritten, so both the short-lived access token **and** the long-lived refresh token remain visible everywhere the URL travels.

## Root cause

Two ends of one flow, verified in this repo:

1. **Frontend trusts and keeps the URL.** `client/src/views/Auth/OAuthCallback.vue:43-62` (`onMounted`) does:

   ```typescript
   const tokensParam = route.query.tokens as string;            // line 47
   const userParam = route.query.user as string;                // line 48
   ...
   const tokens = JSON.parse(decodeURIComponent(tokensParam)); // line 58
   authStore.setToken(tokens.access, tokens.refresh);          // line 61
   authStore.setUser(userData);                                // line 62
   ```

   There is no `history.replaceState` / `router.replace` call anywhere in the component (or elsewhere in `client/src`, per grep) — the token-bearing URL stays in the address bar and is written to browser history before and after parsing.

2. **The route makes the leak durable.** `client/src/router/index.ts:21-25` registers `/auth/callback` as a real history-mode route, so the full URI (tokens included) is recorded by the browser and by any proxy/access log that logs the request line.

3. **Backend supplies the tokens in the redirect.** Per the existing incident record (`docs/incidents/785cd6ee6d3241ee.md`), `apps/accounts/views.py:104-125` generates the JWTs and URL-encodes them into the success redirect (`&tokens=...&user=...`). The entry points are `window.location.href = "/api/v1/auth/google/login/"` in `SignIn.vue:142-144` and `SignUp.vue:284-287`.

4. **Storage compounds it.** `authStore.setToken` persists both tokens to `localStorage` (XSS-readable), so the leaked refresh token remains valid long after the page is gone.

## How to reproduce

1. Open the sign-in page and click **Continue with Google**; complete the consent screen.
2. On landing at `/auth/callback?...tokens=%7B%22access%22%3AeyJ...%7D`, read the address bar — both JWTs are present percent-encoded.
3. Press Back: the same URL is in history. Check nginx/Django access logs: the request line contains the full query string in plaintext.

## Blast radius

- **Access logs** — proxy and app logs persist the tokens on disk and into any log aggregation/retention pipeline.
- **Browser history & sync** — the URL outlives the session by months and syncs via Chrome/Firefox history sync.
- **Referer leakage** — any third-party resource loaded by the callback page (fonts in `assets/main.css`, analytics, error trackers) receives the full URL in `Referer`.
- **Refresh token is the prize** — with `SIMPLE_JWT.ACCESS_TOKEN_LIFETIME` at 1 day, the refresh token mints new access tokens indefinitely: a leaked URL equals account takeover, not a temporary session.
- Affects every Google sign-in in every environment; email/password users are unaffected.

## Suggested fix

**Frontend (minimal, ships independently) — scrub the URL before anything else can observe it.** Capture the raw query synchronously at setup, rewrite the address bar immediately, then validate:

```typescript
// OAuthCallback.vue <script setup>
import { ref, onMounted } from "vue";
import { useRouter } from "vue-router";
import { useAuthStore } from "@/stores/auth";

const router = useRouter();
const authStore = useAuthStore();
const isProcessing = ref(true);
const error = ref(false);
const errorMessage = ref("");

// Read the query ONCE, synchronously, then strip it from the URL/history
// before any await, render, or third-party request can observe it.
const query = { ...router.currentRoute.value.query };
window.history.replaceState(window.history.state, "", window.location.pathname);

const redirectToSignIn = () => router.push({ name: "sign-in" });

onMounted(async () => {
    try {
        if (query.auth_success !== "true") {
            throw new Error((query.auth_message as string) || "Authentication failed");
        }
        if (!query.tokens || !query.user) throw new Error("Missing authentication data");

        const tokens = JSON.parse(decodeURIComponent(query.tokens as string));
        const userData = JSON.parse(decodeURIComponent(query.user as string));

        authStore.setToken(tokens.access, tokens.refresh);
        authStore.setUser(userData);

        redirectToHome();
    } catch (err: any) {
        ...
    }
});
```

Notes on the patch: drop the cosmetic 1-second delay (line 64) — it only extends the window in which tokens sit in `localStorage`-adjacent state and the URL in referrer-reachable history entries; keep the existing error UI and 5-second redirect.

**Backend (the real fix, per `785cd6ee6d3241ee`)** — stop putting tokens in the URL at all: either return them in the JSON body of the existing code-exchange endpoint (`GoogleAuthTokenView`, `views.py:137-189`) via a frontend-initiated POST, or set the refresh token as an `HttpOnly; Secure; SameSite=Lax` cookie from the callback and hand back only the short-lived access token. Option: redirect with a single-use authorization code the frontend exchanges via POST — never the tokens themselves.

**Hardening regardless:** move session storage out of `localStorage` (XSS-readable) toward HttpOnly cookies, and shorten `ACCESS_TOKEN_LIFETIME` (30–60 min) so a leaked access token expires quickly.

## Applied fix

Not applied in this pass — this report documents the defect and provides the ready-to-apply patch above. The frontend scrub is a self-contained edit to `client/src/views/Auth/OAuthCallback.vue`; the backend change touches `apps/accounts/views.py` and the sign-in entry points in `SignIn.vue`/`SignUp.vue`.
