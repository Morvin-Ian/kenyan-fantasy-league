# `config/celery.py` hardcodes `config.settings.development` for the Celery app, so production worker/beat ignore `DJANGO_SETTINGS_MODULE` and run on development settings

## Summary

`config/celery.py:11` calls `app.config_from_object("config.settings.development", namespace="CELERY")` unconditionally. Every other entry point in the repo honors `DJANGO_SETTINGS_MODULE` — `docker-compose.prod.yml` sets it to `config.settings.production` for `api`, `celery_worker`, and `celery_beat` — but the Celery application object never reads it. In production the result is a split-brain process: the Django layer inside the worker/beat containers starts on production settings (via the env var), while the Celery app itself (broker URL, result backend, timezone, and any future `CELERY_*` knob) is configured from the development module. This is item #1 of incident `f6fce3d5db94b95b`, still unfixed — and it stopped being merely latent when commit `994136b` gave `production.py` settings that `development.py` does not have.

## What happened

Tracing how each container gets its settings:

| Process | Django settings | Celery app config |
|---|---|---|
| `api` (gunicorn, `docker/production/django/start`) | `config.settings.production` (compose `environment:` beats the `setdefault` in `config/wsgi.py:14`) | n/a |
| `celery_worker` (`docker/production/django/celery/worker/start`) | `config.settings.production` (compose `environment:` beats the `setdefault` in `config/celery.py:8`) | **`config.settings.development`** (`config/celery.py:11`) |
| `celery_beat` (`docker/production/django/celery/beat/start`) | `config.settings.production` (same mechanism) | **`config.settings.development`** |
| `manage.py` commands (CI migrate step, `ci.yml:126`) | whatever the shell exports; `manage.py:9` only defaults | n/a |

The relevant code, `config/celery.py:8-14`:

```python
os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings.development")

app = Celery("config")
app.config_from_object("config.settings.development", namespace="CELERY")

# Load task modules from all registered Django app configs.
app.autodiscover_tasks(lambda: settings.INSTALLED_APPS)
```

Line 8 is a `setdefault`, so the compose value wins and Django-side code in the worker runs production settings. Line 11 is unconditional and takes a literal module path, so the Celery app object is always configured from `development.py` regardless of environment.

When `f6fce3d5db94b95b` was written, `development.py` and `production.py` were byte-identical, which masked the bug. They no longer are: `production.py:32-71` now defines `SERVED_DOMAINS`/`pinned_hosts`, pins `ALLOWED_HOSTS`, and sets `SECURE_PROXY_SSL_HEADER`, `USE_X_FORWARDED_HOST`, `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`, and the HSTS trio — none of which exist in `development.py`. The divergence trap has sprung; it just hasn't caused a visible failure yet because none of the newly-divergent settings happen to affect task execution.

## Root cause

1. `config_from_object()` is called with a hardcoded string instead of resolving the module from the environment. The idiomatic form — `app.config_from_object("django.conf:settings", namespace="CELERY")`, or reading `os.environ["DJANGO_SETTINGS_MODULE"]` — was not used.
2. Nothing fails loudly: both settings modules read `CELERY_BROKER`/`CELERY_BACKEND` from the same env vars (`development.py:27-28`, `production.py:27-28`), so broker wiring is coincidentally correct and the misconfiguration is invisible in logs.
