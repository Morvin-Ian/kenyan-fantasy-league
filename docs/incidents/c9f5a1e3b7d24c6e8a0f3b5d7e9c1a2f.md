# Production deployment review (follow-up): dev tooling (`watchmedo`, `runserver`, Vite dev server) still ships in the deployable images, Celery still loads the development settings module, and no `dev.fantasykenya.com` preview environment exists in the repo

## What happened

A follow-up review of the production deployment path after incident `f6fce3d5db94b95b` (which flagged `watchmedo` in prod Celery scripts, `runserver` in prod, and dev-settings Celery). The reported symptom is that the `dev.fantasykenya.com` preview/staging environment appears to serve the app with development tooling. Verified against the current tree:

**Fixed since the last review:**
- The production `api` container now serves traffic with **gunicorn**, not `runserver`: `docker/production/django/start:13-18` (`exec gunicorn config.wsgi:application --bind 0.0.0.0:8000 ...`). `runserver` remains only in the dev image (`docker/local/django/start:12`).
- The production `celery_worker` and `celery_beat` scripts no longer use `watchmedo`; they `exec celery` directly (`docker/production/django/celery/worker/start:5`, `docker/production/django/celery/beat/start:9-11`).

**Still present (this report):**
1. `config/celery.py:11` **unconditionally** loads `config.settings.development` for the Celery app object, so the production worker and beat run on development settings despite `DJANGO_SETTINGS_MODULE=config.settings.production` being set in `docker-compose.prod.yml:15,78,96`.
2. `docker/production/django/celery/flower/start:6-7` still runs under `watchmedo auto-restart` — the one prod start script missed by the previous fix — and `watchdog==5.0.2` (`requirements.txt:71`) is still installed in every production image.
3. The production image installs the **entire dev/test toolchain**: `docker/production/django/Dockerfile:22` runs `pip3 install -r requirements.txt`, which includes `black`, `flake8`, `isort`, `pytest`, `pytest-cov`, `selenium`, `flower`, and `watchdog`; `Dockerfile:15` also apt-installs the `postgresql` server package.
4. **`dev.fantasykenya.com` does not exist anywhere in the repo** — no DNS entry, no nginx `server_name`, no certbot cert, no compose service. The only frontend serving paths the repo defines are the nginx static build for `fantasykenya.com`/`www.fantasykenya.com` and the Vite dev server on `0.0.0.0:3000`. If the preview is served by pointing a domain at the dev stack, the code that answers is exactly that dev tooling (`runserver` + `npm run dev`).

## Root cause

### 1. Celery ignores `DJANGO_SETTINGS_MODULE` and always loads `config.settings.development`

`config/celery.py:8-11`:

```python
os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings.development")

app = Celery("config")
app.config_from_object("config.settings.development", namespace="CELERY")
```

Line 11 is decisive: `config_from_object("config.settings.development", ...)` is unconditional, so even though `docker-compose.prod.yml` sets `DJANGO_SETTINGS_MODULE=config.settings.production` on `api` (line 15), `celery_worker` (line 78) and `celery_beat` (line 96), the Celery app object still reads `CELERY_*` from the development module. `manage.py:9` and `config/wsgi.py:14` use `setdefault`, so the env var wins there and the `api` container does run production settings — **only the background-task processes are pinned to dev settings.**

Today the two modules read the same env keys for `DATABASES` and `CELERY_*`, so nothing has visibly failed — but `config/settings/production.py:32-47` already diverges from `development.py` with 15 lines of security hardening (`SECURE_PROXY_SSL_HEADER`, `USE_X_FORWARDED_HOST`, `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`, `SESSION_COOKIE_HTTPONLY`, HSTS, `SECURE_CONTENT_TYPE_NOSNIFF`, `SECURE_REFERRER_POLICY`). Any task that builds responses, touches sessions/cookies, or constructs URLs runs without those protections. And the trap is a divergence bomb: the next edit that makes `production.py` differ (broker URL, task routing, timezone, logging, email, cache) will apply to `api` only and never to `worker`/`beat`, which will keep scheduling on dev settings silently.

### 2. One production start script still uses `watchmedo`, and `watchdog` is still in the production image

`docker/production/django/celery/flower/start:6-7` is unchanged from the dev version:

```bash
watchmedo auto-restart -d config/ -p "*.py" -- \
  celery --broker="redis://redis:6379/0" -A config.celery flower --port=5555
```

The script is copied into the image as `/start-flower` (`docker/production/django/Dockerfile:32-34`). Flower is not in the production compose, so this is latent today, but it is the same defect class the previous incident fixed for worker/beat: `watchmedo` (from `watchdog==5.0.2`, `requirements.txt:71`) spawns Celery as a child process, does not reliably forward SIGTERM (graceful shutdown is lost, in-flight tasks can be dropped), and hot-restarts the process whenever a `.py` file changes — which, on the VPS, races the deploy's `git pull --ff-only` (`ci.yml:118`). Any future addition of a `flower` service to `docker-compose.prod.yml` silently resurrects all of it.

### 3. The production image bundles the full dev/test toolchain

`docker/production/django/Dockerfile:22` installs every entry in `requirements.txt` into the image that runs in production: `black` (line 6), `flake8` (30), `isort` (35), `pytest` (75), `pytest-cov` (76), `selenium` (74), `flower` (31), `watchdog` (71). `Dockerfile:15` additionally apt-installs `postgresql` (the server) plus `build-essential`/`gcc`. None of these are used by the prod runtime (gunicorn + celery + psycopg2 only). This is image bloat and attack surface — notably `selenium`, a browser-automation framework with a Chromedriver dependency tree, and a full PostgreSQL server binary — with no compensating benefit. It is also the reason the prod image *can* run dev tooling at all.

### 4. There is no `dev.fantasykenya.com` preview environment in the repo

A repo-wide search for `dev.fantasykenya.com`, `preview`, and `staging` finds nothing that defines a preview environment (the only hits are unrelated: `client/package.json:9` `"preview": "vite preview"`, admin "preview" display fields, and a log message in `apps/kpl/tasks/standings.py:234`). The only domain references in the codebase are the production domain:

- `client/vite.config.ts:13-16` — `allowedHosts: ['fantasykenya.com', 'www.fantasykenya.com']` (note: `dev.fantasykenya.com` is **not** in this list).
- `docker/production/nginx/nginx.conf:8,24` — `server_name fantasykenya.com www.fantasykenya.com;` (HTTP redirect + HTTPS).
- `docker/production/nginx/nginx.conf:29-30` — TLS cert paths `/etc/letsencrypt/live/fantasykenya.com/...`.

The only two frontend serving paths the repo can produce:

- **Production:** `client/production/Dockerfile` builds the Vue app with `npm run build` and serves the static `dist/` from nginx on 80/443, proxying `/api/v1` and `/guardian` to `api:8000` (gunicorn). This is the only path wired to a domain.
- **Dev stack:** `docker-compose.yml:22-37` runs the `client` container with `command: npm run dev -- --host 0.0.0.0` on `0.0.0.0:3000` (`vite.config.ts:11` also sets `server.host: '0.0.0.0'`), and the `api` service's `8000:8000` port mapping is commented out (`docker-compose.yml:12-13`).

So the only way `dev.fantasykenya.com` could be served by dev tooling is if the VPS exposes the dev stack's ports (`:3000` Vite dev server, or `:8000` `runserver`) to the public internet — the repo itself never binds those ports to any domain, and Vite's `allowedHosts` would reject an unlisted `Host` header (a protection, not a configured solution). The server-side DNS/nginx/port mapping for the preview domain is outside the repo and cannot be verified from here; what the repo verifiably ships is the dev tooling in the deployable images and the dev-settings Celery, which is what this report documents.

## Suggested fix

1. **Make Celery read the settings module from the environment** (`config/celery.py:11`): replace the hardcoded module name with the same env value Django itself uses, e.g.
   ```python
   os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings.development")
   app = Celery("config")
   app.config_from_object(os.environ["DJANGO_SETTINGS_MODULE"], namespace="CELERY")
   ```
   `docker-compose.prod.yml` already sets `DJANGO_SETTINGS_MODULE=config.settings.production` on worker/beat, so this makes prod run prod settings with no compose change.
2. **Drop `watchmedo` from the prod flower script** (`docker/production/django/celery/flower/start:6-7`): mirror the worker/beat fix (`exec celery -A config.celery flower --port=5555`), or remove the script and `flower` from the production image entirely while flower is not in the prod compose.
3. **Split dev/test deps out of the production install**: move `black`, `flake8`, `isort`, `pytest`, `pytest-cov`, `selenium`, `flower`, `watchdog` into a dev-only requirements file (or a pip `--no-deps`/multi-stage install) so `docker/production/django/Dockerfile:22` installs only runtime deps. Also drop `postgresql` from `Dockerfile:15` (the app only needs `libpq`/`psycopg2-binary`).
4. **Define the preview environment explicitly** (whatever it should be): either a real staging compose that builds the production images with a staging `.env` (gunicorn + nginx static build, like prod), or — if the preview is intentionally the dev stack — put it behind the repo's nginx with a `server_name dev.fantasykenya.com;` block, TLS via certbot, and `/api/v1` proxying, instead of exposing raw `:3000`/`:8000`. At minimum, document in the README/Makefile what `dev.fantasykenya.com` is supposed to run, since today nothing in the repo mentions it.

## Applied fix

Not yet applied — this report documents the verified state and the concrete patch. The highest-value edit is #1 (Celery settings), which is a one-line change with an existing regression-testable contract; #2 and #3 remove the remaining dev tooling from the production image.
