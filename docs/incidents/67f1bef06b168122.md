# `.github/workflows/ci.yml` assumes nginx reload activates bind-mounted Host-rejection rules

## Verdict
defect — an unknown Host reached Django even though the repository’s nginx configuration rejects it; the deployment workflow relied on reloading an existing nginx process rather than guaranteeing it starts with the mounted edge configuration.

## What happened
A requester addressed the public deployment as `169.58.218.237`, and the request reached Django’s `CommonMiddleware`. Django correctly rejected the IP because production permits only `fantasykenya.com` and `www.fantasykenya.com`, producing the logged `DisallowedHost` before an application view or data mutation ran. The checked-in nginx configuration should reject that Host at the edge with `444`, so the live nginx process had not loaded the expected configuration.

## Root cause
`.github/workflows/ci.yml:120-124` previously assumed that `docker compose up --build -d --remove-orphans` followed by `nginx -s reload` always applied the bind-mounted configuration:

```sh
$compose up --build -d --remove-orphans
$compose exec -T nginx nginx -s reload
```

`docker-compose.prod.yml:54` bind-mounts `docker/production/nginx/nginx.conf` into the container. That configuration contains an HTTP default server which rejects unmatched Hosts at `docker/production/nginx/nginx.conf:8-12`, a TLS default rejecting unknown SNI at `:14-21`, and an application-host guard at `:46-48`; the proxy locations only occur later at `:72-86`. The failed assumption is that a reload command against an existing container is sufficient to ensure the live worker has loaded the current mount; it does not guarantee recovery from stale process state or a failed/unapplied reload.

The Django dependency files named by the traceback are outside this repository and could not be read. The repository does not reveal whether the affected live deployment bypassed GitHub Actions, used an older revision, or had a reload failure.

## How to reproduce
1. Run nginx using an older configuration which proxies `/api/v1` or `/guardian` while preserving `Host`.
2. Update the bind-mounted `docker/production/nginx/nginx.conf` without ensuring nginx is recreated with that configuration.
3. Send a request to a proxied path with:

```http
Host: 169.58.218.237
```

The stale nginx process can forward the host to Django, which raises `DisallowedHost`. With the current nginx configuration loaded, nginx returns `444` before Django receives the request.

## Blast radius
Any unknown Host directed at `/api/v1` or `/guardian` can reach Django while a deployment retains stale nginx configuration. Valid requests for `fantasykenya.com` and `www.fantasykenya.com` continue through the existing routes.

## Likely cause commit
cc10945 (`maajun: incident report for docker-compose.prod.yml delays nginx host-rejection configur…`) most plausibly introduced the insufficient activation approach: it added periodic and explicit reload handling, but did not recreate nginx to guarantee the process starts with the current bind-mounted edge rules.

## Applied fix
- `.github/workflows/ci.yml:120-124` now force-recreates only the nginx service with `$compose up -d --force-recreate --no-deps nginx` after the main compose update and before the explicit reload. This guarantees nginx starts from the current bind-mounted `nginx.conf` rather than retaining a stale process configuration.
- `tests/test_allowed_hosts.py:137-144` now asserts that the production workflow force-recreates nginx and retains the explicit reload command, so removal of either activation measure fails the regression test.

Verify by deploying through the GitHub Actions workflow, then requesting `/api/v1/` with `Host: 169.58.218.237`; nginx should close the request with `444` and no corresponding `django.security.DisallowedHost` entry should appear in `docker:api`. I could not run tests, deploy, or inspect the live nginx process because this environment has no command-execution access.
