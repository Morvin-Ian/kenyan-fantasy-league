# `DisallowedHost: Invalid HTTP_HOST header: 'fantasykenya.com'` — production API rejects its own domain

## What happened
Every request the nginx proxy forwards to the Django API with `Host: fantasykenya.com` (or `www.fantasykenya.com`) was rejected before reaching any view. Django's `CommonMiddleware` calls `request.get_host()` (`django/middleware/common.py:48`), which raises `DisallowedHost` because the host is not in `ALLOWED_HOSTS`. The user sees nginx pass through a Django 400 response — the whole `/api/v1` and `/guardian` API surface is down for the public site.

## Root cause
`config/settings/base.py:47` builds `ALLOWED_HOSTS` *exclusively* from an environment variable:

```python
ALLOWED_HOSTS = [h for h in os.getenv("ALLOWED_HOSTS", "*").split(" ") if h]
```

The deployment's env file (`.env.prod`, gitignored, lives only on the server) sets `ALLOWED_HOSTS` to a value that does **not** contain `fantasykenya.com` (the error proves the resolved list excludes it; it could be a stale dev value like `localhost api` or empty, which would resolve to `[]`). The assumption that does not hold: *"the deployment's `ALLOWED_HOSTS` env var will include the site's real domains."* The env file predates the setting becoming authoritative. Commit `2bbdb28` (the fix for incident `bb1261de30d1dac3`, documented in `docs/incidents/bb1261de30d1dac3.md:20-33`) replaced the previously hardcoded `ALLOWED_HOSTS = ["*"]` with this env-driven expression — the wildcard used to accept the domain silently, so the stale env value never mattered until that commit deployed.

Two aggravating facts verified in the repo:
- The deployment runs `python3 manage.py runserver` (`docker/production/django/start:12`), and `manage.py:9` hardcodes `DJANGO_SETTINGS_MODULE = config.settings.development` (also `wsgi.py:14`). So `config/settings/production.py` is **never loaded** — `base.py` is the effective settings, and a fix placed in `production.py` would be dead code.
- `docker/production/nginx/nginx.conf:52` (`proxy_set_header Host $host;`) forwards the browser's `Host` header verbatim, so the domain reaches Django exactly as `fantasykenya.com`.

## How to reproduce
Point any HTTP client at the API with the real host header, with the deployment's `ALLOWED_HOSTS` env value unchanged (e.g. `ALLOWED_HOSTS="localhost api"` in `.env.prod`):

```
curl -H "Host: fantasykenya.com" http://<server>/api/v1/...
```

→ Django 400 `DisallowedHost`. With `ALLOWED_HOSTS` unset the default `"*"` hides the bug; with the pre-`2bbdb28` code (`["*"]`) it could not occur at all.

## Blast radius
The entire public API: nginx routes both `/api/v1` and `/guardian` to Django with the original `Host` header (`docker/production/nginx/nginx.conf:48-62`), so **every** request for any user is rejected, and `www.fantasykenya.com` fails identically. Static files and the Vue bundle are served by nginx and unaffected.

## Likely cause commit
`2bbdb28` — "maajun: manual report for What do you think can be imporoved in these site." It changed `ALLOWED_HOSTS` from the hardcoded `["*"]` to the env-driven expression now at `base.py:47`, making a stale server-side env value authoritative and thereby rejecting the site's own domain (confirmed by `docs/incidents/bb1261de30d1dac3.md:20-33`, which documents exactly this change, and the error's start time shortly after that deploy).

## Suggested fix
In `config/settings/base.py:47-51`, always merge the production domains into `ALLOWED_HOSTS` so a stale or missing env value can no longer reject the site's own domain. The env-driven list and the `"*"` default are preserved, so dev/CI behavior is unchanged:

```python
ALLOWED_HOSTS = [
    *[h for h in os.getenv("ALLOWED_HOSTS", "*").split(" ") if h],
    "fantasykenya.com",
    "www.fantasykenya.com",
]
```

Regression test (added, `config/settings/test_settings.py`) — fails before the change (with `ALLOWED_HOSTS="localhost api"`, `ALLOWED_HOSTS` resolves to `["localhost", "api"]` and the assertions fail), passes after:

```python
def test_production_domains_allowed_even_when_env_has_stale_value(monkeypatch):
    monkeypatch.setenv("ALLOWED_HOSTS", "localhost api")
    importlib.reload(base_settings)
    assert "fantasykenya.com" in base_settings.ALLOWED_HOSTS
    assert "www.fantasykenya.com" in base_settings.ALLOWED_HOSTS
```

Note: this repo change alone removes the reported failure. Separately, the server's `.env.prod` should be updated to `ALLOWED_HOSTS=fantasykenya.com www.fantasykenya.com` (best practice + closes the `"*"` default in production), but that file is outside this repository.

## Applied fix
- `config/settings/base.py` — `ALLOWED_HOSTS` now always includes `fantasykenya.com` and `www.fantasykenya.com` in addition to the env-driven list (env default `"*"` unchanged). One targeted change, no other lines touched.
- `config/settings/test_settings.py` — new pytest module (project has no existing test files; `pytest.ini` already points at `config.settings.development` and `pytest-django==4.9.0` is in `requirements.txt`). Two tests reload `config.settings.base` with a stale `ALLOWED_HOSTS` value and with the env var unset, asserting the production domains are always accepted.

Verify with: `docker compose exec api pytest config/settings/test_settings.py` (or `make test`); both tests pass, and both fail on the pre-fix `base.py`. Then re-run any request with `Host: fantasykenya.com` — it now reaches the views instead of returning 400.

What I could not determine: the exact `ALLOWED_HOSTS` value in the server's `.env.prod` (gitignored, absent from the clone). The error only proves it resolves to a list excluding `fantasykenya.com`; the fix makes that value harmless either way.
