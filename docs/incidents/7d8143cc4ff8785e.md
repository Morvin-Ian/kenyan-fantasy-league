# `tests/test_allowed_hosts.py` did not require nginx’s unknown-host guard to return before proxying

## Verdict
defect — the regression test only checked that the host guard text and an unrelated `return 444` existed somewhere in nginx configuration, so it could pass even if the guard stopped rejecting unrecognised hosts.

## What happened
A request with `Host: grafana.fantasykenya.com` reached Django on the live deployment. Django’s `CommonMiddleware` rejected the host before a view ran because it is not an allowed production domain, resulting in the logged `DisallowedHost` traceback.

The checked-in edge configuration is intended to close this request with nginx status `444` before Django receives it, but the existing test did not prove that the host guard itself performed that rejection. The supplied server logfile could not be read directly because it is outside the accessible workspace.

## Root cause
`tests/test_allowed_hosts.py:105-119` tested the two required nginx fragments independently:

```python
assert "if ($host !~ ^(fantasykenya\\.com|www\\.fantasykenya\\.com)$) {" in conf
assert "return 444;" in conf
```

The second assertion could be satisfied by either default-server rejection at `docker/production/nginx/nginx.conf:11` or `:23`, without requiring the KFL TLS guard to return. The test therefore assumed the presence of any `return 444;` established that the `$host` guard rejected invalid hostnames; that assumption does not hold.

The relevant nginx logic is at `docker/production/nginx/nginx.conf:47-51`:

```nginx
if ($host !~ ^(fantasykenya\.com|www\.fantasykenya\.com)$) {
    return 444;
}
```

It is designed to reject `grafana.fantasykenya.com`, because Django production settings allow only `fantasykenya.com` and `www.fantasykenya.com` at `config/settings/production.py:45-54`. The live error indicates that this configuration was not effective on the running request path; the repository cannot determine whether that was an un-reloaded/stale nginx container, a different mounted configuration, or a bypassing proxy.

## How to reproduce
Before the nginx guard is active, send a request to a Django-proxied endpoint with:

```http
GET /api/v1/ HTTP/1.1
Host: grafana.fantasykenya.com
```

The `/api/v1` proxy preserves the incoming host at `docker/production/nginx/nginx.conf:75-80`, and Django rejects it because it is absent from `SERVED_DOMAINS` at `config/settings/production.py:45`. With the guard loaded, nginx returns `444` at `docker/production/nginx/nginx.conf:47-51` before proxying.

## Blast radius
Any unrecognised hostname sent to `/api/v1` or `/guardian` can produce the same Django log entry when the intended nginx guard is absent or ineffective; both locations forward `Host $host` at `docker/production/nginx/nginx.conf:75-89`. Valid KFL hosts retain existing routing, and `mogul.fantasykenya.com` remains isolated in `docker/production/nginx/mogul.conf:41-90`.

## Likely cause commit
27cbf1f (`feat: serve mogul.manager from the shared nginx edge`) most plausibly introduced the edge-host-routing risk: the repository’s prior incident record identifies it as adding the shared nginx virtual-host arrangement while unmatched names continued to select the KFL server.

## Applied fix
- `tests/test_allowed_hosts.py:105-119` now uses one regular expression that requires `return 444;` inside the specific KFL `$host` rejection block, rather than accepting an unrelated `return 444;` elsewhere in the file. The test fails if a future nginx edit removes or separates the guard’s rejection while leaving default-server rejections intact.

Verification is to run `pytest tests/test_allowed_hosts.py`, then reload/recreate the production nginx container from the checked-in compose configuration. Requesting `/api/v1/` with `Host: grafana.fantasykenya.com` should result in nginx closing the request with `444` and no corresponding `django.security.DisallowedHost` record. I could not execute tests or reload nginx because this environment has no command-execution tool.
