# Google OAuth JWT tokens were placed directly in the redirect URL, leaking the user's session into browser history, server access logs, and Referer headers

**Summary:** `apps/accounts/views.py` (`GoogleAuthCallbackView`) appended the freshly-issued JWT `access`/`refresh` tokens and the full user payload to the frontend redirect URL after every Google sign-in, so each login persisted the user's credentials in browser history, the web server's access logs, and any `Referer` header sent onward from the callback page.

## What happened

After signing in with "Continue with Google", the backend redirected the browser to the frontend with the session credentials embedded in the query string — an `access` token (24 h lifetime) and `refresh` token (7 d lifetime), plus the user object. Anyone with read access to the browser's history, the API/nginx access logs, or a `Referer` header the callback page emitted could replay those tokens against `/api/v1/*` and fully impersonate the user (including profile PATCH and every authenticated fantasy endpoint). The tokens never expired at the moment of the leak, so a leaked pair stayed valid for up to a week.

## Root cause

`GoogleAuthCallbackView.get` in `apps/accounts/views.py` built the success redirect by interpolating the tokens directly into the URL. Query strings are persisted in exactly the places the credentials must not go:

1. **Browser history** — the URL with `access=<JWT>&refresh=<JWT>` is saved by the browser, and is also visible via the Back button and in autocomplete.
2. **Server access logs** — nginx and Django log the full request line, including the query string, on the *frontend* host that receives the redirect (and the API host if the redirect target is ever logged there).
3. **Referer headers** — the callback page that loads from the URL carries the whole token-bearing URL in its `Referer` header to every subsequent request it makes, including to third-party resources.

JWT `refresh` tokens are the account-revocation problem in particular: they are opaque long-lived credentials, and `simplejwt`'s blacklist is only effective if the *stolen* token is the one presented — a leaked refresh token lets an attacker mint fresh access tokens for the entire 7-day window.

## How to reproduce

1. Start the stack and click "Continue with Google".
2. Complete the Google consent screen.
3. Observe the browser address bar after the callback: the URL contains `?auth_success=true&access=<JWT>&refresh=<JWT>&user=<payload>` (pre-fix behavior).
4. Open DevTools → History (or check the server access log) — the full credential-bearing URL is retained.

## Blast radius

- **Every Google sign-in** (new registration and existing-user login) leaked credentials; the email/password flow uses `POST /auth/jwt/create/` and is unaffected.
- The credentials are **valid for 24 h / 7 d** from issuance, so a log file or shared machine exposed a working session long after the user signed in.
- The leak is silent — the user sees a perfectly normal login; the damage is purely in the artifacts the URL leaves behind.

## Likely cause commit

The token-in-URL redirect predates the current `auth_code` exchange (see the "Applied fix" below) and was introduced with the original OAuth callback flow. Recent master history (CI workflow, black/flake8/isort formatting, docs, and the `services.py` env-trimming fix) does not touch this mechanism.

## Suggested fix

Stop putting credentials in the URL. The backend should stash the token payload in a short-lived, single-use store (Django cache) and redirect with only an opaque one-time code; the frontend should then redeem the code over a `POST` request whose body never enters the URL.

## Applied fix

Three files changed, matching the repo's existing security-review pattern:

1. **`apps/accounts/views.py`**
   - `GoogleAuthCallbackView.get` no longer embeds tokens in the redirect. It generates a one-time code (`secrets.token_urlsafe(32)`, `views.py:124`), caches the `{access, refresh, user, is_new_user, expires_in}` payload under `google_oauth_auth_code:<code>` with a 60-second TTL (`OAUTH_AUTH_CODE_TTL_SECONDS`, `views.py:22`), and redirects with only `?auth_success=true&auth_code=<code>&is_new_user=...&origin=...` (`views.py:138-141`).
   - `GoogleAuthTokenView.post` now redeems that code (`views.py:172-184`): it looks the payload up in cache, returns `400 "Invalid or expired authorization code."` when missing, and deletes the key *before* returning so each code is single-use. The legacy `code`/`id_token`/`access_token` exchange path remains for API clients.
2. **`apps/accounts/serializers.py`**
   - `GoogleAuthSerializer` gained the `auth_code` field (`serializers.py:59`) and its `validate` now accepts `auth_code` alongside `code`/`id_token`/`access_token` (`serializers.py:61-73`).
