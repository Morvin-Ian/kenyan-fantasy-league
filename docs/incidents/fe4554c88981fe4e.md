# Incident Report: Production hardening review — "What do you think can be improved in these site."

**Error summary:** A review of the KPL Fantasy League production path (compose, Django settings, Celery wiring, and the Vue client) found four concrete, verifiable issues — one latent Celery configuration trap, one crash-recovery gap, and two configuration/robustness weaknesses — plus a handful of small client-side items carried over from the previous review (`docs/incidents/bb1261de30d1dac3.md`). The two big production-wiring fixes from `docs/incidents/f6fce3d5db94b95b.md` (gunicorn in `/start`, `exec celery` in the worker/beat scripts) are confirmed in place; the third fix from that report is **not**.

---

### 1. High — Celery still hardcodes `config.settings.development`; prod worker/beat ignore `DJANGO_SETTINGS_MODULE`

**File:** `config/celery.py:8-11`

```python
os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings.development")

app = Celery("config")
app.config_from_object("config.settings.development", namespace="CELERY")
```

**What happened / root cause:** The second line is unconditional. `docker-compose.prod.yml:14-15,77-78,95-96` sets `DJANGO_SETTINGS_MODULE=config.settings.production` for the `api`, `celery_worker`, and `celery_beat` containers, but every Celery app reads its `CELERY_*` keys from the **development** module regardless. Today this is latent: `config/settings/production.py:27-29` and `config/settings/development.py:27-29` are identical for `CELERY_BROKER_URL`/`CELERY_RESULT_BACKEND`, and `CELERY_TIMEZONE` matches too. The moment production.py diverges (broker URL, result backend, task routing, timezone, logging, email), the `api` container gets the new value and all background work silently keeps the old one — exactly the divergence trap `f6fce3d5db94b95b.md` documented as defect #1. Note that report's "Applied fix" section was never written (the file truncates mid-sentence at line 53), and the code confirms the fix was **not** applied — while the other two defects from that report *were* fixed (`docker/production/django/start:13-18` now runs gunicorn; `celery/worker/start:5` and `celery/beat/start:9` now `exec` celery directly).

**Suggested fix:**

```python
app.config_from_object("django.conf:settings", namespace="CELERY")
```

This makes Celery read `CELERY_*` from the settings module selected by the environment (production on the server, development locally), removing the hardcoded module name.

### 2. High — No healthchecks and no `restart` policy on the stateful/critical services → a crash is permanent

**File:** `docker-compose.prod.yml:2-20, 22-42, 65-101`

**What happened / root cause:** `postgres-db` and `redis` have no `healthcheck:`, and `api`/`celery_worker`/`celery_beat` have no `restart:` policy (only `nginx`, `certbot`, and `selenium` restart). Consequences:

- `api` `depends_on: [postgres-db, redis]` (lines 16-18) fires the moment the *containers exist*, not when Postgres accepts connections — the entrypoint's poll loop is the only guard, and it bounds the whole first-boot init window (30 attempts × 2 s).
- If any of `api`/`worker`/`beat` exits 1 — OOM, a transient DB hiccup past the poll budget, a segfault in the scraper — nothing brings it back; the site stays down until a human runs `docker compose up -d`. This is the same gap `docs/incidents/7e4a9c1b2d3f4a5b6c7d8e9f0a1b2c3d.md` flagged as "Not yet applied."

**Suggested fix:** add `pg_isready`/`redis-cli ping` healthchecks with `condition: service_healthy` in `depends_on`, and add `restart: unless-stopped` to `api`, `celery_worker`, `celery_beat` (and ideally `postgres-db`, `redis`).

### 3. Medium — Production does not force `DEBUG = False`

**File:** `config/settings/base.py:47` / `config/settings/production.py`

**What happened / root cause:** The earlier fix (`bb1261de30d1dac3`) correctly coerces the env value to a boolean, but production still *trusts* the env: `DEBUG = env("DEBUG", "false").lower() == "true"`. If `.env.prod` ever contains `DEBUG=true` (or a typo like `DEBUG= yes`), the production site serves Django's verbose error pages — stack traces, settings, environment — to anyone who triggers a 500. `production.py` is the one place where this should be non-negotiable.

**Suggested fix:** add `DEBUG = False` to `config/settings/production.py` (it will override the base value unconditionally).
