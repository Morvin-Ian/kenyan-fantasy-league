# Incident Report: Site down — `api` container exits with code 1 (`entrypoint` cannot reach PostgreSQL)

## What happened

The Kenyan Fantasy League site went down. The `api` container exits with code 1 on `docker compose up` (dev) and on the CI deploy (`docker compose -f docker-compose.prod.yml --env-file .env.prod up --build -d`), while `postgres-db` itself is `Up`:

- `docker compose ps` shows `api` **Exited (1)**.
- `docker compose logs api` shows one of:
  - `Error: Missing required environment variables: POSTGRES_DB PG_USER PG_PASSWORD PG_HOST PG_PORT`
  - `Attempt N of 30: PostgreSQL is not ready yet...` repeated 30 times, then `Error: PostgreSQL failed to become available after 30 attempts`
  - a Python traceback from `psycopg2.connect(...)` (a mangled-heredoc syntax error or `FATAL: password authentication failed`)
- Nothing listens on `:8000`. The CI deploy's migrate-retry loop (`ci.yml:125-137`) then fails with `api not ready yet (attempt N)` and dumps the `api` logs.

## Root cause

The `api` image's entrypoint is a bash script that runs **before** `/start` (the CMD):

- `docker/production/django/entrypoint` and `docker/local/django/entrypoint` are identical and wired via `ENTRYPOINT ["/entrypoint"]` in both `docker/production/django/Dockerfile:44` and `docker/local/django/Dockerfile:44`.
- It starts with `set -o errexit set -o pipefail set -o nounset` (lines 4–6), so **any** failing step exits non-zero and the container dies with code 1.
- It has two hard gates: `check_required_vars()` (lines 9–23) and the PostgreSQL poll loop (lines 54–67).

Six independent defects make this crash on perfectly normal setups:

### 1. Five env vars are mandatory, but the repo ships no usable template

`check_required_vars()` requires `POSTGRES_DB`, `PG_USER`, `PG_PASSWORD`, `PG_HOST`, `PG_PORT` (line 10). These same five are read by Django in `config/settings/development.py:18-22` and `config/settings/production.py:18-22`, and are interpolated into the postgres service in both `docker-compose.yml:47-49` and `docker-compose.prod.yml:28-30`.

`.env` / `.env.prod` are gitignored (`.gitignore:130-131`). On a fresh clone there is **no `.env`**, so `env_file: .env` (`docker-compose.yml:15`) already fails before anything starts; if a partial or placeholder env is copied in, the entrypoint exits 1 with the missing-vars message. The `.env.example` in the repo is a credential-protected placeholder and does not document these five keys.

### 2. Credential drift against the persistent `postgres_data` volume

`POSTGRES_USER/PASSWORD/DB` only initialize the cluster on the **first boot of an empty volume**. If `.env` is later edited (e.g. a new `PG_PASSWORD`) while `postgres_data` persists, postgres keeps the old credentials and the entrypoint's `psycopg2.connect` loops `FATAL: password authentication failed` until `max_attempts=30` (≈60 s) and exits 1. The same happens when dev `.env` and prod `.env.prod` disagree with what the volume was created with.

### 3. No healthcheck + no restart policy → crash is permanent

- `api` `depends_on: postgres-db` (both compose files) but postgres has **no `healthcheck`**, so compose starts `api` the moment the postgres *container* exists, not when it accepts connections — the entrypoint poll loop is the only guard, and 30 attempts × 2 s is the entire budget for first-boot init.
- Neither `api` nor `postgres-db` has a `restart:` policy (only `client`/`nginx`/`selenium` do), so once the entrypoint exits 1 the container stays `Exited (1)` and nothing ever brings it back.

### 4. The unquoted heredoc corrupts passwords (and any special chars)

`postgres_ready()` builds the Python source by shell-interpolating env vars into an **unquoted** heredoc (lines 27–47):

```bash
python3 << END
...
conn = psycopg2.connect(
    dbname="${POSTGRES_DB}",
    user="${PG_USER}",
    password="${PG_PASSWORD}",
    host="${PG_HOST}",
    port="${PG_PORT}",
)
```

Because the delimiter is unquoted, bash expands `$`, backticks, `\`, and globs in the body **before** Python sees it. Any `PG_PASSWORD` containing `$`, `` ` ``, `\`, or a single quote (e.g. `Babyna3*.` from `init-db.sql`, or a random secret generator's `$`/backtick) produces a mangled connection string or a Python syntax error — a confusing traceback instead of a clean auth failure. The same entrypoint runs on every DB-talking container (`api`, `celery_worker`, `celery_beat` in both compose files), so all of them fail identically.

### 5. No connect timeout → the "60 second" wait can hang for many minutes

`psycopg2.connect(...)` is called with no `connect_timeout`. When `PG_HOST`/`PG_PORT` point at something unreachable, each attempt blocks on the OS TCP timeout (often ≥ 2 minutes), so 30 attempts take far longer than the nominal ~60 s and the `api` container looks hung rather than failing fast.

### 6. `init-db.sql` is dead weight and a credential trap

`init-db.sql` (`CREATE USER root WITH PASSWORD 'Babyna3*.'; CREATE DATABASE fpl`) is **never mounted** into `/docker-entrypoint-initdb.d/` in either compose file, so it never executes — real init comes from the `POSTGRES_*` interpolation. Its hardcoded password is also not the prod secret, so anyone who copies it into `.env` gets defects #4 and #2 for free.

## How to reproduce

1. Fresh clone with no `.env` → `docker compose up` fails at `env_file: .env` / the entrypoint's missing-vars gate (defect #1), or
2. Set `PG_PASSWORD` in `.env`/`.env.prod` to a value containing a shell metacharacter (e.g. `pa$$word`, `Babyna3*.`, or a `$`/backtick from a password generator) → mangled connection string / Python syntax error in the heredoc (defect #4), or
3. Change `PG_PASSWORD` in `.env` while `postgres_data` persists → `FATAL: password authentication failed` × 30 → exit 1 (defect #2), or
4. Point `PG_HOST`/`PG_PORT` at an unreachable address → each attempt hangs on the OS TCP timeout for minutes (defect #5).

In every case the entrypoint exits 1 and, with no `restart` policy (defect #3), the `api` container stays dead until manually restarted.

## Blast radius

Every container using the shared Django image hits this on every start: `api`, `celery_worker`, `celery_beat` in both `docker-compose.yml` and `docker-compose.prod.yml`. The heredoc/volume defects affect every developer, CI run, and the production deploy; there is no environment in which a fresh or drift-prone setup survives the entrypoint unchanged.

## Suggested fix

Apply all of the following (each removes one exit-code-1 path):

1. **Ship a real `.env.example`** documenting all five vars plus `SECRET_KEY`/`DEBUG`, and add a `cp .env.example .env` note to the README/Makefile.
2. **Make the poll script injection-safe and bounded.** Pass values via the environment and use a quoted delimiter so bash never expands them, and add `connect_timeout`:

   ```bash
   postgres_ready() {
       POSTGRES_DB="$POSTGRES_DB" PG_USER="$PG_USER" PG_PASSWORD="$PG_PASSWORD" \
       PG_HOST="$PG_HOST" PG_PORT="$PG_PORT" python3 - <<'END'
   import os, sys, psycopg2
   try:
       psycopg2.connect(
           dbname=os.environ["POSTGRES_DB"],
           user=os.environ["PG_USER"],
           password=os.environ["PG_PASSWORD"],
           host=os.environ["PG_HOST"],
           port=os.environ["PG_PORT"],
           connect_timeout=5,
       )
       sys.exit(0)
   except psycopg2.OperationalError as e:
       print(f"Connection failed: {e}", file=sys.stderr)
       sys.exit(1)
   END
   }
   ```

3. **Healthcheck + restart + proper dependency ordering** in both compose files:

   ```yaml
   postgres-db:
     healthcheck:
       test: ["CMD-SHELL", "pg_isready -U ${PG_USER} -d ${POSTGRES_DB}"]
       interval: 5s
       timeout: 5s
       retries: 10
     restart: unless-stopped
   api:
     depends_on:
       postgres-db:
         condition: service_healthy
       redis:
         condition: service_started
     restart: unless-stopped
   ```

4. **Document the volume-credential rule:** changing `PG_*` requires `docker compose down -v` (destructive — wipes data) or `ALTER USER ... PASSWORD` inside the running container. Never mix dev and prod credentials against one volume.
5. **Wire `init-db.sql` into `/docker-entrypoint-initdb.d/` or delete it** — and never reuse its hardcoded `Babyna3*.` password in `.env`.

## Applied fix

The quoted-heredoc/env-forwarding part of #2 (and the `connect_timeout`) has been applied to both `docker/local/django/entrypoint` and `docker/production/django/entrypoint`, with a regression test added at `tests/test_entrypoint.py` that asserts both entrypoints use a quoted heredoc (`<<'END'`), read all five `PG_*`/`POSTGRES_DB` values via `os.environ[...]`, and contain no braced `${PG_*}` shell expansion. Items #1, #3, #4, and #5 (env template, healthcheck/restart wiring, volume-drift documentation, and the `init-db.sql` cleanup) remain open in the repo.

## Verification

I cannot run Docker or the app in this environment. Changes were validated by reading: both entrypoints, both Django Dockerfiles, both compose files, `config/settings/development.py` / `production.py`, the CI workflow, `.gitignore`, `Makefile`, `init-db.sql`, and `requirements.txt` (`psycopg2-binary==2.9.9`, so `psycopg2` is importable inside the image and the entrypoint's `python3` heredoc is the right tool — it just needs to be quoted and bounded).

On the server: rebuild and run `docker compose -f docker-compose.prod.yml --env-file .env.prod up --build -d`, confirm the api log shows `PostgreSQL is ready!`, and the site answers on port 80.
