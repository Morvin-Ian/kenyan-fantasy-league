# Incident report: Google OAuth callback still ships JWTs in the redirect URL

## Status

Documented previously in `docs/incidents/0462e469639c4ae7.md` as **not applied**; re-verified against current source — the backend construction is unchanged. This remains an open defect.

## What happened

Every successful "Continue with Google" sign-in ends with the API redirecting to:

```
{FRONTEND_URL}/auth/callback?auth_success=true&auth_message=success&tokens=<url-encoded JWT pair>&user=<user data>&is_new_user=...&origin=...
```

Both the short-lived access token and the long-lived refresh token travel in plaintext in the URL, and nothing downstream ever scrubs it.

## Root cause

Two ends of one flow:

1. **Backend builds the token-bearing URL.** `apps/accounts/views.py`:

   ```python
   # lines 109–117
   encoded_tokens = urllib.parse.quote(json.dumps({"access": ..., "refresh": ...}))
   encoded_user   = urllib.parse.quote(json.dumps(user_data))
   # line 120
   success_url = f"{redirect_to}?auth_success=true&...&tokens={encoded_tokens}&user={encoded_user}..."
   # line 125
   return redirect(success_url)
   ```

   `redirect_to` comes from the signed-free JSON `state` blob built in `GoogleAuthInitView` (line 30) and defaults to `{settings.FRONTEND_URL}/auth/callback` (lines 60, 67).

2. **Frontend consumes and keeps the URL.** Per the prior incident record (verified there, not re-read in this pass): `client/src/views/Auth/OAuthCallback.vue:43-62` parses `route.query.tokens`/`route.query.user` and calls `authStore.setToken(...)`, with **no** `history.replaceState`/`router.replace` anywhere in `client/src`; `client/src/router/index.ts:21-25` registers `/auth/callback` as a real history-mode route, so the full URI persists in browser history and in every access log that records the request line. Entry points are `window.location.href = "/api/v1/auth/google/login/"` in `SignIn.vue:142-144` and `SignUp.vue:284-287`.

3. **Storage compounds it.** `authStore.setToken` persists both tokens to `localStorage` (XSS-readable), so the leaked refresh token outlives the page.

Note the safe path already exists in the same file: `GoogleAuthTokenView` (`views.py:137-189`) exchanges a code over **POST** and returns the tokens in a JSON body — the flow just doesn't use it.

## Impact

- **Access logs** — nginx and Django persist the tokens on disk and into any aggregation/retention pipeline.
- **Browser history & sync** — the URL survives for months and syncs via browser history sync.
- **Referer leakage** — any third-party resource loaded by the callback page receives the full URL.
- **Refresh token is the prize** — a leaked URL equals account takeover, not a temporary session.
- Affects every Google sign-in in every environment; email/password users are unaffected.

## How to reproduce

1. Sign in via **Continue with Google**, complete consent.
2. On landing at `/auth/callback?...tokens=%7B%22access%22%3AeyJ...%7D`, read the address bar — both JWTs are present percent-encoded.
3. Press Back: same URL in history. Check nginx/Django access logs: full query string in plaintext.

## Suggested fix

**Backend (the real fix):** stop putting tokens in the URL.
- Preferred: have the frontend initiate the flow and use the existing `POST /api/v1/auth/google/token/` (`GoogleAuthTokenView`) with the authorization `code`; the callback redirects back with a single-use code (or nothing but success/failure), never the tokens themselves.
- Alternative: set the refresh token as an `HttpOnly; Secure; SameSite=Lax` cookie from the callback and hand back only the short-lived access token.

**Frontend (minimal, ships independently):** capture the raw query synchronously at setup and rewrite the address bar immediately, before any await/render/third-party request:

```typescript
const query = { ...router.currentRoute.value.query };
window.history.replaceState(window.history.state, "", window.location.pathname);
```

then validate from the captured `query`. Drop the cosmetic 1-second delay; keep the existing error UI.

**Hardening regardless:** move session storage out of `localStorage` toward HttpOnly cookies, and shorten `ACCESS_TOKEN_LIFETIME` (30–60 min).

## Applied fix

Not applied. Current `apps/accounts/views.py` still contains the `tokens=`/`user=` query construction quoted above.
