# Production `ALLOWED_HOSTS` omits the SSO hostname in `config/settings/production.py`

## Verdict
defect — `sso.fantasykenya.com` is a deployment hostname that Django rejects before the request reaches an application view.

## What happened
A request addressed to `sso.fantasykenya.com` reached the Django API and was rejected by `CommonMiddleware` when `request.get_host()` validated the `Host` header. Django production settings allowed only `fantasykenya.com` and `www.fantasykenya.com`, so the caller received Django’s invalid-host response and the API logged `DisallowedHost`.

## Root cause
At `config/settings/production.py:45-54`, production derives its host allowlist from:

```python
SERVED_DOMAINS = ["fantasykenya.com", "www.fantasykenya.com"]
ALLOWED_HOSTS = pinned_hosts(ALLOWED_HOSTS, SERVED_DOMAINS)
```

The assumption that the two `SERVED_DOMAINS` entries were the complete set of deployment hostnames did not hold: the live request used `sso.fantasykenya.com`. Since that hostname was absent from the resulting `ALLOWED_HOSTS`, Django correctly raised the exception at the dependency frame `django/http/request.py:150`. The dependency source is outside this repository and could not be inspected here.

## How to reproduce
Send a request to the API with:

```http
GET /api/v1/ HTTP/1.1
Host: sso.fantasykenya.com
```

With the previous settings, production generated `ALLOWED_HOSTS` without that hostname and Django raised `DisallowedHost` during `CommonMiddleware.process_request`.

## Blast radius
Requests using `sso.fantasykenya.com` were rejected before any view, authentication flow, or database mutation ran. Requests using the existing `fantasykenya.com` and `www.fantasykenya.com` hosts were unaffected.

## Likely cause commit
Unclear — none of the listed commits touches `sso.fantasykenya.com` or the production host allowlist in a way that explains this hostname; the prior nginx host-rejection changes concern unknown hosts rather than adding this deployment domain.

## Applied fix
- `config/settings/production.py:54` was changed so production always includes `sso.fantasykenya.com` in `ALLOWED_HOSTS`, while preserving the existing environment filtering and `SERVED_DOMAINS` fallback.
- `tests/test_allowed_hosts.py:36-39` added a regression test asserting that the SSO hostname is present in the production allowlist.

Verification should run `pytest tests/test_allowed_hosts.py`, then deploy/reload the API and request the SSO endpoint with `Host: sso.fantasykenya.com`; Django should no longer emit `DisallowedHost`.
