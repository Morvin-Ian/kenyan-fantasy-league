# Google OAuth login leaks JWT access and refresh tokens in the browser URL

## What happened

Every user who signs in with "Continue with Google" gets their freshly minted JWT pair placed **in the URL query string** of the redirect back to the frontend. The frontend parses them out of `window.location` and never scrubs the URL, so valid credentials for the next 1–7 days sit in the address bar, history, sync, Referer headers, and every reverse-proxy/Django access log on disk.

## Root cause

Two ends of the same flow:

1. **Backend builds the success redirect with the tokens embedded.** In `apps/accounts/views.py`, `GoogleAuthCallbackView.get()` generates the JWTs and URL-encodes them into the redirect target:

   ```python
   tokens = UserAuthService.generate_tokens(user)          # :105
   encoded_tokens = urllib.parse.quote(                    # :109-116
       json.dumps({"access": tokens["access"], "refresh": tokens["refresh"]})
   )
   encoded_user = urllib.parse.quote(json.dumps(user_data))  # :117
   success_url = (                                          # :120
       f"{redirect_to}?auth_success=true&auth_message=success"
       f"&tokens={encoded_tokens}&user={encoded_user}"
       f"&is_new_user={is_new}&origin={origin}"
   )
   return redirect(success_url)
   ```

   Both the access token **and the refresh token** ride in `?tokens=...`. The error paths (`views.py:79-80`, `86`, `129-130`, `133-134`) only carry error text, so the leak is specific to successful sign-ins.

2. **Frontend accepts the tokens from the URL.** `client/src/views/Auth/OAuthCallback.vue` (route `/auth/callback`, `client/src/router/index.ts:22-25`) reads `route.query.tokens` / `route.query.user`, `JSON.parse`s them, and stores them:

   ```typescript
   const tokensParam = route.query.tokens as string;             // :47
   const tokens   = JSON.parse(decodeURIComponent(tokensParam)); // :58
   authStore.setToken(tokens.access, tokens.refresh);            // :61  → localStorage
   authStore.setUser(userData);                                  // :62
   ```

   Nothing ever scrubs the URL (`history.replaceState` is not called), so the tokens stay visible in the address bar and in history after sign-in completes.

**Note:** the repo already ships the safe alternative and doesn't use it — `GoogleAuthTokenView.post()` (`views.py:137-189`, route `/api/v1/auth/google/token/`) returns the identical payload (`access`, `refresh`, `user`, `is_new_user`) **in a JSON response body**, proving the redirect-with-tokens design is unnecessary, not load-bearing.

## How to reproduce

1. Configure Google OAuth (`GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`) and run the stack.
2. Sign in via "Continue with Google".
3. Observe the callback hop — the URL contains `?tokens=%7B%22access%22%3A%22eyJ...%22%2C%22refresh%22%3A%22eyJ...%22%7D&user=...` (both JWTs, percent-encoded).
4. Open browser history after landing on Home — the full token URL is saved.
5. Check the API/nginx access log; the full URI including the token query string is logged in plaintext.

## Blast radius

Every Google sign-in, in every environment, leaks both tokens:

- **Access logs** — nginx and Django log the request line including the query string; tokens land on disk in plaintext and are typically shipped to log aggregation/retention systems.
- **Browser history** — persists locally and in synced history (e.g. Chrome sync), outliving the session by months.
- **Referer leakage** — any third-party resource the callback page loads (fonts, analytics, error trackers) receives the full URL in the `Referer` header.
- **Refresh token is the prize** — per `SIMPLE_JWT` in `config/settings/base.py:209-219`, access lifetime is 1 day but refresh lifetime is **7 days** with `ROTATE_REFRESH_TOKENS=True`, so a leaked URL equals account takeover, not a temporary session.
- **Secondary:** `redirect_to` comes from the request (`views.py:22`), is stored unsigned in `state` (`views.py:29-34`), and is echoed verbatim as the token-carrying redirect target (`views.py:60-67`, `120`). If attacker-influenced, the victim's fresh tokens are delivered to the attacker's origin; unsigned `state` also provides no OAuth CSRF protection.

## Likely cause commit

**Pre-existing.** The defect lives in `apps/accounts/views.py` and `client/src/views/Auth/OAuthCallback.vue`, neither of which appears in recent master history (CI workflow, black/flake8/isort formatting, docs commits only). Trigger: any successful Google sign-in.

## Suggested fix

Prefer not putting tokens in the URL at all:

1. **Best:** keep the code exchange server-side but hand tokens to the frontend through a channel that isn't the URL — set the refresh token as an `HttpOnly; Secure; SameSite=Lax` cookie from the callback and return only the short-lived access token in the body, or have the frontend POST the Google `code` to the existing `POST /api/v1/auth/google/token/` and read tokens from the JSON response.
2. **If the redirect flow must stay:** redirect with a short-lived, single-use authorization code and have the frontend exchange it via POST — never the tokens themselves.
3. **Frontend hardening regardless:** on mount, immediately scrub the query string with `history.replaceState({}, "", window.location.pathname)` so tokens leave the address bar and history; move tokens out of XSS-readable `localStorage`; sign/validate `state` with a random nonce and stop echoing request-supplied `redirect_to`.

## Applied fix

Not yet applied — this report documents the failure and the concrete patch. The minimal safe change is #1 (tokens via response body or HttpOnly cookie, never the URL); #3 (URL scrubbing + state hardening) can ship independently as belt-and-braces.
