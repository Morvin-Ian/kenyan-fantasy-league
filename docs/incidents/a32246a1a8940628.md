# apps/accounts/views.py trusts caller-supplied OAuth callback redirect targets

## Verdict
defect — `GoogleAuthInitView` accepted an arbitrary `redirect_to` query parameter and placed it in OAuth state, letting a login flow redirect an authenticated user to an attacker-controlled site.

## What happened
A user could begin Google sign-in through `/api/v1/auth/google/login/?redirect_to=https://attacker.example`. Before this change, `apps/accounts/views.py` embedded that URL in unsigned JSON state and the callback redirected to it after successful authentication, including the one-time authorization code. The reported `tests/test_oauth_callback_client.py` is absent from this checkout; `tests/test_google_oauth_callback.py` is the relevant existing callback regression-test file.

## Root cause
At `apps/accounts/views.py:33-45` before the fix, the initialization view trusted a browser query parameter as a post-login destination:

```python
redirect_to = request.GET.get("redirect_to", settings.FRONTEND_URL)
...
state_data = {
    "redirect_to": f"{redirect_to}/auth/callback",
```

The callback then treated that client-controlled state field as trusted at `apps/accounts/views.py:81-83`. The assumption that a `redirect_to` supplied by the initiating request is a safe frontend origin does not hold; it permits an open redirect at the authentication boundary.

## How to reproduce
1. Start OAuth with `GET /api/v1/auth/google/login/?redirect_to=https://attacker.example`.
2. Complete a valid Google authentication.
3. Before the fix, the callback redirects to `https://attacker.example/auth/callback?auth_success=true&auth_code=...`, exposing the redeemable code to that origin.

## Blast radius
Every Google OAuth login initiation hit this behavior through `GoogleAuthInitView` at `apps/accounts/views.py:32-62`. The code was short-lived and single-use, but an attacker controlling the redirect target could redeem it first through `POST /api/v1/auth/google/token/` (`apps/accounts/views.py:164-184`).

## Applied fix
- `apps/accounts/views.py:1-93` now fixes the callback target to `settings.FRONTEND_URL`, signs the state with Django signing, and rejects a tampered state with a frontend `invalid_state` redirect rather than trusting its contents.
- `tests/test_google_oauth_callback.py:16-27` now asserts that the init view does not read `redirect_to` from the request, state is signed and verified, and invalid state has an explicit failure path.

Verification: run `pytest tests/test_google_oauth_callback.py`.
