# apps/fantasy/views.py passes an unvalidated gameweek query string to an integer lookup

## Verdict
defect — a client-supplied non-numeric `gameweek` reaches the ORM lookup, raises an exception, and is converted into an HTTP 500 rather than a validation response.

## What happened
A signed-in team owner requesting `GET /api/v1/fantasy/players/gameweek-players/?gameweek=invalid` received an Internal Server Error. `FantasyPlayerViewSet.get_gameweek_selection` passed the query-string value directly to `Gameweek.objects.get`, then its broad exception handler returned a 500 response, which Django logged for this endpoint. The supplied server log entry contains only Django’s top-level 500 message; its traceback could not be read because `/root/kenyan-fantasy-league/logs/fantasy_league.log` is outside the accessible workspace.

## Root cause
At `apps/fantasy/views.py:161-176`, the endpoint assumed that a present `gameweek` query parameter was valid for the `Gameweek.number` positive-integer field:

```python
if gameweek_number:
    gameweek = Gameweek.objects.get(number=gameweek_number)
```

`request.query_params.get("gameweek")` returns a string. Values such as `invalid` cannot be coerced for the integer ORM lookup; the resulting exception previously escaped this branch into the broad 500 handler at `apps/fantasy/views.py:235-239`. The assumption that every supplied query value is a valid positive integer does not hold.

## How to reproduce
1. Authenticate as a user with a `FantasyTeam`.
2. Request `GET /api/v1/fantasy/players/gameweek-players/?gameweek=invalid`.
3. Before the fix, the lookup raises and the generic handler returns HTTP 500; after the fix, it returns HTTP 400 with `{"detail": "Gameweek must be a positive integer."}`.

## Blast radius
This affects authenticated users of the `gameweek-players` action whenever they supply a non-numeric `gameweek` value. `apps/fantasy/views.py:334-340` has the same raw `Gameweek.objects.get(number=gameweek_number)` pattern in the `activate-chip` endpoint and remains follow-up work.

## Likely cause commit
Unclear — the supplied commits include a regression-test adjustment (`38ed6c8`) and an earlier incident report (`b6b5b71`), but neither establishes when the unvalidated query-parameter lookup at `apps/fantasy/views.py:161-176` was introduced.

## Applied fix
`apps/fantasy/views.py:161-176` now converts a supplied `gameweek` to an integer and returns HTTP 400 for non-numeric, zero, or negative values before querying `Gameweek`.

`tests/test_fantasy_user_team.py:111-138` now parameterizes `invalid`, `0`, and `-1` requests against the endpoint and asserts the HTTP 400 validation response. Verification is to run this test module and confirm those requests return the asserted response; tests were not executed here because this environment provides no command-execution tool.
