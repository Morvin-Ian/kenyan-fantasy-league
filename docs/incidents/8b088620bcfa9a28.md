# Production nginx waits six hours to load the unknown-host rejection in `docker-compose.prod.yml`

## Verdict
defect — `docker/production/nginx/nginx.conf` correctly rejects unknown hosts, but `docker-compose.prod.yml` left a changed bind-mounted edge configuration inactive for up to six hours.

## What happened
A requester sent `Host: webmail.fantasykenya.com` to a Django-proxied endpoint. Django’s `CommonMiddleware` rejected it because production permits only `fantasykenya.com` and `www.fantasykenya.com`, so the request created an API-side `DisallowedHost` error before any view ran. The production nginx configuration is intended to return `444` before proxying such traffic, but a running nginx worker can continue using its old configuration until its scheduled reload.

## Root cause
`docker-compose.prod.yml:66-67` previously deferred nginx reloads for six hours:

```yaml
# Reload every 6h so renewed certs get picked up without a manual restart.
command: /bin/sh -c 'while :; do sleep 6h & wait $${!}; nginx -s reload; done & nginx -g "daemon off;"'
```

Meanwhile, the bind-mounted production configuration at `docker-compose.prod.yml:54` contains explicit default-server rejection in `docker/production/nginx/nginx.conf:8-24`, and an in-server guard at `:47-51`. The failed assumption is that a configuration committed to the mounted file becomes active promptly; nginx does not reload its configuration automatically when a bind-mounted file changes. Consequently, an old worker configuration could still forward `$host` through the API proxy headers at `docker/production/nginx/nginx.conf:75-89`.

Django’s traceback dependency files are outside this repository and could not be read. The traceback contains no application frame and identifies Django `CommonMiddleware` and `request.get_host()` as the surfacing path.

## How to reproduce
Deploy the pre-change compose configuration, update only the mounted `docker/production/nginx/nginx.conf` to contain the unknown-host `return 444` blocks, and send an HTTPS request to `/api/v1/` within the six-hour reload interval:

```http
Host: webmail.fantasykenya.com
```

The old loaded nginx configuration can proxy the request to Django, which rejects it. After nginx reloads the current configuration, the same request must receive nginx status `444` without reaching the API.

## Blast radius
Any unrecognised hostname sent to `/api/v1` or `/guardian` during the stale-configuration interval could reach Django and generate the same error. Valid hosts retain their existing routes; Django permits `fantasykenya.com` and `www.fantasykenya.com` at `config/settings/production.py:45-54`.

## Likely cause commit
39412aa (`maajun: incident report for Production nginx forwards unrecognised Host headers to Django…`) most plausibly introduced the exposure window: the current nginx rejection was added to the mounted configuration, but the compose reload command at `docker-compose.prod.yml:66-67` retained its six-hour refresh interval.

## Applied fix
- `docker-compose.prod.yml:66-67` now reloads nginx every five minutes rather than every six hours, so changes to the bind-mounted production edge configuration—including the unknown-host `444` rejection in `docker/production/nginx/nginx.conf:8-24`—become active promptly. Certificate renewals remain reloaded automatically.

Verify by deploying the changed compose configuration, waiting no more than five minutes (or reloading nginx immediately), then requesting `/api/v1/` with `Host: webmail.fantasykenya.com`. Nginx should close the request with `444`, and no matching `django.security.DisallowedHost` record should appear in `docker:api`.
