# Django rejects every request to `dev.fantasykenya.com` with `DisallowedHost` because the production `ALLOWED_HOSTS` (env-driven since commit 48ab966) does not list that host

## What happened

A user (or the dev frontend) opened `dev.fantasykenya.com`; nginx forwarded the request to the Django API with the client's `Host` header intact, and Django answered `400 DisallowedHost: Invalid HTTP_HOST header: 'dev.fantasykenya.com'` for every `/api/v1/*` request carrying that host. The error is logged by `docker:api` from `django.middleware.common.CommonMiddleware.process_request` (`django/middleware/common.py:48` → `django/http/request.py:150`), which validates the `Host` header against `ALLOWED_HOSTS` and raises before any view runs.

## Root cause

`config/settings/base.py:58-60`:

```python
ALLOWED_HOSTS = [
    h.strip() for h in re.split(r"[,\s]+", env("ALLOWED_HOSTS", "*")) if h.strip()
]
```

Both settings modules import this unchanged (`config/settings/development.py:1`, `config/settings/production.py:1`), and no repo-tracked file sets `ALLOWED_HOSTS` (only the gitignored `.env`/`.env.prod`, `.gitignore:130-131`, feed it via `env_file` in `docker-compose.yml:14` / `docker-compose.prod.yml:12`). The default `"*"` would accept any host, so the only way `'dev.fantasykenya.com'` can be rejected is that the container's `ALLOWED_HOSTS` environment variable is set to a pinned list that omits the dev host.

The other half of the chain is nginx: `docker/production/nginx/nginx.conf:52` (and `:60`) does `proxy_set_header Host $host;`, so Django sees exactly the hostname the client sent — `dev.fantasykenya.com` — and checks it against the pinned list. The failing assumption, introduced when `ALLOWED_HOSTS` was changed from a hardcoded `["*"]` to an env-pinned list (documented in `docs/incidents/bb1261de30d1dac3.md:20-33`): *the pinned `ALLOWED_HOSTS` value covers every hostname the deployment actually serves.* On this server that assumption does not hold — nginx routes the `dev.` subdomain to the API, but the env list only names the production domains.

## How to reproduce

1. On the server (`/root/kenyan-fantasy-league`), confirm `ALLOWED_HOSTS` in `.env.prod` (or `.env`) is a non-wildcard list that does not include `dev.fantasykenya.com`.
2. `curl -H "Host: dev.fantasykenya.com" http://localhost:80/api/v1/...` (or any request routed to the `api` container with that Host, as nginx does with `proxy_set_header Host $host`).
3. Django logs `DisallowedHost: Invalid HTTP_HOST header: 'dev.fantasykenya.com'` and returns 400.

## Blast radius

Every `/api/v1/*` request that reaches the API with the `dev.fantasykenya.com` Host gets a 400 — the whole dev/staging frontend is down, not one endpoint. Any other hostname the server's nginx routes to `api` but the env list omits fails identically, and the pin applies to both dev and production settings modules (both inherit `base.py`). Secondary: `CSRF_TRUSTED_ORIGINS` (`config/settings/base.py:62-71`) also lacks `https://dev.fantasykenya.com`, so state-changing POSTs from the dev origin would fail CSRF even after this fix.

## Likely cause commit

**`48ab966 Fix DisallowedHost and harden the production deployment`** — its subject names the error, and it is the commit that switched `ALLOWED_HOSTS` from the hardcoded `["*"]` (documented as the pre-change state in `docs/incidents/bb1261de30d1dac3.md:26-30`) to the env-pinned form in `config/settings/base.py:58-60`. The follow-up `38a2ca3` (black/isort) is cosmetic only.

## Suggested fix

This is an environment-variable defect on the server, not a code defect: the repo's default (`"*"`) cannot produce this error, and no repo change can add a value to a gitignored `.env.prod`. On the server, edit `/root/kenyan-fantasy-league/.env.prod` so `ALLOWED_HOSTS` includes every host nginx actually routes to the API, e.g.:

```
ALLOWED_HOSTS=fantasykenya.com www.fantasykenya.com dev.fantasykenya.com
```

then recreate the API container so the env is re-read:

```
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d api
```

Verify with `curl -H "Host: dev.fantasykenya.com" http://localhost/api/v1/...` (expect a real response, not a 400) and check `docker compose logs api` for the DisallowedHost line. Also add `"https://dev.fantasykenya.com"` to `CSRF_TRUSTED_ORIGINS` in `config/settings/base.py:62-71` if the dev frontend performs state-changing requests. I deliberately did **not** hardcode `dev.fantasykenya.com` into `base.py`'s default: the env value overrides the default, so it would not fix the error, and baking a staging hostname into shared settings would defeat the Host-header hardening 48ab966 added. No regression test can be written in this repo for a value that lives only on the server.

## Applied fix

**No repository edit.** The operative cause is the `ALLOWED_HOSTS` value in the server's gitignored `.env.prod` (`.gitignore:130-131`), which is outside this repository; a repo edit would be either ineffective (the env overrides the `"*"` default at `config/settings/base.py:59`) or a security regression. How to verify the change above: run the curl check and confirm `docker:api` stops logging `DisallowedHost` for `dev.fantasykenya.com`; the site's `/api/v1` requests from the dev subdomain then reach Django's views.
