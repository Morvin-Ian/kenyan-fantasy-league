# nginx forwards unknown `Host` headers (e.g. `forum.fantasykenya.com`) to Django, which rejects them with `DisallowedHost`

## What happened

A client — most plausibly an internet scanner or a stale DNS record pointing `forum.fantasykenya.com` at this server — sent an HTTPS request to the API. nginx proxied it to Django **preserving the original `Host` header**, and Django's `ALLOWED_HOSTS` check rejected it, logging an `ERROR` (`django.security.DisallowedHost`) for every such probe. No legitimate user is affected; the site itself has no `forum` subdomain or service.

## Root cause

The failure is the interaction of two halves:

1. **nginx forwards any Host it receives.** `docker/production/nginx/nginx.conf:65-71` proxies `/api/v1` to the API with `proxy_set_header Host $host;` (line 69). Both server blocks declare `server_name fantasykenya.com www.fantasykenya.com;` (lines 24, 40) but neither is `default_server`, so nginx's implicit default-server fallback (the only port-443 block) **accepts a request for any Host** and proxies it to Django with the Host intact. The port-80 block never proxies (it only 301s), so the error necessarily came in over HTTPS.
2. **Django now rejects it.** `config/settings/base.py:58-60` builds `ALLOWED_HOSTS` from the `ALLOWED_HOSTS` env var (defaulting to `"*"` only when unset). The production `.env.prod` pins the real domains, so `forum.fantasykenya.com` fails the check in `django/http/request.py:150` (`raise DisallowedHost(msg)`), surfaced from `django/middleware/common.py:48`.

The assumption that does not hold: *the nginx `server_name` blocks are the only traffic that reaches the API.* In nginx, an unmatched `Host` does **not** get refused — it falls through to the default server, which here still proxies. Before commit `48ab966` restored the env-driven allowlist, `ALLOWED_HOSTS = ["*"]` silently accepted these requests, so the error only became visible (and starts spamming the log) after that hardening.

## How to reproduce

From anywhere with network access to the server:

```
curl -k -H "Host: forum.fantasykenya.com" https://<server-ip>/api/v1/<any-path>
```

nginx matches no `server_name`, the port-443 default server proxies to `api:8000` with `Host: forum.fantasykenya.com`, and Django responds `400` while logging the `DisallowedHost` ERROR shown in the report. (The exact path is not in the log, but only `/api/v1` and `/guardian` are proxied to Django, and the port-80 block never proxies, so it was an HTTPS request to one of those.)

## Blast radius

Every request whose `Host` header is not in the production `ALLOWED_HOSTS` list — `forum.*`, `mail.*`, `admin.*`, IP-address hosts, any subdomain probe — hits the same rejection and writes the same ERROR block. Each one also consumes a Django request/response cycle and a log line; under scanner volume this is log spam plus wasted backend work. Legitimate traffic (`fantasykenya.com`, `www.fantasykenya.com`) is unaffected.

## Likely cause commit

**`48ab966` "Fix DisallowedHost and harden the production deployment"** — it restored env-driven `ALLOWED_HOSTS` at `config/settings/base.py:58-60` (previously the wildcard `["*"]`, per `docs/incidents/bb1261de30d1dac3.md:20-33`), which is what turned previously-silent unknown-Host requests into logged `DisallowedHost` errors. The nginx default-server fallback that lets those requests reach Django predates it.

## Suggested fix

Reject unmatched Host headers at nginx **before** they reach Django, keeping `ALLOWED_HOSTS` as a second line of defence. Added to `docker/production/nginx/nginx.conf` (before the port-80 redirect block):

```nginx
# Reject requests whose Host header is not one of the site's domains. Without
# this block, nginx's implicit default-server fallback forwards arbitrary Host
# headers (e.g. forum.fantasykenya.com from scanners or stale DNS records) to
# the API with the Host preserved, and Django logs DisallowedHost for every
# probe. Closing the connection here keeps Django's ALLOWED_HOSTS check as a
# second line of defence rather than the first. Requests for
# fantasykenya.com/www.fantasykenya.com still match the named server blocks
# below (an explicit server_name match wins over default_server).
server {
    listen 80 default_server;
    listen 443 ssl default_server;
    server_name _;
    ssl_certificate /etc/letsencrypt/live/fantasykenya.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/fantasykenya.com/privkey.pem;
    return 444;
}
```

An explicit `server_name` match wins over `default_server`, so `fantasykenya.com`/`www.fantasykenya.com` (including the HTTP ACME challenge at `/.well-known/acme-challenge/`) are untouched; only unmatched hosts get `444` (connection closed). The cert paths are the same ones the existing port-443 block already requires, so no new boot dependency.

**Regression test** (new `tests/test_nginx_conf.py`, matching the project's existing static-content test style in `tests/test_entrypoint.py`):

```python
def test_nginx_rejects_unmatched_hosts_before_django():
    body = NGINX_CONF.read_text()

    # A catch-all default server must exist for both ports the proxy listens on.
    assert "listen 80 default_server" in body
    assert "listen 443 ssl default_server" in body
    assert "server_name _;" in body

    # It must drop the connection instead of proxying to Django.
    assert "return 444;" in body
```

This fails before the change (no `default_server`, no `return 444` in the file) and passes after.

## Applied fix

- **`docker/production/nginx/nginx.conf`** — added the catch-all `default_server` block (lines 5–20) on ports 80 and 443 returning `444` for any Host that does not match the named `server_name` blocks, so unknown-host requests are dropped at the proxy and never reach Django.
- **`tests/test_nginx_conf.py`** (new) — regression test asserting the `default_server`/`return 444` catch-all exists for both ports.

**Verify:**
1. `pytest tests/test_nginx_conf.py` passes.
2. On the server: `docker compose -f docker-compose.prod.yml --env-file .env.prod exec nginx nginx -t` (config is valid), then redeploy via the CI workflow (`git pull --ff-only origin master` + `compose up --build -d`).
3. `curl -k -H "Host: forum.fantasykenya.com" https://127.0.0.1/api/v1/` → empty reply (connection closed), and no new `DisallowedHost` entries in `logs/fantasy_league.log`; `curl -k -H "Host: fantasykenya.com" https://127.0.0.1/api/v1/` still behaves as before.

**Not changed / could not determine:** the exact value of `ALLOWED_HOSTS` in the gitignored server-side `.env.prod` (not in the repo; `.env.example` is credential-protected). The error itself proves it is set to a list that excludes `forum.fantasykenya.com` — which is correct, since no forum app, DNS record, or nginx `server_name` for that host exists anywhere in this repository (`grep forum` across the repo: no matches). If the owners ever intend to serve a real forum on that subdomain, that is infrastructure outside this repo (DNS + a service + adding the host to `ALLOWED_HOSTS` and nginx `server_name`), and the new catch-all would correctly keep blocking it until then.
