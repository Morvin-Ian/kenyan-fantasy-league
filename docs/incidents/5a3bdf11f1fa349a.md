# Site-wide improvement review: DEBUG stays on in production, `ALLOWED_HOSTS` wildcard, and a duplicated standings request

## What happened

A review of the KPL Fantasy League codebase for improvement opportunities found three concrete, verifiable issues — one critical Django misconfiguration, one security hardening gap, and one duplicated network request. All three have been fixed. Two of the fixes were verified against the code as it stands in this repository; one (the `ALLOWED_HOSTS` change) landed in a slightly more robust form than originally drafted.

### 1. Critical — `DEBUG` is parsed as a string, so it stays ON in production

**File:** `config/settings/base.py:47`

```python
DEBUG = env("DEBUG", "false").lower() == "true"   # after
```

**Root cause:** `DEBUG` was previously read with a bare `os.getenv("DEBUG")`. When the env file sets `DEBUG=False`, `os.getenv` returns the string `"False"`, and every non-empty string is truthy in Python — so `DEBUG` was effectively `True` in production. Django then serves its verbose error pages (stack traces, settings, environment) to anyone who triggers a 500. The fix coerces the value to a real boolean via `.lower() == "true"`, and reuses the existing `env()` helper (base.py:32-40), which also strips stray whitespace. It matches the pattern already used for `LINEUPS_SCRAPING_ENABLED` in the same file.

### 2. High — `ALLOWED_HOSTS = ["*"]` in all environments

**File:** `config/settings/base.py:58-60`

```python
ALLOWED_HOSTS = [
    h.strip() for h in re.split(r"[,\s]+", env("ALLOWED_HOSTS", "*")) if h.strip()
]
```

**Root cause:** the env-driven configuration had been replaced with a hardcoded `["*"]`, which permits Host-header attacks and defeats Django's `ALLOWED_HOSTS` protection in production. The fix restores env-driven configuration — accepting a comma- or space-separated list, stripping each entry and dropping empties — while defaulting to `"*"`, so dev/CI setups that don't set the variable behave exactly as before. Production can now pin its real domains (e.g. `ALLOWED_HOSTS=fantasykenya.com www.fantasykenya.com`) via `.env.prod`.

### 3. Medium — Standings page fired the standings request twice on load

**File:** `client/src/views/StandingsView.vue`

**Root cause:** the component previously had two independent triggers for the same fetch — a `watch(..., { immediate: true })` that calls `fetchStandings()` when the store is empty, and an `onMounted` block that also called it. Because the first call is async and hadn't completed by mount time, both fired, doubling the request against the API (and hammering the 24-hour cached `/kpl/standings/` endpoint). The duplicate `onMounted` fetch was removed. As it stands now, `onMounted` (lines 317-328) handles only auth initialization, the sign-in redirect, and the responsive items-per-page / resize listener; the single `watch` with `{ immediate: true }` (lines 211-215) is the only fetch trigger and also covers the case where standings are later cleared.

## Related fixes already in place (verified)

The same review pass confirmed that the following previously-reported fixes are present in the code:

- **Entrypoint credential handling** — `docker/production/django/entrypoint` (and its local twin, enforced by `tests/test_entrypoint.py`) passes `POSTGRES_DB`/`PG_USER`/`PG_PASSWORD`/`PG_HOST`/`PG_PORT` through the environment to a quoted heredoc (`<<'END'`), reads them via `os.environ[...]`, and bounds each attempt with `connect_timeout=5`.
- **Production API runs gunicorn, not `runserver`** — `docker/production/django/start` ends with `exec gunicorn config.wsgi:application --bind 0.0.0.0:8000 --workers "${GUNICORN_WORKERS:-3}"`.
- **Production Celery no longer runs under `watchmedo`** — `docker/production/django/celery/worker/start` is `exec celery -A config worker --loglevel=info`; `beat/start` is `exec celery -A config.celery beat ...`; only the unused-in-prod `flower/start` still uses `watchmedo`.
- **Profile update resolves via the authenticated user** — `apps/profiles/views.py:35-41`, `UpdateProfileAPIView.patch` uses `Profile.objects.get(user=self.request.user)` instead of trusting the URL UUID, fixing the Google-OAuth "Profile not found." flow and closing the IDOR.
- **Transient errors no longer log users out** — `client/src/stores/auth.ts:210-211`, `refreshUserProfile()` re-throws without calling `logout()`, leaving token destruction to the axios 401/refresh interceptor.

## Remaining observations (not changed)

- `config/celery.py:11` still calls `app.config_from_object("config.settings.development", namespace="CELERY")` unconditionally, so the Celery app reads `CELERY_*` from the development module even though `docker-compose.prod.yml` sets `DJANGO_SETTINGS_MODULE=config.settings.production` for api/worker/beat. Currently masked because the two settings modules are identical; it will bite the moment they diverge.
- Leftover debug logging in production paths: `console.log("Ok")` at `client/src/stores/auth.ts:148`, `console.log(response)` at `auth.ts:173`, and `console.log('Lineup uploaded successfully')` at `client/src/views/FixturesView.vue:221`.
- `authStore.updateProfile` reads `error.response.data.detail` without a guard (`auth.ts:228`) — a missing response body would throw instead of showing a clean error.
- `SIMPLE_JWT.ACCESS_TOKEN_LIFETIME` is 1 day (`config/settings/base.py:211`); consider shortening (e.g. 30–60 min) since the refresh-token flow in `axios-interceptor.ts` already handles rotation.

## Verification

I cannot run the app or tests in this environment, so changes were validated by re-reading the edited files (`config/settings/base.py`, `client/src/views/StandingsView.vue`, `apps/profiles/views.py`, `client/src/stores/auth.ts`, both entrypoints, the production start scripts, `config/celery.py`, and `docker-compose.prod.yml`). The `DEBUG` fix is the highest-value change — it's a classic Django pitfall that silently disables production safety.
