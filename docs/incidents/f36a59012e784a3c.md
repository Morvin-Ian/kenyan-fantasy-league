# Production deploy leaves nginx’s Host-rejection configuration stale in `.github/workflows/ci.yml`

## Verdict
defect — `docker/production/nginx/nginx.conf:8-24` and `:47-51` correctly reject unknown hosts, but the deployment workflow did not reload nginx after replacing the bind-mounted configuration, allowing the running edge to continue forwarding invalid hosts to Django.

## What happened
A requester sent `Host: 169.58.218.237` to the production deployment. Django received that unrecognised value and correctly rejected it in `CommonMiddleware` before an application endpoint ran, producing the logged `DisallowedHost` error. The checked-in nginx configuration should have closed this request with status `444` before proxying, so the live error indicates nginx was still using an earlier configuration.

## Root cause
`.github/workflows/ci.yml:119-120` rebuilt and started the compose services:

```sh
compose="docker compose -f docker-compose.prod.yml --env-file .env.prod"
$compose up --build -d --remove-orphans
```

The nginx configuration is bind-mounted by `docker-compose.prod.yml:54`:

```yaml
- ./docker/production/nginx/nginx.conf:/etc/nginx/conf.d/default.conf
```

A bind mount updates the file visible in the container, but nginx continues using its already-loaded configuration until it reloads. The workflow assumed `up --build -d` would apply the changed nginx configuration; that assumption does not hold when the nginx container remains running. The stale configuration could therefore continue proxying `$host` through `docker/production/nginx/nginx.conf:75-80`, allowing Django’s intended `ALLOWED_HOSTS` guard in `config/settings/production.py:45-54` to log the rejection.

The trace names Django dependency files outside this repository; they could not be read here. The supplied traceback identifies Django `CommonMiddleware` calling `request.get_host()` as the surfacing path.

## How to reproduce
1. Deploy an nginx container using a configuration that proxies `/api/v1` and preserves `Host`.
2. Replace its bind-mounted `docker/production/nginx/nginx.conf` with the current configuration containing the default servers and `$host` rejection guard, without reloading or recreating nginx.
3. Request `/api/v1` through the public edge with:

```http
Host: 169.58.218.237
```

The stale nginx process can forward the host to Django, which rejects it with `DisallowedHost`. After nginx reloads the current configuration, its default HTTP/TLS server blocks at `docker/production/nginx/nginx.conf:8-24` return `444` before Django is reached.

## Blast radius
Every deployment that changes the bind-mounted nginx configuration but retains the existing nginx process can leave routing and Host-header policy stale until nginx’s six-hour in-container reload loop runs (`docker-compose.prod.yml:66-67`). All unknown-host probes during that window can reach Django-proxied `/api/v1` or `/guardian` routes and generate the same error.

## Likely cause commit
39412aa (`maajun: incident report for Production nginx forwards unrecognised Host headers to Djang…`) most plausibly introduced the gap: it added the nginx unknown-host rejection configuration, but the deployment workflow at `.github/workflows/ci.yml:115-138` did not reload the long-running bind-mounted nginx process to activate it.

## Applied fix
- `.github/workflows/ci.yml:120-123` now runs `$compose exec -T nginx nginx -s reload` immediately after `up --build -d --remove-orphans`, applying the bind-mounted nginx configuration on every production deployment instead of waiting for the six-hour periodic reload.
- `tests/test_allowed_hosts.py:119-129` now asserts that the production deployment workflow explicitly reloads nginx, preventing removal of the activation step while the nginx Host-rejection regression tests remain present.

Verify by deploying through the GitHub Actions workflow, then requesting `/api/v1` with `Host: 169.58.218.237`: nginx should close the request with `444`, and no corresponding `django.security.DisallowedHost` entry should appear. Requests using `fantasykenya.com` and `www.fantasykenya.com` should continue through their existing routes.
