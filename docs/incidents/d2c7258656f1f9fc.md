# `docker-compose.prod.yml` delays deployment of nginx Host-header rejection for up to six hours

## Verdict
defect — nginx already rejects unknown hosts in configuration, but the production reload loop leaves that mounted protection inactive for up to six hours after it changes.

## What happened
A requester sent `Host: vmi3526112.contaboserver.net` to the deployment and reached Django, which rejected it during `CommonMiddleware` host validation. The production edge configuration contains default virtual hosts and an HTTPS host guard intended to return nginx status `444` before proxying such traffic, but `docker-compose.prod.yml` reloads nginx only every six hours. Thus a running container with the preceding configuration can keep forwarding unknown hosts to Django long after the edge fix is deployed.

## Root cause
`docker-compose.prod.yml:66-67` mounted the nginx configuration but only reloaded it after a six-hour sleep:

```yaml
# Reload every 6h so renewed certs get picked up without a manual restart.
command: /bin/sh -c 'while :; do sleep 6h & wait $${!}; nginx -s reload; done & nginx -g "daemon off;"'
```

This assumes a bind-mounted nginx configuration is applied promptly. It is not: nginx must be reloaded, so the preceding process configuration remains active until that timer expires. That stale configuration can preserve the earlier routing path identified by `docker/production/nginx/nginx.conf:74-88`, which forwards `$host` to Django:

```nginx
proxy_set_header Host $host;
```

Django correctly refuses this unrecognised value because `config/settings/production.py:45-54` limits `ALLOWED_HOSTS` to the served domains. The Django source files named in the traceback are installed dependencies outside this repository and could not be read; the traceback itself establishes that `CommonMiddleware` surfaced the validated-host rejection.

## How to reproduce
Deploy or modify the bind-mounted `docker/production/nginx/nginx.conf` while nginx is already running, then within six hours request a Django-proxied path such as `/api/v1/` with:

```http
Host: vmi3526112.contaboserver.net
```

Before the next scheduled nginx reload, the pre-change configuration can continue to forward the host to Django, producing `DisallowedHost`.

## Blast radius
Any unknown-host request reaching `/api/v1` or `/guardian` while nginx runs a stale configuration can generate the same Django error; `docker/production/nginx/nginx.conf:74-88` forwards the received `$host` on both routes. Intended `fantasykenya.com` and `www.fantasykenya.com` requests retain their current behavior.

## Likely cause commit
39412aa (`maajun: incident report for Production nginx forwards unrecognised Host headers to Django…`) most plausibly introduced the six-hour deployment gap: it added the current nginx host-rejection configuration while leaving `docker-compose.prod.yml:66-67` configured to reload only every six hours.

## Applied fix
- `docker-compose.prod.yml:66-67` now reloads nginx every five minutes rather than every six hours, so changes to the bind-mounted edge configuration—including unknown-host rejection—become active promptly while still refreshing renewed certificates.
- `tests/test_allowed_hosts.py:119-125` now asserts that the production compose configuration uses the five-minute reload interval, preventing the host-rejection configuration from again being delayed for hours.
