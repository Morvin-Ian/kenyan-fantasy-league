# `CustomUserManager.create_user` applied `is_staff=False`/`is_superuser=False` defaults *after* `self.model(**extra_fields)` had consumed the dict — the guard was a no-op (`apps/accounts/managers.py`)

## What happened

A code review of `apps/accounts/managers.py` found that the two lines intended to guarantee ordinary users are created non-privileged did nothing:

```python
user = self.model(
    username=username,
    first_name=first_name,
    last_name=last_name,
    email=email,
    **extra_fields,
)                                        # extra_fields consumed here (old lines 33-39)

user.set_password(password)
extra_fields.setdefault("is_staff", False)      # old line 42 — no effect
extra_fields.setdefault("is_superuser", False)  # old line 43 — no effect
user.save(using=self._db)
```

`extra_fields` was unpacked into the `self.model(...)` constructor *before* the `setdefault` calls, so mutating the dict afterward could not reach the instance. Any `is_staff`/`is_superuser` value present in `extra_fields` was already baked into the `user` object; any value absent kept the model field default (`is_staff` defaults to `False` on `apps/accounts/models.py:22`, `is_superuser` via `PermissionsMixin`). The lines were dead code that *appeared* to be a privilege guard but enforced nothing.

## Root cause

In `apps/accounts/managers.py`, `create_user` (lines 18–53 after fix) constructed the model instance with `**extra_fields`, then ran `extra_fields.setdefault("is_staff", False)` and `extra_fields.setdefault("is_superuser", False)`, and only then saved. Because `setdefault` neither overrides an existing key nor retroactively mutates an already-constructed instance, the guard had zero effect:

- If a caller passed `is_staff=True` / `is_superuser=True` in `**extra_fields`, the account was minted with those privileges **unchecked** — `create_user` contained no validation like `create_superuser` does (lines 62–66), and the no-op `setdefault`s could not reject or override them.
- If a caller passed nothing, the flags fell through to the model's `BooleanField(default=False)` defaults, so behavior was *coincidentally* safe — which is exactly why the bug was silent.

The `create_superuser` path was unaffected: it `setdefault`s `is_staff`/`is_superuser`/`is_active` *before* delegating to `create_user`, so those values flow through `**extra_fields` into the constructor correctly. Its trailing duplicate `user.save(using=self._db)` after the delegate call was redundant but harmless.

## How to reproduce

Before the fix:

```python
from django.contrib.auth import get_user_model

User = get_user_model()
u = User.objects.create_user("hacker", "h@example.com", "pw", is_staff=True, is_superuser=True)
print(u.is_staff, u.is_superuser)  # -> True True, with no error
```

No exception was raised and no log was emitted. Contrast with `create_superuser`, which refuses `is_staff`/`is_superuser` that are not `True`. After the fix this raises `ValueError`.

## Blast radius

Every user created through `CustomUserManager.create_user` was affected by the missing guard. The manager is the single `objects` manager for `apps.accounts.User` (`apps/accounts/models.py:29`) and backs:

- djoser registration (`/api/v1/auth/users/`) and activation flows,
- social-auth (Google OAuth) account creation via `apps/accounts/services.py`,

so the default `False` field values were the only thing keeping those flows non-privileged. Immediate impact was limited (dead code + false assurance), but any future refactor relaxing the model defaults — or any caller forwarding `is_staff`/`is_superuser` from request data — silently became a privilege-escalation vector with no validation layer to catch it.

## Likely cause commit

**Pre-existing design defect.** The bug was in the original manager implementation, not introduced by a recent change; the recent history (PRs #78, #72, #62, and the `ALLOWED_HOSTS` pinning) does not touch `apps/accounts/managers.py`.

## Suggested fix

1. Move the `setdefault` calls **before** the `self.model(...)` construction so they act on the dict that is actually unpacked.
2. Add an explicit guard in `create_user` mirroring `create_superuser`, so `create_user` can never mint a privileged account even if a caller forces the flags.
3. Remove the redundant `user.save(using=self._db)` in `create_superuser` — `create_user` already persists the instance.

## Applied fix

Two files changed:

- **`apps/accounts/managers.py`** — the core fix:
  - `extra_fields.setdefault("is_staff", False)` and `extra_fields.setdefault("is_superuser", False)` now run **before** `self.model(**extra_fields)` (lines 35–36), with a comment explaining why ordering matters.
  - Added an explicit guard (lines 38–41): `create_user` raises `ValueError` if `is_staff is True` or `is_superuser is True`, forcing privileged accounts through `create_superuser`.
  - Removed the redundant trailing `user.save(using=self._db)` in `create_superuser` (now returns `self.create_user(...)` directly, lines 77–79).

- **`tests/test_custom_user_manager.py`** (new) — the regression test that would have caught this:
  - `test_create_user_defaults_to_non_privileged` — ordinary creation yields `is_staff is False`, `is_superuser is False`, `is_active is True`.
  - `test_create_user_rejects_staff_flag` — passing `is_staff=True` raises `ValueError`.
  - `test_create_user_rejects_superuser_flag` — passing `is_superuser=True` raises `ValueError`.
  - `test_create_superuser_still_works` — `create_superuser` still mints a fully privileged account.

Verified against the on-disk file after editing: `apps/accounts/managers.py` (79 lines) has the `setdefault`s at lines 35–36, the guard at 38–41, construction at 43–49, and the simplified `create_superuser` tail at 77–79. No file outside the repository needs to change.
