# Production nginx forwards unrecognised Host headers to Django in `docker/production/nginx/nginx.conf`

## Verdict
defect — unknown public Host headers are expected internet traffic, but nginx forwarded them to Django despite being the default TLS server, producing avoidable application-level `DisallowedHost` errors.

## What happened
A requester addressed the deployment using `ed.da.3aa9.ip4.static.sl-reverse.com`. Nginx forwarded that hostname unchanged to Django’s `/api/v1` or `/guardian` upstream, and Django rejected it in `CommonMiddleware` before any application endpoint ran. The requester received the rejected-host response and the expected edge probe was recorded as an API error.

## Root cause
`docker/production/nginx/nginx.conf:54-59` and `:62-67` preserve and proxy every matched server’s incoming hostname:

```nginx
location /api/v1 {
    proxy_pass http://api;
    proxy_set_header Host $host;
```

The HTTPS virtual host at `docker/production/nginx/nginx.conf:21-24` is the default server for unmatched TLS hostnames because it is the first `listen 443` server. It had no host rejection before proxying, so it assumed every request reaching its API locations carried one of its `server_name` values. That assumption does not hold for reverse-DNS and Host-header probe traffic. Django then correctly rejects the value because `config/settings/production.py:45-54` allows only `fantasykenya.com` and `www.fantasykenya.com`.

The dependency files named by the traceback are outside the repository and could not be read here; the traceback identifies Django’s `CommonMiddleware` calling `request.get_host()` as the surfacing path.

## How to reproduce
Send an HTTPS request to this nginx instance’s `/api/v1` or `/guardian` path with:

```http
Host: ed.da.3aa9.ip4.static.sl-reverse.com
```

Before this change, nginx selected the default HTTPS server and passed `$host` to Django. Django’s `ALLOWED_HOSTS` validation then raised `DisallowedHost`.

## Blast radius
All unmatched Host-header requests that target the default HTTPS server and a Django-proxied route previously generated API-side `DisallowedHost` errors. Requests for the configured KFL hosts continue through the existing `/api/v1` and `/guardian` proxy paths; `mogul.manager` has a separate server block in `docker/production/nginx/mogul.conf:41-90`.

## Likely cause commit
27cbf1f (`feat: serve mogul.manager from the shared nginx edge`) most plausibly exposed the gap: it added a second edge virtual host while documenting that the KFL HTTPS server remains the default for unmatched hostnames; no default-host rejection existed in `docker/production/nginx/nginx.conf`.

## Applied fix
- `docker/production/nginx/nginx.conf:26-30` now rejects any default-server request whose `$host` is not `fantasykenya.com` or `www.fantasykenya.com` with nginx status `444`, before it can enter a proxy location or reach Django.
- `tests/test_allowed_hosts.py:86-97` now asserts that the production nginx configuration contains the explicit unknown-host guard and `return 444`, preventing a future configuration edit from restoring the API log path.

Verify by reloading the production nginx configuration and requesting `/api/v1` with `Host: ed.da.3aa9.ip4.static.sl-reverse.com`: nginx should close the connection with `444`, and no corresponding `django.security.DisallowedHost` entry should appear in the API logs. Requests with `Host: fantasykenya.com` and `Host: www.fantasykenya.com` should retain their existing behavior. I could not execute the test suite or reload nginx because this environment provides no command-execution access.
