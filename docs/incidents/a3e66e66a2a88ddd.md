# `User.get_fullname` in `apps/accounts/models.py:38-40` calls `.title()` on nullable name fields, so every email/password signup — which the frontend submits with `first_name: null` — 500s during response serialization and the account can never log in

## Summary

`apps/accounts/models.py:38-40` defines `get_fullname` as a `@property` that does `self.first_name.title()` and `self.last_name.title()` with **no null guard**, even though both fields are declared `null=True` (`models.py:15-20`). `UserSerializer.get_full_name` (`apps/accounts/serializers.py:42-43`) returns `obj.get_fullname`, and `UserSerializer` is wired as djoser's `user`/`current_user` serializer (`config/settings/base.py:250-251`) — so the instant a user row has a `NULL` name, every auth endpoint that serializes the user raises `AttributeError: 'NoneType' object has no attribute 'title'`. The frontend signup (`client/src/views/Auth/SignUp.vue:260-267`) sends `first_name: null, last_name: null` on **every** registration, so this is not an edge case: it is the normal signup path.

## What happened

A user registers through the email/password form. The request succeeds server-side (the row is created with `NULL` names), but the response serialization crashes:

1. `SignUp.vue:260-267` posts `{ first_name: null, last_name: null, username, email, password, re_password }`.
2. `UserCreateSerializer` (`apps/accounts/serializers.py:46-55`) lists `first_name`/`last_name` in `fields` but does not make them required; djoser's `create` persists them as stored — `NULL` (the model allows it: `models.py:15-20`).
3. djoser's `UserViewSet.create` responds with `DJOSER["SERIALIZERS"]["user"]` = `UserSerializer` (`base.py:250`) → `get_full_name` → `obj.get_fullname` → `self.first_name.title()` where `first_name is None` → **500**.
4. The user *was* created (the view is not atomic), so the client shows a generic registration error and a retry fails with "user with this email already exists".
5. If the user is created out-of-band, `POST /api/v1/auth/jwt/create/` (login) and `GET /api/v1/auth/users/me/` crash identically, because djoser's token and current-user serializers also use `UserSerializer`.

## Root cause

The same "full name" concept is implemented in three places with **inconsistent null handling**, and the two used by the auth flow are the unguarded ones:

| Location | Behaviour |
|---|---|
| `apps/accounts/models.py:38-40` — `@property get_fullname` | `f"{self.first_name.title()} {self.last_name.title()}"` — crashes on `None` |
| `apps/accounts/serializers.py:36-43` — `get_first_name`/`get_last_name`/`get_full_name` | each calls `.title()` unguarded — crashes on `None` |
| `apps/profiles/serializers.py:38-45` — `get_full_name` | `if not first_name or not last_name: return None` — **guarded** |

The profile serializer proves the codebase already knows names can be `NULL`; the auth path simply forgot the same guard. Google OAuth users escape the crash only by accident — `services.py:93-94` defaults missing names to `""` instead of `None` — which is also why manual QA with "Continue with Google" never sees it and the email/password path stays broken in production.

A secondary, latent trap in the same property: it is a `@property` named with the `get_` prefix that Django convention reserves for *methods* (`AbstractUser.get_full_name()`). Any caller writing `user.get_fullname()` gets `TypeError: 'str' object is not callable`. Grep shows the only current consumer (`serializers.py:43`) correctly omits the parens, so this is latent — but the name invites the bug.

A third, display-level issue: `.title()` is applied to names both in the property and again in the serializer's `get_first_name`/`get_last_name`, mangling legitimate casing (`"McDonald".title() → "Mcdonald"`, `"o'brien".title() → "O'Brian"`), while `ProfileView.vue:36` displays the raw DB values — the same user's name renders differently depending on endpoint. Django's own `AbstractUser.get_full_name()` returns names as stored, without transformation.

## How to reproduce

1. `POST /api/v1/auth/users/` with exactly what the shipped frontend sends (`SignUp.vue:260-267`):
   ```json
   {"username":"testuser","email":"test@example.com","password":"Str0ngPass!","re_password":"Str0ngPass!","first_name":null,"last_name":null}
   ```
2. Response: **500** with `AttributeError: 'NoneType' object has no attribute 'title'` raised at `apps/accounts/models.py:40` (via `apps/accounts/serializers.py:43`).
3. The `testuser` row now exists with `first_name = NULL, last_name = NULL`.
4. `POST /api/v1/auth/jwt/create/` with `test@example.com` / the password → **500** with the same traceback (djoser token serializer includes `UserSerializer`).
5. `GET /api/v1/auth/users/me/` with a valid token for that user → **500**.

Omitting `first_name`/`last_name` from the body produces the same result (the keys never reach `validated_data`, so the model default `NULL` stands).

## Blast radius

- **Every email/password registration through the shipped UI 500s**, and the account it creates can never log in — the primary signup path of the site is effectively dead.
- Affected endpoints (all serialize through `UserSerializer` per `DJOSER["SERIALIZERS"]`, `base.py:250-251`): `POST /auth/users/`, `POST /auth/jwt/create/`, `POST /auth/jwt/refresh/`, `GET /auth/users/me/`, plus `GoogleAuthResponseSerializer.user` (`serializers.py:76`).
- **Masked in QA**: the Google flow writes `""` names (no crash), and the profile page uses the *guarded* `ProfileSerializer` — so logged-in flows look fine until a null-named user is serialized by an auth endpoint.
- Non-atomic create means a 500 response does **not** mean the user wasn't created — support gets confusing "can't register, email already exists" reports.

## Likely cause commit

**Pre-existing.** `get_fullname` predates the recent master history (CI workflow, black/flake8/isort formatting, and docs commits only). It became *reachable as a crash* when the frontend began submitting `first_name: null`/`last_name: null` in the signup payload — the serializer wiring (`base.py:250-251`) and the property itself are old.

## Suggested fix

Make the model the single, null-safe source of truth and make the serializers delegate to it:

@property
def full_name(self) -> str:
    """Full name, tolerant of NULL/blank first/last names."""
    return f"{self.first_name or ''} {self.last_name or ''}".strip()
