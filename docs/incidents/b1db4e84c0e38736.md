# Production nginx forwards client-supplied `X-Forwarded-Host` to Django in `docker/production/nginx/nginx.conf`

## Verdict
defect — nginx validates `$host` but leaves an inbound `X-Forwarded-Host` unchanged; Django is configured to prefer that header and rejects `cp.fantasykenya.com`.

## What happened
A request reached the production API with an effective host of `cp.fantasykenya.com`, and Django rejected it before an application view ran. The requester received Django’s invalid-host response and the API logged a `DisallowedHost` error. This can occur even when nginx’s public `Host` header is a configured KFL domain, because Django prefers `X-Forwarded-Host`.

## Root cause
`docker/production/nginx/nginx.conf:75-80` and `:84-89` set the proxied `Host` but did not clear a client- or upstream-proxy-supplied `X-Forwarded-Host`:

```nginx
proxy_set_header Host $host;
```

`config/settings/production.py:45` permits only `fantasykenya.com` and `www.fantasykenya.com`, while `config/settings/production.py:61` enables:

```python
USE_X_FORWARDED_HOST = True
```

Django therefore validates `X-Forwarded-Host` when it exists. The failed assumption was that setting `proxy_set_header Host $host` also prevents other inbound forwarded-host headers from reaching Django; nginx passes headers not explicitly overridden, so `X-Forwarded-Host: cp.fantasykenya.com` survives and is rejected.

The logged server file and installed Django dependency files named in the traceback were unavailable from this checkout; the supplied traceback establishes that Django’s `CommonMiddleware` surfaced the rejection through `request.get_host()`.

## How to reproduce
Send a request to either production proxy route with a valid public host and a conflicting forwarded host:

```http
GET /api/v1/ HTTP/1.1
Host: fantasykenya.com
X-Forwarded-Host: cp.fantasykenya.com
```

Before this change, nginx proxied the forwarded-host header unchanged. With `USE_X_FORWARDED_HOST = True`, Django selected `cp.fantasykenya.com` and raised `DisallowedHost`.

## Blast radius
Both Django proxy routes, `/api/v1` and `/guardian`, accepted an inbound `X-Forwarded-Host`; any client or upstream proxy providing an unlisted value could generate the same API error. Static and Vue routes do not reach Django through these proxy locations.

## Likely cause commit
Unclear — the supplied recent commit list includes earlier fixes for unknown `Host` headers, but the readable configuration does not identify which listed commit introduced `USE_X_FORWARDED_HOST` or the un-cleared forwarded header.

## Applied fix
- `docker/production/nginx/nginx.conf:75-81` now clears `X-Forwarded-Host` in the `/api/v1` proxy location, so Django validates nginx’s already-checked `$host`.
- `docker/production/nginx/nginx.conf:84-90` now clears the same header for `/guardian`.
- `tests/test_allowed_hosts.py:119-134` now asserts that each Django proxy location explicitly clears `X-Forwarded-Host`.

Verify by reloading the production nginx configuration and requesting `/api/v1/` and `/guardian` with `Host: fantasykenya.com` plus `X-Forwarded-Host: cp.fantasykenya.com`: Django should no longer log `DisallowedHost` for that forwarded header. I could not execute tests or reload nginx because this environment has no command-execution access.
