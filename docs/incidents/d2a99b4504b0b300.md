# Production nginx trusts client-supplied X-Forwarded-Host in `docker/production/nginx/nginx.conf`

## Verdict
defect — production enables Django’s `USE_X_FORWARDED_HOST`, but its API proxies did not replace an inbound `X-Forwarded-Host` header with the hostname nginx had validated.

## What happened
A request reached the API with an effective host of `logon.fantasykenya.com`, which is not in Django’s production `ALLOWED_HOSTS`. Django’s `CommonMiddleware` called `request.get_host()` and rejected the request before any application view ran, producing the logged `DisallowedHost` error. The request could have used a valid outer `Host` header while carrying the untrusted forwarded-host value.

## Root cause
`config/settings/production.py:57-61` explicitly trusts `X-Forwarded-Host`:

```python
SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")
USE_X_FORWARDED_HOST = True
```

However, `docker/production/nginx/nginx.conf:75-90` previously set `Host $host` for `/api/v1` and `/guardian` but did not set `X-Forwarded-Host`. The proxy therefore assumed an inbound `X-Forwarded-Host` was already trustworthy. That assumption does not hold: the client-provided value `logon.fantasykenya.com` reached Django, which correctly compared it against the pinned hosts at `config/settings/production.py:45-54` and rejected it.

The Django dependency files named in the traceback are outside this checkout, so their exact Django 4.2 source could not be read here. The trace and `USE_X_FORWARDED_HOST` setting identify the effective-host path.

## How to reproduce
Send a request through the production nginx API proxy with a valid served host and a conflicting forwarded host:

```http
GET /api/v1/ HTTP/1.1
Host: fantasykenya.com
X-Forwarded-Host: logon.fantasykenya.com
```

Before this change, nginx forwarded the supplied `X-Forwarded-Host` to Django; with `USE_X_FORWARDED_HOST=True`, Django rejected `logon.fantasykenya.com`.

## Blast radius
Every `/api/v1` and `/guardian` request reaching the production nginx server could trigger this error when an upstream proxy or client supplied an unrecognised `X-Forwarded-Host`. The existing unknown-`Host` rejection at `docker/production/nginx/nginx.conf:47-51` does not cover this separate header.

## Likely cause commit
39412aa (`maajun: incident report for Production nginx forwards unrecognised Host headers to Django…`) most plausibly left the gap: its resulting production nginx configuration added validation for `$host` but, as shown at `docker/production/nginx/nginx.conf:75-90`, did not also overwrite the trusted `X-Forwarded-Host` input.

## Applied fix
- `docker/production/nginx/nginx.conf:75-90` now sets `X-Forwarded-Host $host` in both Django proxy locations, replacing any client-provided forwarded host with nginx’s validated host.
- `tests/test_allowed_hosts.py:119-133` now asserts that both `/api/v1` and `/guardian` set `X-Forwarded-Host $host`, preventing this proxy-trust boundary from being removed.

Verify by reloading the production nginx configuration and sending the reproduction request: Django should receive `fantasykenya.com` as the forwarded host and no `django.security.DisallowedHost` entry should be emitted.
