# `docker-compose.prod.yml` leaves nginx serving stale host-routing configuration for up to six hours

## Verdict
defect — the production compose command reloaded nginx only every six hours, allowing an already-running container to keep forwarding unrecognised hosts to Django after the checked-in rejection configuration was deployed.

## What happened
A request carrying `Host: staff.fantasykenya.com` reached the API container, where Django’s `CommonMiddleware` rejected it as outside `ALLOWED_HOSTS`. The request did not reach an application view or mutate data, but it produced the reported `django.security.DisallowedHost` API error. The checked-in nginx configuration rejects this host before proxying, so the API log indicates nginx was running a stale configuration or had not yet performed its scheduled reload.

## Root cause
The defect was at `docker-compose.prod.yml:66-67`:

```yaml
# Reload every 6h so renewed certs get picked up without a manual restart.
command: /bin/sh -c 'while :; do sleep 6h & wait $${!}; nginx -s reload; done & nginx -g "daemon off;"'
```

The deployment assumed a six-hour delay was acceptable for mounted nginx configuration changes. That assumption does not hold for the unknown-host rejection in `docker/production/nginx/nginx.conf:8-24` and `47-51`, which must take effect before hostile traffic is proxied. The running container could retain its prior virtual-host table for almost six hours after the bind-mounted configuration changed.

Django correctly rejects the value at `config/settings/production.py:45-54`:

```python
SERVED_DOMAINS = ["fantasykenya.com", "www.fantasykenya.com"]
...
ALLOWED_HOSTS = pinned_hosts(ALLOWED_HOSTS, SERVED_DOMAINS)
```

## How to reproduce
1. Start the production nginx service from a configuration revision that lacks the unknown-host rejection.
2. Deploy the checked-in `docker/production/nginx/nginx.conf` without recreating or manually reloading the nginx container.
3. Within the original six-hour reload interval, request `/api/v1/` with `Host: staff.fantasykenya.com`.
4. nginx can forward the request to Django, which logs the reported `DisallowedHost`.

## Blast radius
Any unrecognised hostname could reach Django during the stale-config window, including arbitrary scanner traffic and `staff.fantasykenya.com`. Requests through the intended `fantasykenya.com` and `www.fantasykenya.com` hosts retain their existing routing; Django remains defense in depth for any request that bypasses nginx rejection.

## Likely cause commit
39412aa (`maajun: incident report for Production nginx forwards unrecognised Host headers to Djang…`) most plausibly introduced this operational gap: it added nginx unknown-host handling, while `docker-compose.prod.yml` still delayed reloading the mounted configuration for six hours.

## Applied fix
- `docker-compose.prod.yml:66-68` now reloads nginx every minute rather than every six hours, so the mounted unknown-host rejection configuration is applied promptly without a manual container restart. The comment now documents that both certificate renewal and mounted configuration updates require the reload.
- `tests/test_allowed_hosts.py:119-127` now asserts that the production compose configuration uses a one-minute nginx reload and retains the reload command, preventing the stale-routing interval from silently returning.

Verification: deploy the compose change, then request a proxied path with `Host: staff.fantasykenya.com`. Within one minute, nginx should close the request with status `444`, and no corresponding `django.security.DisallowedHost` entry should appear in API logs. I could not execute tests or operate the deployment because this environment has no command-execution access.
