## Incident Report: Auth session is not restored on app pages

**Error summary:** The frontend's session-bootstrap call is wrapped in exactly the wrong condition. `initialize()` — the only code that reads the persisted token out of localStorage and hydrates the auth store — runs **only on the routes that are excluded from the app layout** (`sign-in`, `sign-up`, `activation`, password-reset pages, 404). On every real app page the guard skips it, so a returning user with a valid token in localStorage is treated as signed out until they happen to visit a login screen first.

### Defect

**File:** `client/src/App.vue:12-28`

```vue
const excludedRoutes = [
  "sign-in",
  "sign-up",
  "activation",
  "reset-password",
  "reset-password-request",
  "NotFound",
];

const isExcludedRoute = computed(() => excludedRoutes.includes(route.name as string));

onMounted(async () => {
  if (isExcludedRoute.value) {          // ← inverted
    await authStore.initialize();
    await kplStore.fetchAllData();
  }
});
```

### What happens / root cause

1. `authStore.initialize()` (`client/src/stores/auth.ts:235-242`) is the sole session-restoration path:

   ```ts
   async initialize(): Promise<void> {
     const token = localStorage.getItem("token");
     const refresh = localStorage.getItem("refresh");
     if (token) {
       this.setToken(token, refresh);
       await this.refreshUserProfile();
     }
   }
   ```

2. `App.vue` runs it in `onMounted` **only when `isExcludedRoute` is true**, i.e. on sign-in/sign-up/activation/reset/404. There is no router `beforeEach` guard anywhere else that would compensate — `client/src/router/index.ts` registers plain route records with no `meta.requiresAuth` and no navigation guards, so nothing else ever calls `initialize()`.

3. Consequences for a user who reloads `https://…/standings` or follows a shared link straight to `/fkl_team`:
   - `authStore.token` stays empty even though `localStorage.token` exists → the axios interceptor has no access token to attach, so authenticated API calls go out unauthenticated.
   - `refreshUserProfile()` is never called → `user` is null → the navbar/profile UI renders the logged-out state.
   - `kplStore.fetchAllData()` also never fires on these pages, so store-driven views start from an empty state.
   - The same reload works fine when the user last visited `/sign-in` — which makes the bug look intermittent ("works after I log in again").

4. The condition reads as if it were meant to be "run bootstrap everywhere *except* the bare auth screens", but as written it excludes precisely the pages that need the session. Note also that `route.name` is checked once in `onMounted`; since `App.vue` never unmounts on navigation, even the intended behaviour would only fire for the *first* route of a visit.

### Suggested fix

Invert the guard so bootstrap runs on app pages, and move it into a router guard so it runs once per visit regardless of entry route:

```ts
// client/src/router/index.ts
router.beforeEach(async () => {
  const authStore = useAuthStore();
  const kplStore = useKplStore();
  await authStore.initialize();      // cheap no-op when already initialized
  await kplStore.fetchAllData();
});
```

Minimal alternative keeping the current structure:

```ts
onMounted(async () => {
  if (!isExcludedRoute.value) {      // ← flip the polarity
    await authStore.initialize();
    await kplStore.fetchAllData();
  }
});
```

(Optionally make `initialize()` idempotent — early-return when `this.token` is already set — so repeated calls from guards are free.)

### Blast radius

Every deep link, hard refresh, or bookmarked URL on the six app routes (`home`, `team`, `standings`, `fixtures`, `leagues`, `profile`) for any previously signed-in user. Fantasy-team submission and profile updates fail with 401s; standings/fixtures degrade to anonymous data. No backend change involved.
