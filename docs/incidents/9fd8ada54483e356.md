# Production nginx lets clients control Django’s trusted `X-Forwarded-Host` in `docker/production/nginx/nginx.conf`

## Verdict
defect — `USE_X_FORWARDED_HOST` trusts a header that nginx previously forwarded unchanged from the client, so a valid public Host could be overridden with an unrecognised hostname before Django validates it.

## What happened
A requester reached a Django-proxied route with `X-Forwarded-Host: webmail.fantasykenya.com`. Django’s `CommonMiddleware` called `request.get_host()` and rejected that value because production allows only `fantasykenya.com` and `www.fantasykenya.com` (`config/settings/production.py:45-54`). No application view ran or data was written, but the rejected request generated the logged `DisallowedHost` error.

The supplied log and Django dependency paths are outside the readable workspace, so the traceback source could not be opened directly.

## Root cause
`docker/production/nginx/nginx.conf:75-81` previously replaced the proxied `Host` but did not replace `X-Forwarded-Host`:

```nginx
location /api/v1 {
    proxy_pass http://api;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Host $host;
```

Nginx passes request headers upstream unless explicitly replaced. Meanwhile, production enables Django’s trusted forwarded-host behavior at `config/settings/production.py:61`:

```python
USE_X_FORWARDED_HOST = True
```

The proxy assumed that setting `Host $host` was sufficient to establish the upstream hostname. That assumption does not hold when a client supplies `X-Forwarded-Host`: Django preferentially uses that client-controlled header and receives `webmail.fantasykenya.com`, despite nginx’s `$host` guard at `docker/production/nginx/nginx.conf:49-51`.

## How to reproduce
Send an HTTPS request to `/api/v1/...` or `/guardian/...` with an allowed Host and an unrecognised forwarded host:

```http
Host: fantasykenya.com
X-Forwarded-Host: webmail.fantasykenya.com
```

Before the change, nginx proxied the supplied `X-Forwarded-Host` unchanged and Django rejected it with the logged error.

## Blast radius
Both KFL Django proxy locations, `/api/v1` and `/guardian`, had the same pass-through behavior (`docker/production/nginx/nginx.conf:75-90`). Any client could cause a `DisallowedHost` log entry with a forged `X-Forwarded-Host`, even when its ordinary `Host` passed nginx’s public-host guard.

## Likely cause commit
Unclear — the available commit summary identifies shared-nginx work (`27cbf1f`) but does not expose file-level changes for the listed commits, so this investigation cannot attribute the pre-existing missing forwarded-host override to a specific commit.

## Applied fix
- `docker/production/nginx/nginx.conf:75-90` now sets `X-Forwarded-Host $host` in both Django proxy locations, replacing any client-supplied value with nginx’s validated host before it reaches Django.
- `tests/test_allowed_hosts.py:119-134` now verifies that both `/api/v1` and `/guardian` explicitly replace `X-Forwarded-Host`, preventing removal of the proxy trust boundary.

Verify by reloading the production nginx configuration and requesting a proxied route with `Host: fantasykenya.com` plus `X-Forwarded-Host: webmail.fantasykenya.com`: Django should receive `fantasykenya.com` and no `django.security.DisallowedHost` entry should be emitted. I could not execute tests or reload nginx because this environment has no command-execution access.
