# Google OAuth sends credentials read via raw `os.getenv()` — the whitespace-tolerant `env()` hardening in `config/settings/base.py` never reached `apps/accounts/services.py`

**Summary:** `apps/accounts/services.py` re-read `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` with bare `os.getenv()` (lines 42–43, 68) instead of using the trimmed values already computed in `config/settings/base.py:405-406`, so a single stray space in `.env`/`.env.prod` corrupted the client_id and broke every Google sign-in — the exact failure mode the `env()` helper was written to prevent.

## What happened

Users signing in with "Continue with Google" got `Failed to exchange authorization code` (or `Token audience mismatch`) whenever the deployed environment file carried incidental whitespace around the Google credential values. The settings layer was already hardened against this (`config/settings/base.py:32-40`), but the OAuth service bypassed that hardening entirely and went back to the raw process environment.

## Root cause

Two parallel sources of truth for the same credentials, and the one the OAuth flow actually used was the unhardened one:

1. **The tolerant reader existed and was applied — but only in settings.**
   `config/settings/base.py:32-40`:

   ```python
   def env(name, default=None):
       """os.getenv, but tolerant of stray whitespace around values.

       docker-compose's env_file keeps values verbatim, so a trailing space on a
       line makes its way into the value and breaks things far from the cause
       (e.g. a Google client_id arriving as "...googleusercontent.com%20").
       """
       value = os.getenv(name, default)
       return value.strip() if isinstance(value, str) else value
   ```

   And `config/settings/base.py:405-406` uses it:

   ```python
   GOOGLE_CLIENT_ID = env("GOOGLE_CLIENT_ID")
   GOOGLE_CLIENT_SECRET = env("GOOGLE_CLIENT_SECRET")
   ```

2. **The OAuth service ignored those settings and re-read the raw environment.**
   `apps/accounts/services.py:39-49` (`exchange_code_for_tokens`) posted to Google with:

   ```python
   data={
       "client_id": os.getenv("GOOGLE_CLIENT_ID"),
       "client_secret": os.getenv("GOOGLE_CLIENT_SECRET"),
       ...
   }
   ```

   and `apps/accounts/services.py:68` (`validate_token`) independently checked the ID-token audience against the same untrimmed value:

   ```python
   if token_info.get("aud") != os.getenv("GOOGLE_CLIENT_ID"):
       raise ValueError("Token audience mismatch")
   ```

Because docker-compose's `env_file:` passes values through verbatim (the premise documented in the `env()` docstring itself), a line like `GOOGLE_CLIENT_ID=1234-abcd.apps.googleusercontent.com ` (trailing space) yielded `"…%20"`-style corruption in `services.py` while `base.GOOGLE_CLIENT_ID` held the clean value. The token-exchange POST then failed with Google's `invalid_client`, or — if the exchange somehow succeeded — the `aud` comparison rejected the token. Both paths raise `ValueError` and land in the callback's error redirect.

## How to reproduce

1. Add a trailing space (or newline artifact) to `GOOGLE_CLIENT_ID` in `.env` / `.env.prod` — invisible in editors, preserved by `env_file:`.
2. Start the stack and sign in with "Continue with Google".
3. Observe the backend log: `Failed to exchange code for tokens: 400 Client Error: Bad Request for url: https://oauth2.googleapis.com/token` followed by the raised `ValueError("Failed to exchange authorization code")`; the frontend receives the `auth_error` redirect.
4. Contrast: `python -c "from config.settings.base import GOOGLE_CLIENT_ID; print(repr(GOOGLE_CLIENT_ID))"` prints the clean value — proving the hardened setting exists but was unused by the OAuth flow.

## Blast radius

- **Every Google sign-in fails** in any environment (dev or prod) whose env file carries stray whitespace on either credential line — the whole "Continue with Google" flow is dead, including registration, since `get_or_create_user` is only reachable after token validation.
- **Two independent failure points**: the token-exchange POST *and* the audience check each compared against the corrupted value, so partial trimming fixes don't help.
- **Silent deployment risk**: nothing validated the credential format at startup; the misconfiguration surfaced only as user-facing login failures.
- Email/password users are unaffected, which masks the outage during rollout testing.

## Likely cause commit

**Pre-existing.** The `env()` helper and the `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` settings were added in the hardening pass documented in `docs/incidents/bb1261de30d1dac3.md`, but `apps/accounts/services.py` predates it and was never migrated. Recent master history touches only CI workflow, black/flake8/isort formatting, and docs — none plausibly touched the accounts app.

## Suggested fix

Make `config.settings.base` the single source of truth — the settings module already imports cleanly inside task modules elsewhere (e.g. `apps/kpl/tasks/standings.py:11`):

```python
# apps/accounts/services.py
from config.settings import base

...
    data={
        "client_id": base.GOOGLE_CLIENT_ID,
        "client_secret": base.GOOGLE_CLIENT_SECRET,
        ...
    }
```

and likewise:

```python
if token_info.get("aud") != base.GOOGLE_CLIENT_ID:
    raise ValueError("Token audience mismatch")
```

## Applied fix

Changed **`apps/accounts/services.py`** (the only file that needed to differ):

1. Removed the now-unused `import os` and added `from config.settings import base` (line 9).
2. `exchange_code_for_tokens` now sends `"client_id": base.GOOGLE_CLIENT_ID` and `"client_secret": base.GOOGLE_CLIENT_SECRET` (lines 43–44) instead of raw `os.getenv(...)` calls.
3. `validate_token` now compares `token_info.get("aud") != base.GOOGLE_CLIENT_ID` (line 69).

Verified by re-reading the file post-edit: no `os.getenv("GOOGLE_` usage remains, imports are consistent with the existing pattern in `apps/kpl/tasks/standings.py`, and no other module reads these credentials from the raw environment (`grep GOOGLE_CLIENT config/` matches only the two hardened settings definitions). Nothing outside the repository needs to change — the same `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` env vars are read as before, just through the whitespace-trimming `env()` path.
