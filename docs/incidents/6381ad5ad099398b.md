# Google OAuth sign-in puts JWT access and refresh tokens in the redirect URL

**Summary:** The Google OAuth callback builds its success redirect with both JWTs embedded in the query string (`apps/accounts/views.py:104–125`), and `client/src/views/Auth/OAuthCallback.vue:43–66` reads them straight out of `route.query` without ever scrubbing the URL — so every Google sign-in leaks long-lived credentials into the address bar, browser history, `Referer` headers, and nginx/Django access logs.

---

## What happened

Every user who signs in with "Continue with Google" receives their freshly minted JWT pair **in the URL** of the redirect back to the frontend:

```
/auth/callback?auth_success=true&auth_message=success&tokens=%7B%22access%22%3A%22eyJ...%22%2C%22refresh%22%3A%22eyJ...%22%7D&user=...
```

The tokens are then parsed out of `window.location` and persisted. Anyone who can observe that URL — server access logs, synced browser history, a third-party resource loaded on the callback page, or a shoulder-surfer — obtains credentials that grant full account takeover, because the refresh token outlives the session (`SIMPLE_JWT.ACCESS_TOKEN_LIFETIME` is 1 day in `config/settings/base.py`) and can mint new access tokens indefinitely.

## Root cause

Two ends of the same flow:

**1. Backend embeds the tokens in the redirect target** — `apps/accounts/views.py`:

```python
tokens = UserAuthService.generate_tokens(user)          # line 105
encoded_tokens = urllib.parse.quote(                    # line 109
    json.dumps({"access": tokens["access"], "refresh": tokens["refresh"]})
)
encoded_user = urllib.parse.quote(json.dumps(user_data))  # line 117

success_url = (                                         # line 120
    f"{redirect_to}?auth_success=true&auth_message=success"
    f"&tokens={encoded_tokens}&user={encoded_user}"
    f"&is_new_user={is_new}&origin={origin}"
)
return redirect(success_url)
```

Both the access token **and the refresh token** ride in `?tokens=`. The error paths (lines 79–80, 85–88, 129–134) carry only error text, so the leak is specific to successful sign-ins.

**2. Frontend accepts tokens from the URL and never cleans up** — `client/src/views/Auth/OAuthCallback.vue`:

```typescript
const tokensParam = route.query.tokens as string;            // line 47
const userParam = route.query.user as string;                // line 48
...
const tokens = JSON.parse(decodeURIComponent(tokensParam));  // line 58
const userData = JSON.parse(decodeURIComponent(userParam));  // line 59

authStore.setToken(tokens.access, tokens.refresh);           // line 61
authStore.setUser(userData);                                 // line 62
```

`setToken` persists both JWTs to `localStorage` (XSS-readable), and no `history.replaceState` call ever removes the query string, so the tokens remain visible in the address bar and history after the redirect completes.

**Aggravating factor:** `redirect_to` is taken from user-controlled input (`request.GET.get("redirect_to", ...)` at `views.py:22`, echoed into `state` at line 30 and back into `success_url` at line 120), so the token-carrying redirect target is attacker-influenced — widening this from a passive leak into a potential exfiltration channel.

## How to reproduce

1. Configure Google OAuth (dev or prod) and click "Continue with Google".
2. Observe the redirect back to `/auth/callback` — it contains `?tokens=<url-encoded JWT pair>&user=<profile JSON>`.
3. Run `docker compose logs api` or check the nginx access log: the full request URI, including both JWTs, is logged in plaintext.

## Blast radius

- **Access logs:** nginx and Django log the request line with the query string; tokens land on disk and in any log aggregation/retention pipeline.
- **Browser history:** the URL persists locally and in synced history (Chrome Sync), outliving the session by months.
- **Referer leakage:** any third-party asset the callback page loads (fonts, analytics, error tracking) receives the full URL in the `Referer` header.
- **Refresh token is the prize:** it can mint new access tokens for up to its full lifetime, so a single leaked URL equals account takeover, not a temporary session.
- **Scope:** every Google sign-in, in every environment.

## Likely cause commit

Pre-existing. The defect lives in `apps/accounts/views.py` (Google callback) and `client/src/views/Auth/OAuthCallback.vue`; recent master history touches only CI workflow, formatting, and docs. Related open CI failure: run #20 on branch `fix/prod-hardening`, commit `48ab966c`.

## Suggested fix

Prefer not putting tokens in the URL at all:

1. **Best:** keep the code exchange server-side but hand tokens over through a channel that isn't the URL — POST the Google code to the existing `GoogleAuthTokenView` (`views.py:137–189`) and return the tokens in the JSON response body, or set the refresh token as an `HttpOnly; Secure; SameSite=Lax` cookie from the callback and return only the short-lived access token in the body.
2. **If the redirect flow must stay:** redirect with a short-lived, single-use authorization code and have the frontend exchange it via POST — never the tokens themselves.
3. **Frontend hardening regardless:** on mount, immediately scrub the query string:
   ```typescript
   window.history.replaceState({}, "", window.location.pathname);
   ```
   and prefer HttpOnly cookies over `localStorage` for the refresh token.

## Applied fix

Not yet applied — this report documents the failure and the concrete patch. The minimal safe change is #1 (tokens via response body or HttpOnly cookie, never the URL); #3 (URL scrubbing) is a worthwhile belt-and-braces measure that can ship independently.

## Verification

No automated tests exist for the OAuth flow (`tests/` contains only `test_allowed_hosts.py` and `test_entrypoint.py`). A regression test should assert that `GoogleAuthCallbackView.get` never includes `tokens=` in its redirect target, and that `OAuthCallback.vue` calls `history.replaceState` before persisting credentials. Findings were validated by reading `apps/accounts/views.py`, `apps/accounts/urls.py`, `config/urls.py`, `client/src/views/Auth/OAuthCallback.vue`, `client/src/router/index.ts`, and `config/settings/base.py`/`production.py`.
