# Production nginx routes unknown Host headers to Django instead of rejecting them at the edge

## Verdict
defect — production nginx used the `fantasykenya.com` virtual host as the implicit default, so scanner traffic with arbitrary hosts could be proxied to Django and generate avoidable `DisallowedHost` errors.

## What happened
A client sent `Host: ed.da.3aa9.ip4.static.sl-reverse.com` to the public deployment. Since the production nginx configuration had no explicit default virtual host, nginx selected the first application server; an `/api/v1` or `/guardian` request could then be forwarded upstream with that unrecognised host. Django’s `CommonMiddleware` correctly rejected it against `ALLOWED_HOSTS`, producing the logged `DisallowedHost` error before any application view or data mutation ran.

## Root cause
`docker/production/nginx/nginx.conf:6-18` previously made the public HTTP application server the first—and therefore implicit default—server:

```nginx
server {
    listen 80;
    server_name fantasykenya.com www.fantasykenya.com;
```

The equivalent HTTPS server begins at `docker/production/nginx/nginx.conf:21-24`. The configuration assumed requests arriving at the edge would have one of the declared `server_name` values. That assumption does not hold for direct IP scans and arbitrary `Host` headers. The proxy locations preserve the received host via `proxy_set_header Host $host` at `docker/production/nginx/nginx.conf:52` and `:60`, so invalid host values reached Django.

Django’s rejection is correct: `config/settings/production.py:45-54` permits only `fantasykenya.com` and `www.fantasykenya.com`.

## How to reproduce
Send a request to the production address with an unrecognised host and an API path, for example:

```http
GET /api/v1/ HTTP/1.1
Host: ed.da.3aa9.ip4.static.sl-reverse.com
```

Before this change, nginx could select the first production server and proxy the request through `/api/v1` (`docker/production/nginx/nginx.conf:47-53`), after which Django rejects the host. After this change, nginx’s default server returns `444` before proxying.

## Blast radius
Any arbitrary host targeting a proxied production endpoint could create the same Django error; static and Vue routes were not proxied to Django. The two intended domains retain their existing routing, and Django retains its `ALLOWED_HOSTS` validation as defense in depth.

## Likely cause commit
27cbf1f (`feat: serve mogul.manager from the shared nginx edge`) — it added a second nginx virtual-host file and explicitly documents that `fantasykenya.com` remains the default for unmatched hostnames, preserving the unsafe implicit-default behavior in `docker/production/nginx/nginx.conf`.

## Applied fix
- `docker/production/nginx/nginx.conf:6-27` now defines explicit default HTTP and HTTPS servers for `server_name _` that return nginx status `444` without proxying unknown-host traffic to Django. The HTTPS default uses the existing `fantasykenya.com` certificate files because nginx requires a certificate to complete TLS handling before returning the rejection.
- `tests/test_allowed_hosts.py:36-77` now excludes the nginx catch-all name from the configured application-domain comparison and asserts that both default listeners reject unknown hosts without a proxy location.

Verification is to run the repository test suite including `tests/test_allowed_hosts.py`, reload the production nginx configuration, and request `/api/v1/` using an unrecognised `Host`; nginx should close the request with `444` and no new Django `DisallowedHost` log entry should be emitted.
