# Production host-header validation is effectively disabled, CSRF origins omit the forum subdomain, and DB credentials travel as plaintext compose interpolation

## What happened

A review of the production deployment path — `docker-compose.prod.yml`, `docker/production/nginx/nginx.conf`, `config/settings/base.py`, and `config/settings/production.py` — found four concrete, verifiable issues in the current code. None is a confirmed outage; #1–#3 are security-configuration gaps whose effect is silent until an attacker (or a 403 for a legitimate forum POST, #4) exercises them:

1. **🟠 Medium — `ALLOWED_HOSTS` defaults to `["*"]` in production.** The wildcard only disappears if the operator happens to set `ALLOWED_HOSTS` in the gitignored `.env.prod`; nothing in the repo enforces that, so Django's Host-header validation can be disabled in production.
2. **🟠 Medium — `USE_X_FORWARDED_HOST = True` trusts a client-controllable header that nginx never normalizes.** Combined with #1, an attacker can present any `Host`/`X-Forwarded-Host` and Django accepts it, poisoning password-reset links and absolute URLs.
3. **🟡 Low — Production DB credentials are plaintext compose interpolation.** `docker-compose.prod.yml` passes `POSTGRES_PASSWORD=${PG_PASSWORD}` and the app reads `PG_USER`/`PG_PASSWORD` straight from env; the values are visible in `docker compose config`/process listings and sit in a gitignored-but-unencrypted `.env.prod`.
4. **🔴 High (conditional) — `CSRF_TRUSTED_ORIGINS` omits `https://forum.fantasykenya.com`.** If a forum subdomain is served by this Django backend, every cross-origin POST from it fails CSRF with 403. Note: I could not verify a forum exists — the repo contains zero references to "forum", and nginx `server_name` only lists `fantasykenya.com` and `www.fantasykenya.com`. This finding is therefore reported as conditional; it needs a one-line confirmation from the operator.

## Root cause

### 1. `ALLOWED_HOSTS = ["*"]` when `ALLOWED_HOSTS` is unset

`config/settings/base.py:58-60`:

```python
ALLOWED_HOSTS = [
    h.strip() for h in re.split(r"[,\s]+", env("ALLOWED_HOSTS", "*")) if h.strip()
]
```

The value is env-driven with a `"*"` default. The previous incident report (`docs/incidents/bb1261de30d1dac3.md`) deliberately chose that default "so existing dev/CI setups (which don't set the variable) behave exactly as before — but production can now pin its real domains." The flaw in that reasoning: **nothing pins production.** `config/settings/production.py` never overrides `ALLOWED_HOSTS`, so whether prod is safe depends entirely on an uncommitted `.env.prod` value that CI and the operator can forget. The intent is already encoded elsewhere — `CSRF_TRUSTED_ORIGINS` hardcodes `https://fantasykenya.com` / `https://www.fantasykenya.com` (`base.py:69-70`) — but `ALLOWED_HOSTS` does not fail closed with the same domains.

### 2. `USE_X_FORWARDED_HOST = True` + wildcard = Host-header injection

`config/settings/production.py:35-36`:

```python
SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")
USE_X_FORWARDED_HOST = True
```

With `USE_X_FORWARDED_HOST = True`, Django validates and uses the **`X-Forwarded-Host`** header instead of `Host`. The nginx upstream block (`docker/production/nginx/nginx.conf:48-54`) sets `proxy_set_header Host $host;` but never sets or strips `X-Forwarded-Host`, so a client-supplied `X-Forwarded-Host: evil.example` passes through untouched. Two compounding effects:

- **Validation:** Django checks the forged header against `ALLOWED_HOSTS`, which is `["*"]` unless the operator pinned it (issue #1) — so the forged value is always accepted.
- **URL generation:** Django then uses the attacker-chosen host for `build_absolute_uri` — the basis of password-reset emails, activation links, and any absolute redirect. Even with `ALLOWED_HOSTS` correctly pinned, the value Django trusts is the one nginx forwarded verbatim, so pinning alone does not fix this path.

The intent of `USE_X_FORWARDED_HOST = True` is to make `request.get_host()` reflect the public hostname behind the proxy, but nginx already forwards the real host via `Host $host` — the setting is redundant for that purpose and only adds a second, unvalidated input.

### 3. DB credentials as plaintext interpolation

`docker-compose.prod.yml:28-30`:

```yaml
environment:
  - POSTGRES_USER=${PG_USER}
  - POSTGRES_PASSWORD=${PG_PASSWORD}
  - POSTGRES_DB=${POSTGRES_DB}
```

and `config/settings/production.py:15-24` reads `PG_*`/`POSTGRES_DB` from env for every container. CI interpolates from the same file: `.github/workflows/ci.yml:119` runs `docker compose -f docker-compose.prod.yml --env-file .env.prod`. Consequences: the secret is plaintext on disk (`.env.prod`, gitignored but world-readable per process/file perms), appears in `docker compose config` output and `docker inspect`/process listings, and is interpolated into every deploy command line. Mitigation already present: the postgres port is bound to loopback only (`docker-compose.prod.yml:26-27`, `127.0.0.1:5432:5432`). This is the standard compose pattern; it is Low because the exposure is local to the host, but it is worth recording against the day the host is shared.
