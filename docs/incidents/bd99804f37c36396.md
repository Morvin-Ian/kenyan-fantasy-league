# Production nginx does not explicitly route `plesk.fantasykenya.com` to its rejecting default host

## Verdict
defect — Django correctly rejects the unconfigured host, but a known host probe reached Django instead of being rejected by the production edge.

## What happened
A request with `Host: plesk.fantasykenya.com` reached Django, where `CommonMiddleware` called `request.get_host()` and Django raised `DisallowedHost`. The request did not reach an application view or write application data. Production nginx is intended to close unknown-host traffic with `444` before it is proxied, but the error shows that guarantee was not explicit for this known probe hostname.

## Root cause
`docker/production/nginx/nginx.conf:8-26` previously used only the catch-all `_` name in its rejecting default virtual hosts:

```nginx
server {
    listen 80 default_server;
    server_name _;
    return 444;
}
```

The configuration assumed nginx’s default-server selection alone would keep `plesk.fantasykenya.com` in the rejecting virtual host. That assumption does not hold in the running deployment: the logged request reached Django despite `config/settings/production.py:45-54` correctly limiting `ALLOWED_HOSTS` to `fantasykenya.com` and `www.fantasykenya.com`.

The dependency files named by the traceback are outside this repository and could not be read here. The trace identifies Django `CommonMiddleware` calling `request.get_host()` as the surfacing path; repository code does not reveal whether the live nginx configuration was stale or another ingress path bypassed it.

## How to reproduce
After deploying and reloading the production nginx configuration, request either HTTP or HTTPS on the public deployment with:

```http
GET /api/v1/ HTTP/1.1
Host: plesk.fantasykenya.com
```

Nginx should return `444` without proxying the request to Django; before this change, the running deployment logged Django’s `DisallowedHost` response.

## Blast radius
The explicit mapping protects this recurring Plesk hostname on both production listeners. Other arbitrary hosts remain covered by the rejecting default servers at `docker/production/nginx/nginx.conf:8-26`; any traffic that bypasses nginx can still reach Django and be rejected by `config/settings/production.py:54`.

## Likely cause commit
Unclear — `74fa438` and `39412aa` introduced generic unknown-host rejection, but the current configuration already contains those protections and no supplied commit explains why the live request still reached Django.

## Applied fix
- `docker/production/nginx/nginx.conf:8-26` now explicitly includes `plesk.fantasykenya.com` in the rejecting HTTP and HTTPS default-server `server_name` directives, preserving `return 444` before any proxy location can reach Django.
- `tests/test_allowed_hosts.py:47-74` now excludes any server containing `_` from the application-domain comparison and asserts that both rejecting default servers explicitly name `plesk.fantasykenya.com` and return `444`.

Verify by running `tests/test_allowed_hosts.py`, deploying the changed nginx configuration, and reloading nginx. Request `/api/v1/` using `Host: plesk.fantasykenya.com`; nginx should close the connection with `444` and the API log should contain no corresponding `django.security.DisallowedHost` entry.
