# nginx proxy leaves client-controlled `X-Forwarded-Host` trusted by Django in `docker/production/nginx/nginx.conf`

## Verdict
defect — production enables Django’s `USE_X_FORWARDED_HOST`, but nginx did not replace the client-supplied forwarding header after validating the actual `Host`.

## What happened
A requester could send a valid public `Host` header while supplying `X-Forwarded-Host: kanri.fantasykenya.com`. Nginx accepted the request because its unknown-host guard checks `$host`, then forwarded the unmodified `X-Forwarded-Host` header to Django. Django used that forwarded value, rejected it against its pinned host list, and emitted the logged `DisallowedHost` error before an application endpoint ran.

## Root cause
`docker/production/nginx/nginx.conf:75-90` proxied the validated host but did not overwrite `X-Forwarded-Host`:

```nginx
proxy_set_header Host $host;
proxy_redirect off;
```

Meanwhile, `config/settings/production.py:60-61` enables:

```python
SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")
USE_X_FORWARDED_HOST = True
```

The proxy assumed that validating `$host` also validated the forwarding host Django trusts. That assumption does not hold: a client can independently provide `X-Forwarded-Host`, including `kanri.fantasykenya.com`. The Django dependency files named by the traceback are not in this repository, so the exact framework implementation could not be read here; the repository configuration establishes that Django is configured to trust this header.

## How to reproduce
Send an HTTPS request through the production nginx edge to either proxied route with a configured public host and an unconfigured forwarded host:

```http
GET /api/v1 HTTP/1.1
Host: fantasykenya.com
X-Forwarded-Host: kanri.fantasykenya.com
```

Before the fix, nginx’s `$host` check passes, while Django receives and validates `kanri.fantasykenya.com`, producing the reported error.

## Blast radius
Both Django proxy locations, `/api/v1` and `/guardian`, had the same missing `X-Forwarded-Host` replacement at `docker/production/nginx/nginx.conf:75-90`. Any client able to reach them could cause `DisallowedHost` errors with an arbitrary unallowed forwarded hostname despite supplying an allowed `Host`.

## Likely cause commit
27cbf1f (`feat: serve mogul.manager from the shared nginx edge`) most plausibly introduced or exposed the nginx trust-boundary gap: it changed the shared edge topology while the KFL server remained the default public application host; the existing incident record identifies that commit as the likely source of related unknown-host forwarding behavior.

## Applied fix
- `docker/production/nginx/nginx.conf:75-90` now sets `X-Forwarded-Host $host` in both Django proxy locations, replacing any client-provided value with the host nginx validated before forwarding the request.
- `tests/test_allowed_hosts.py:119-134` now verifies that both `/api/v1` and `/guardian` explicitly set `X-Forwarded-Host $host`; this assertion fails against the prior configuration.

Verify by reloading the production nginx configuration and requesting `/api/v1` and `/guardian` with `Host: fantasykenya.com` plus `X-Forwarded-Host: kanri.fantasykenya.com`: Django should receive `fantasykenya.com` and no `DisallowedHost` entry for `kanri.fantasykenya.com` should be logged. I could not execute tests or reload nginx because this environment has no command-execution access.
