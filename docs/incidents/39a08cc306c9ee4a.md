# Production nginx leaves mounted Host-rejection fixes inactive for up to six hours in `docker-compose.prod.yml`

## Verdict
defect — production mounts `docker/production/nginx/nginx.conf` into the running nginx container, but its six-hour reload interval can leave the already-correct unknown-host rejection inactive long enough for Django to continue logging `DisallowedHost`.

## What happened
A request with `Host: area-riservata.fantasykenya.com` reached Django and was rejected by `CommonMiddleware` before any application endpoint ran. Django correctly refused the unrecognised host because production permits only `fantasykenya.com` and `www.fantasykenya.com` (`config/settings/production.py:45-54`). The checked-out nginx configuration would reject this traffic at the edge, so the API-side error indicates the running nginx worker had not yet loaded that mounted configuration or was not using it.

## Root cause
`docker-compose.prod.yml:54` mounts the repository’s production nginx configuration into the container:

```yaml
- ./docker/production/nginx/nginx.conf:/etc/nginx/conf.d/default.conf
```

but `docker-compose.prod.yml:66-67` previously only reloaded nginx every six hours:

```yaml
# Reload every 6h so renewed certs get picked up without a manual restart.
command: /bin/sh -c 'while :; do sleep 6h & wait $${!}; nginx -s reload; done & nginx -g "daemon off;"'
```

The assumption that does not hold is that a six-hour delay is acceptable for mounted edge-routing changes. `docker/production/nginx/nginx.conf:8-24` defines default HTTP and HTTPS servers that return `444`, and `:47-51` rejects unexpected `$host` values before proxy locations. Until nginx reloads, an already-running worker can continue applying the prior configuration and forward unknown host headers to Django, where `ALLOWED_HOSTS` correctly raises `DisallowedHost`.

The Django dependency files named in the traceback are outside this repository and could not be read. The error does not establish whether the live server had a stale worker, an outdated mounted file, or a different active nginx configuration; it establishes only that the edge rejection did not take effect for this request.

## How to reproduce
1. Run production nginx with the pre-change reload command from `docker-compose.prod.yml`.
2. Replace or update the mounted `docker/production/nginx/nginx.conf` with the unknown-host guards at `:8-24` and `:47-51`.
3. Before the next scheduled nginx reload, send an API request with:

```http
GET /api/v1/ HTTP/1.1
Host: area-riservata.fantasykenya.com
```

The stale nginx worker can preserve the previous routing and forward the host to Django, which rejects it. After a reload, nginx should close the request with `444` before proxying.

## Blast radius
Any production nginx configuration or certificate update mounted into the container can remain unapplied for up to six hours. In particular, all arbitrary hosts targeting `/api/v1` or `/guardian` may continue producing API-side `DisallowedHost` logs until the stale nginx worker reloads; Django’s rejection remains a defense-in-depth control.

## Likely cause commit
39412aa (`maajun: incident report for Production nginx forwards unrecognised Host headers to Djang…`) most plausibly exposed the operational gap: it added edge host rejection in `docker/production/nginx/nginx.conf`, while `docker-compose.prod.yml:66-67` still allowed a six-hour delay before the mounted configuration was loaded.

## Applied fix
- `docker-compose.prod.yml:66-68` now reloads nginx every five minutes rather than every six hours, so mounted Host-routing guards and renewed certificates become active promptly without requiring a manual container restart.
- `tests/test_allowed_hosts.py:119-127` now verifies that the production compose configuration uses the five-minute reload interval and still invokes `nginx -s reload`, preventing a return to a multi-hour stale-edge-config window.

Verify by deploying the compose change, updating the mounted nginx configuration, then waiting no more than five minutes and sending `/api/v1/` with `Host: area-riservata.fantasykenya.com`; nginx should return `444` without a matching `django.security.DisallowedHost` API log. The test suite and deployment could not be run because this environment has no command-execution access.
