# docker-compose.prod.yml delays nginx host-rejection configuration reloads for six hours

## Verdict
defect — `docker-compose.prod.yml` mounts the host-rejection configuration but waits up to six hours to reload nginx, allowing a stale edge configuration to continue forwarding unknown hosts to Django.

## What happened
A requester sent `Host: painel.fantasykenya.com` to the production deployment. Django received that host and rejected it in `CommonMiddleware` because it is absent from the production allow-list, producing the logged `DisallowedHost` error before an application view or data mutation ran. The checked-in nginx configuration should reject that host first, so the log establishes that the running nginx worker had not loaded the current mounted edge rules.

## Root cause
`docker-compose.prod.yml:54` bind-mounts the repository configuration, but the prior command at `docker-compose.prod.yml:66-67` only reloaded nginx every six hours:

```yaml
- ./docker/production/nginx/nginx.conf:/etc/nginx/conf.d/default.conf
...
command: /bin/sh -c 'while :; do sleep 6h & wait $${!}; nginx -s reload; done & nginx -g "daemon off;"'
```

The mounted `docker/production/nginx/nginx.conf:8-24` declares HTTP and HTTPS default servers returning `444`, and `:47-51` rejects any host other than the two served KFL domains. The configuration therefore assumed reload latency was acceptable after a host-rejection change. That assumption does not hold: the active worker can preserve the old proxy behavior for up to six hours, exposing Django to the avoidable error.

Django correctly restricts production hosts at `config/settings/production.py:45-54`:

```python
SERVED_DOMAINS = ["fantasykenya.com", "www.fantasykenya.com"]
...
ALLOWED_HOSTS = pinned_hosts(ALLOWED_HOSTS, SERVED_DOMAINS)
```

The external Django source files named by the traceback and the supplied live logfile could not be read because they are outside the available repository workspace. The traceback identifies Django’s `CommonMiddleware` host validation as the surfacing path.

## How to reproduce
1. Deploy an nginx container with an older configuration that proxies `/api/v1` or `/guardian` before the unknown-host guard.
2. Update the bind-mounted `docker/production/nginx/nginx.conf` with the current `return 444` rules without restarting or reloading nginx.
3. Within the old six-hour reload interval, request a proxied path with:

```http
Host: painel.fantasykenya.com
```

The stale nginx worker forwards `$host` through `docker/production/nginx/nginx.conf:75-80` or `:83-88`, and Django raises `DisallowedHost`.

## Blast radius
All unknown hosts sent to `/api/v1` or `/guardian` can reach Django for the stale-config interval after an edge-rule update. Requests for `fantasykenya.com` and `www.fantasykenya.com` retain their existing routes; `mogul.fantasykenya.com` is handled independently by `docker/production/nginx/mogul.conf:27-90`.

## Likely cause commit
27cbf1f (`feat: serve mogul.manager from the shared nginx edge`) most plausibly introduced the original unknown-host routing gap; the later host-rejection commits added the current nginx rules, while the six-hour reload cadence in `docker-compose.prod.yml` left a deployment window in which the old behavior could remain live.

## Applied fix
- `docker-compose.prod.yml:66-68` now reloads nginx every five minutes rather than every six hours, so bind-mounted host-rejection rules are applied promptly while certificate renewal handling remains automatic.
- `tests/test_allowed_hosts.py:105-112` now asserts that the production compose definition uses the five-minute nginx reload cadence and still invokes `nginx -s reload`.

Verify by deploying the compose change, updating or confirming the mounted production nginx configuration, and requesting `/api/v1/` with `Host: painel.fantasykenya.com` after the next reload. Nginx should close the connection with `444`, with no matching `django.security.DisallowedHost` log entry. I could not execute the test suite, inspect the live container, or reload nginx because this environment provides no command-execution access.
