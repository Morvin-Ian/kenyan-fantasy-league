# Production settings omitted `painel.fantasykenya.com` from the accepted public domains

## Verdict
defect — the panel hostname was not included in Django’s production allowlist or the production nginx virtual host, so legitimate panel requests could be rejected as `DisallowedHost`.

## What happened
A user or upstream proxy requested the application with `Host: painel.fantasykenya.com`. Django’s `CommonMiddleware` called `request.get_host()` and rejected the hostname because production settings only accepted `fantasykenya.com` and `www.fantasykenya.com`. The nginx configuration also did not declare the panel hostname as an application server name, so the edge and application configuration disagreed with the deployed panel hostname.

## Root cause
`config/settings/production.py:45-49` previously defined only:

```python
SERVED_DOMAINS = [
    "fantasykenya.com",
    "www.fantasykenya.com",
]
```

`ALLOWED_HOSTS` is derived from this list at `config/settings/production.py:58`, so `painel.fantasykenya.com` was absent from Django’s accepted hosts. The same assumption existed in `docker/production/nginx/nginx.conf:29` and `:45`, where the HTTP and HTTPS application virtual hosts declared only the two apex domains. The assumption that all valid production requests use one of those two hostnames did not hold.

## How to reproduce
Send a request to the production panel with:

```http
GET /api/v1/ HTTP/1.1
Host: painel.fantasykenya.com
```

Before this change, Django’s production `ALLOWED_HOSTS` did not contain the hostname, causing `request.get_host()` to raise `DisallowedHost`.

## Blast radius
Panel requests using `painel.fantasykenya.com` were rejected by Django, and nginx could route the hostname through an unintended/default virtual host. Requests using `fantasykenya.com` and `www.fantasykenya.com` were unaffected.

## Likely cause commit
Unclear — none of the listed recent commits visibly establish or document `painel.fantasykenya.com`; the relevant production allowlist and nginx configuration instead reflected only the older apex-domain deployment.

## Applied fix
- `config/settings/production.py:45-49` now includes `painel.fantasykenya.com` in `SERVED_DOMAINS`, causing production `ALLOWED_HOSTS` to accept it.
- `config/settings/base.py:62-72` now includes `https://painel.fantasykenya.com` in `CSRF_TRUSTED_ORIGINS`, allowing HTTPS panel requests that submit CSRF-protected forms.
- `docker/production/nginx/nginx.conf:29` and `:45` now declare `painel.fantasykenya.com` on the HTTP redirect and HTTPS application virtual hosts. The HTTPS unknown-host guard at `:49-51` now treats the panel hostname as valid.
- `.env.example:3-7` now documents the panel hostname in the example `ALLOWED_HOSTS` value.
- `tests/test_allowed_hosts.py:36-39` now verifies that `painel.fantasykenya.com` is present in production `ALLOWED_HOSTS`, and `:115` verifies that nginx’s host guard includes it.

I could not run the test suite or reload nginx because this environment provides no command-execution access. Verification should run `pytest tests/test_allowed_hosts.py`, validate/reload the production nginx configuration, and request `/api/v1/` with `Host: painel.fantasykenya.com`; the request should reach Django without `DisallowedHost`.
