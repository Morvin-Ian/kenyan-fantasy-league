# `client/production/nginx.conf` never proxies `/api` to the Django backend — the compose nginx answers every API request with the SPA's `index.html`, leaving the app functionally dead on `:8080`

## Applied fix

- **`client/production/nginx.conf`** (rewritten): added an `upstream api { server api:8000; }` block and reverse-proxy locations for `/api/v1/` and `/guardian/` (Django admin), plus `/staticfiles/` and `/mediafiles/` alias locations that serve the volumes already mounted into the nginx container. The SPA fallback in `location /` is unchanged.
- **`docker-compose.yml`** (nginx service build args): removed the bogus `VITE_API_BASE_URL: http://localhost:8080/api/v1` argument. Nothing consumed it — the built bundle hardcodes `baseURL: "/api/v1"` (`client/src/axios-interceptor.ts:11`) and no source file reads `VITE_API_BASE_URL` — so the dead arg was actively misleading.

Outside the repository, nothing needs to be set for this fix: the frontend now calls its own origin (`/api/v1`), which nginx proxies to `api:8000` over the existing `fpl-vue` network, matching how `docker/production/nginx/nginx.conf` already works in prod.

## What happened

With the stack brought up via `docker compose up`, the site "loads" — nginx serves the built Vue app on port 8080 — but **every API call fails**. The axios client is created with a relative base (`client/src/axios-interceptor.ts:10-13`, `baseURL: "/api/v1"`), so all requests hit nginx itself. The nginx config shipped for that container had exactly one location block:

```nginx
server {
    listen 80;
    location / {
        root /usr/share/nginx/html;
        try_files $uri $uri/ /index.html;
    }
}
```

There was no `location /api`, no `location /static/`, no `location /media/`. Any request that wasn't a literal file under `/usr/share/nginx/html` fell through `try_files ... /index.html` and returned the SPA's HTML with status 200. The browser received HTML where it expected JSON, and axios rejected with parse errors (`Unexpected token '<'`), so sign-in, standings, profiles, lineups — everything — was broken while the page itself rendered.

## Root cause

Three pieces of configuration agreed on a design that the fourth piece never implemented:

| Piece | State |
|---|---|
| `docker-compose.yml:12-13` | The `api` service's host port is **commented out**, so nginx is the *only* path from the host to Django |
| `client/src/axios-interceptor.ts:11` | The frontend calls relative `/api/v1` — i.e. it expects same-origin proxying by nginx |
| `docker/production/django/start:13-14` | Gunicorn binds `0.0.0.0:8000` inside the shared `fpl-vue` network — reachable as `http://api:8000` |
| `client/production/nginx.conf` | **No reverse-proxy locations existed** — nothing forwarded `/api/v1/` or served `/staticfiles/`, `/mediafiles/` |

So the architecture intended nginx to be the single origin (SPA + API + static + media), but the config only implemented the SPA half. Two secondary symptoms fell out of the same gap:

- `docker-compose.yml:64-66` mounts `static_volume` and `media_volume` into the nginx container at `/app/staticfiles` and `/app/mediafiles`, but no location block ever served them — `collectstatic` output (Django admin CSS/JS) and uploaded media were unreachable.
- The compose file baked a `VITE_API_BASE_URL` build arg that no code ever read (verified: zero references to `import.meta.env.VITE_API_BASE_URL` across `client/`; the only env reads are `BASE_URL` in the router and `MODE` in `stores/kpl.ts`), masking the real problem behind an unused knob.

## How to reproduce

1. Before this fix: `make build` (equivalent to `docker compose up --build -d --remove-orphans`).
2. Open `http://localhost:8080`. The Vue app renders normally.
3. Devtools → Network: every `GET/POST http://localhost:8080/api/v1/...` returns **200 with `content-type: text/html`** — the body is `index.html`.
4. Or from a terminal: `curl -i http://localhost:8080/api/v1/profile/` → HTTP 200, HTML body. Same for any `/staticfiles/<asset>` → falls back to `index.html`.
5. After this fix: the same curl returns JSON from Django, and `/guardian/` loads the styled admin.

## Blast radius

- **Total functional outage behind a healthy-looking UI**: the SPA loaded (nginx 200s), so health checks and casual smoke tests passed, while login, registration, standings, teams, and lineup submission all failed client-side.
- **Misleading errors**: because the API "responded" with 200 + HTML, failures surfaced as frontend parse errors rather than connection errors, and the axios interceptor's 401/refresh logic never saw a real status code.
- **Django admin unstyled/broken**: `/staticfiles/` was never served from the mounted volume.
- Note this affected the *compose* topology (`docker-compose.yml`). The separate `docker/production/nginx/nginx.conf` (with `server_name fantasykenya.com www.fantasykenya.com` and TLS) is a different config used by the prod deployment and already proxies correctly — the new `client/production/nginx.conf` mirrors its routing model minus TLS.

## Likely cause commit

**Pre-existing.** `client/production/nginx.conf` was a minimal SPA-serving config predating the recent master history (CI workflow, formatting, and docs commits only). Nothing in the current tree ever added proxy locations, and the commented-out `api` ports (`docker-compose.yml:12-13`) confirm the proxy was always meant to be the access path.
