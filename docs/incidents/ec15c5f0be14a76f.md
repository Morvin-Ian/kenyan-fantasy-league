# Postgres rejects every connection from the Django containers: `FATAL: password authentication failed for user "postgres"` logged by `docker:postgres-db`

## What happened

At 2026-08-22 21:47:10.872 UTC the `postgres-db` container logged `FATAL: password authentication failed for user "postgres"` for every connection attempt. The `api`, `celery_worker`, and `celery_beat` containers each retried the DB health check 30 times and exited 1, so nothing served traffic on port 80 and the CI deploy's migrate-retry loop (`ci.yml:125-137`) failed. The password the app presents for user `postgres` does not match what the Postgres server accepts.

## Root cause

`docker/production/django/entrypoint:26-50` (byte-identical copy in `docker/local/django/entrypoint`) built the DB health-check program with an **unquoted** bash heredoc:

```bash
python3 << END
...
conn = psycopg2.connect(
    dbname="${POSTGRES_DB}",
    user="${PG_USER}",
    password="${PG_PASSWORD}",
    host="${PG_HOST}",
    port="${PG_PORT}",
)
```

Because the delimiter `END` is unquoted, bash expands every `${...}` in the body *before* Python ever sees it. The assumption that does not hold: *shell interpolation copies the value of `PG_PASSWORD` into the Python source unchanged.* That is only true when the password contains no `$`, backtick, `\` or quote — the moment one appears (any generated secret), bash mangles the value, psycopg2 sends the wrong password, and postgres logs exactly `FATAL: password authentication failed for user "postgres"`. The same entrypoint runs on every container that talks to the DB, since `api`/`worker`/`beat` share the image and `ENTRYPOINT ["/entrypoint"]` (`docker/production/django/Dockerfile:44`).

The other path to this identical log line is server state, not code: the compose files pass `POSTGRES_PASSWORD=${PG_PASSWORD}` from the env file, but the official postgres image only applies it on first init of the `postgres_data` volume — so if `PG_PASSWORD` was ever edited in `.env.prod` (or differs from what the volume was created with), every deploy fails the same way even with a plain alphanumeric password. `.env.prod` is gitignored (server-side), so both paths had to be checked; the heredoc is the defect fixable in this repository.

## How to reproduce

1. Set `PG_PASSWORD` in `.env`/`.env.prod` to a value containing a shell metacharacter (e.g. `pa$$word`, or a `$`/backtick from a password generator), or
2. start `docker compose up` (or the CI deploy) against a `postgres_data` volume that was initialized with a different `POSTGRES_PASSWORD` than the current `PG_PASSWORD`.

Postgres then logs `FATAL: password authentication failed for user "postgres"` for each of the entrypoint's 30 attempts and the `api` container exits 1.

## Blast radius

Every container using the shared Django image hits this on every start: `api`, `celery_worker`, `celery_beat` in both `docker-compose.yml` and `docker-compose.prod.yml` (the worker/beat services also run the entrypoint). Any developer or CI environment whose password contains shell metacharacters fails identically; the volume-drift variant fails for everyone regardless of password until the volume is resynced. Settings confirm the DB credentials travel end-to-end through `PG_*` env vars (`config/settings/production.py:15-24`, `config/settings/development.py:15-24`), so any corruption at the entrypoint propagates to the whole app.

## Likely cause commit

**Unclear.** The recent master commits touch only `.github/workflows/ci.yml`, Python formatting/flake8, and docs — none plausibly touched `docker/*/django/entrypoint`, the compose files, or `config/settings/*.py`, where the defect lives. The heredoc bug is pre-existing; the trigger is the server's `.env.prod`/volume state, which is not in the repo.

## Suggested fix

Quote the heredoc and pass credentials through the environment so bash never expands the body, and bound each attempt with `connect_timeout` (this also stops the 30-attempt loop from hanging on a dead `PG_HOST`):

```bash
postgres_ready() {
    POSTGRES_DB="$POSTGRES_DB" PG_USER="$PG_USER" PG_PASSWORD="$PG_PASSWORD" \
    PG_HOST="$PG_HOST" PG_PORT="$PG_PORT" python3 - <<'END'
import os
import sys
import psycopg2
import time

start_time = time.time()
try:
    conn = psycopg2.connect(
        dbname=os.environ["POSTGRES_DB"],
        user=os.environ["PG_USER"],
        password=os.environ["PG_PASSWORD"],
        host=os.environ["PG_HOST"],
        port=os.environ["PG_PORT"],
        connect_timeout=5,
    )
    conn.close()
    print(f"Successfully connected to PostgreSQL (took {time.time() - start_time:.2f}s)")
    sys.exit(0)
except psycopg2.OperationalError as e:
    print(f"Connection failed: {str(e)}", file=sys.stderr)
    sys.exit(1)
END
}
```

Apply to both `docker/local/django/entrypoint` and `docker/production/django/entrypoint`. On the server, also verify the volume matches the env file: `docker compose exec postgres-db psql -U postgres -c "SELECT 1"`; if it fails, resync with `ALTER USER postgres WITH PASSWORD '<current .env.prod PG_PASSWORD>';` inside the container (or `docker compose down -v`, which wipes data).

## Applied fix

- `docker/local/django/entrypoint` and `docker/production/django/entrypoint`: `postgres_ready()` now forwards `POSTGRES_DB`/`PG_USER`/`PG_PASSWORD`/`PG_HOST`/`PG_PORT` through the environment, feeds Python with a quoted heredoc (`<<'END'`), reads values via `os.environ[...]`, and adds `connect_timeout=5`. Verified in the working tree: both files contain the quoted delimiter and no braced `${PG_*}` expansion remains.
- `tests/test_entrypoint.py` (new): regression test guarding the quoted-heredoc/no-interpolation contract — it asserts both entrypoints use `<<'END'`, read all five `PG_*`/`POSTGRES_DB` values via `os.environ[...]`, and contain no braced `${PG_*}` shell expansion. It fails on the pre-fix entrypoints and passes on the fixed ones.
- `docs/incidents/85310d7c84665436.md` (new): incident record per repo convention.

## Verification

- `pytest -p no:warnings tests/` passes after the change, fails before.
- On the server: rebuild and run `docker compose -f docker-compose.prod.yml --env-file .env.prod up --build -d` and confirm the api log shows `PostgreSQL is ready!` and the site answers on port 80.
- Note: if the server's `postgres_data` volume holds an older password, the `ALTER USER` step above is still required — the code fix removes the mangling path but cannot rewrite the volume.
