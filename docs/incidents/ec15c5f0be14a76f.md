# Production Compose leaves PostgreSQL stopped after an unexpected shutdown

## Verdict
defect — `docker-compose.prod.yml` had no restart policy for `postgres-db`, so a transient database exit could leave the database unavailable indefinitely and make Celery Beat repeatedly fail its database-backed schedule refresh.

## What happened
At 2026-08-29T21:00:00Z, Celery Beat attempted to query the django-celery-beat schedule-change record and PostgreSQL rejected the new connection because it was shutting down. Beat uses the database scheduler configured in `config/settings/base.py:372`, so schedule refreshes and dispatch may be delayed while PostgreSQL is unavailable. Before this change, an unexpected Postgres container exit after that shutdown would leave `postgres-db` stopped because production Compose had no restart policy.

## Root cause
The production PostgreSQL service in `docker-compose.prod.yml:22-37` was configured without `restart`, unlike services such as nginx, which has `restart: always` at `docker-compose.prod.yml:44-46`.

The failing assumption was that PostgreSQL would always be manually restarted after any shutdown:

```yaml
postgres-db:
  image: postgres:12.0-alpine
  ports:
    - "127.0.0.1:5432:5432"
```

`docker-compose.prod.yml:22-28` previously supplied no Docker restart behavior. The supplied traceback is from `django-celery-beat==2.6.0` (`requirements.txt:20`) attempting a normal database connection during shutdown; application code does not explain what initiated that shutdown. The missing restart policy turns that transient condition into a persistent outage.

## How to reproduce
Run the production Compose stack, then cause `postgres-db` to exit unexpectedly (for example, stop or kill the container). Before the change, Compose leaves it stopped; `celery_beat`, configured at `docker-compose.prod.yml:89-105`, subsequently receives the reported `FATAL: the database system is shutting down`/connection failures when its `DatabaseScheduler` accesses PostgreSQL.

## Blast radius
Production `api`, `celery_worker`, and `celery_beat` all depend on `postgres-db` (`docker-compose.prod.yml:2-18`, `71-87`, and `89-105`), and their Django settings obtain database connection values from environment variables at `config/settings/production.py:15-24`. This change prevents a stopped Postgres container after an unexpected exit, but does not eliminate connection errors during the shutdown and restart interval itself.

## Likely cause commit
Unclear — none of the supplied recent commits can be tied to the missing PostgreSQL restart policy from repository files read, and the error requires server-side Postgres lifecycle logs to identify the shutdown trigger.

## Applied fix
- `docker-compose.prod.yml:24` now sets `restart: unless-stopped` on `postgres-db`, so Docker restarts PostgreSQL after an unexpected process or container exit but respects an operator’s intentional stop.
- `tests/test_entrypoint.py:56-62` now verifies that the production `postgres-db` service declares `restart: unless-stopped`; it would fail against the prior Compose configuration and passes once the policy is present.

Verification should run the repository test suite and, in a non-production Compose environment, stop `postgres-db` without manually stopping the service and confirm Docker restarts it. I could not execute tests or Docker commands in this environment.
