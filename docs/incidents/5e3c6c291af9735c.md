# Django rejects every request proxied by nginx: `DisallowedHost: Invalid HTTP_HOST header: 'fantasykenya.com'` in `config/settings/base.py:47`

## What happened

A user opening `https://fantasykenya.com/api/v1/...` got a 400 and the `api` container logged `django.security.DisallowedHost: Invalid HTTP_HOST header: 'fantasykenya.com'` on every request. nginx (`docker/production/nginx/nginx.conf:48-54`) correctly forwards the real `Host: fantasykenya.com` header to `api:8000`; Django's `CommonMiddleware` (`django/middleware/common.py:48` → `django/http/request.py:150`, per the traceback) then rejects the request because `fantasykenya.com` is not in `ALLOWED_HOSTS`. The site was up but every API call failed.

## Root cause

`config/settings/base.py:47`:

```python
ALLOWED_HOSTS = [h for h in os.getenv("ALLOWED_HOSTS", "*").split(" ") if h]
```

This builds `ALLOWED_HOSTS` *entirely* from the environment. Because the default is `"*"` (which Django's `validate_host` accepts for any host), the `DisallowedHost` exception can only fire when the server's gitignored `.env.prod` (loaded via `env_file:` in `docker-compose.prod.yml:12-13`) sets `ALLOWED_HOSTS` to a pinned value that omits `fantasykenya.com` and `www.fantasykenya.com` and contains no `*`. The assumption that does not hold: *the deploy env will always list the real production domain.* Nothing in the repo enforces that, yet every other place that knows the deployment already pins the domain — `docker/production/nginx/nginx.conf:8,24` (`server_name fantasykenya.com www.fantasykenya.com`), `config/settings/base.py:56-57` (`CSRF_TRUSTED_ORIGINS`), and `client/vite.config.ts:14-15`. The line above was introduced by the fix for incident `bb1261de30d1dac3` (commit `2bbdb28`), which replaced a hardcoded `ALLOWED_HOSTS = ["*"]` with this env-driven form — before that change this error was impossible.

## How to reproduce

1. Set `ALLOWED_HOSTS="localhost api nginx"` (no `*`, no public domain) in the env file loaded by the `api` container, i.e. `.env.prod` as wired in `docker-compose.prod.yml:12-13`.
2. `docker compose -f docker-compose.prod.yml --env-file .env.prod up --build -d`.
3. `curl https://fantasykenya.com/api/v1/...` → nginx proxies with `Host $host` (`docker/production/nginx/nginx.conf:52`) → Django raises `DisallowedHost` and logs the exact error above.

The server's actual `.env.prod` is gitignored and not visible in this repo, so I cannot confirm its exact `ALLOWED_HOSTS` value; the error itself proves it is pinned and omits the domain.

## Blast radius

Every proxied endpoint, not just one route: nginx forwards `Host $host` for both `location /api/v1` and `location /guardian` (`docker/production/nginx/nginx.conf:48-62`), so the entire API surface returns 400 while the site appears up. The same failure would hit any developer or staging environment that pins `ALLOWED_HOSTS` without the domain. No data is corrupted — requests are rejected before reaching any view.

## Likely cause commit

**`2bbdb28`** — the incident report for `bb1261de30d1dac3` that changed `config/settings/base.py` from `ALLOWED_HOSTS = ["*"]` to the env-driven `os.getenv("ALLOWED_HOSTS", "*")` form (documented in `docs/incidents/bb1261de30d1dac3.md:20-33`); with the server's `.env.prod` pinning hosts that omit `fantasykenya.com`, that change turns a previously impossible error into a guaranteed one. The other recent commits touch only CI, formatting, the entrypoint heredoc, and docs.

## Suggested fix

Always accept the production domains when the env value doesn't already wildcard — matching what nginx's `server_name` and `CSRF_TRUSTED_ORIGINS` already assume. In `config/settings/base.py`, after line 47:

```python
ALLOWED_HOSTS = [h for h in os.getenv("ALLOWED_HOSTS", "*").split(" ") if h]
# nginx forwards the real Host header (`proxy_set_header Host $host` in
# docker/production/nginx/nginx.conf), so the production domains must be
# accepted even when the deploy env pins ALLOWED_HOSTS to a value that
# omits them.
if "*" not in ALLOWED_HOSTS:
    ALLOWED_HOSTS += ["fantasykenya.com", "www.fantasykenya.com"]
```

Dev/CI keep `ALLOWED_HOSTS = ["*"]` (env unset → default `*` → the `if` is skipped), so behavior there is byte-identical to before; only pinned environments gain the domains, and the Host-header protection from `bb1261de30d1dac3` remains for every other host. Optionally, also add `fantasykenya.com`/`www.fantasykenya.com` to the server's `.env.prod` — the code change makes that belt-and-suspenders rather than load-bearing.

Regression test — `tests/test_settings_allowed_hosts.py` (new; pytest runs `test_*.py` per `pytest.ini:3`). It pins `ALLOWED_HOSTS` to a value that omits the domain, reloads `config.settings.base`, and asserts both domains are present. It fails before the change (`ALLOWED_HOSTS == ["localhost", "api", "nginx"]`) and passes after:

```python
import importlib

from config.settings import base


def test_allowed_hosts_always_accept_production_domains(monkeypatch):
    with monkeypatch.context() as mp:
        mp.setenv("ALLOWED_HOSTS", "localhost api nginx")
        importlib.reload(base)

        assert "fantasykenya.com" in base.ALLOWED_HOSTS
        assert "www.fantasykenya.com" in base.ALLOWED_HOSTS

    importlib.reload(base)
```

## Applied fix

- `config/settings/base.py` — after the env-driven `ALLOWED_HOSTS` line, append `fantasykenya.com` and `www.fantasykenya.com` whenever the resolved list contains no `*`, with a comment pointing at the nginx `Host` forwarding. No imports, formatting, or unrelated lines touched.
- `tests/test_settings_allowed_hosts.py` (new) — regression test as above.

To verify: run `pytest -p no:warnings tests/` (the new test fails on the pre-fix `base.py` and passes now; the existing `tests/test_entrypoint.py` still passes), and `flake8 . && black --check --exclude='migrations|venv|client' . && isort . --check-only` as CI does. On the server: rebuild with `docker compose -f docker-compose.prod.yml --env-file .env.prod up --build -d`, then `curl -I https://fantasykenya.com/api/v1/...` — it should return a real response instead of `DisallowedHost`. One thing I could not determine: the exact `ALLOWED_HOSTS` value in the server's gitignored `.env.prod`; the error proves it is pinned and omits the domain, but the value itself is not in this repo.
