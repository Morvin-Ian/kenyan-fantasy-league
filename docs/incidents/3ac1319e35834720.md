# Google OAuth redirect leaks the JWT pair in the browser URL — fixed with URL scrubbing in `client/src/views/Auth/OAuthCallback.vue`

## What happened

Every "Continue with Google" sign-in lands on the frontend callback with a freshly minted **access and refresh JWT** embedded in the URL query string (`?tokens=...&user=...`). The callback page parses the tokens out of `window.location`, stores them, and navigates away — but never removes them from the URL. The tokens remain visible in the address bar, in browser history (including synced history), in server/proxy access logs, and in any `Referer` header the page emits. A leaked refresh token mints new access tokens, so this is account takeover, not a session hiccup.

## Root cause

Two ends of the same flow, both unchanged in the current checkout:

1. **Backend builds the success redirect with the tokens embedded** — `apps/accounts/views.py:104-125`. After `UserAuthService.generate_tokens(user)`, both JWTs are JSON-encoded, `urllib.parse.quote`d, and spliced into the redirect target:

   ```python
   tokens = UserAuthService.generate_tokens(user)                      # line 105
   encoded_tokens = urllib.parse.quote(                                # line 109
       json.dumps({"access": tokens["access"], "refresh": tokens["refresh"]})
   )
   success_url = f"{redirect_to}?auth_success=true&auth_message=success&tokens={encoded_tokens}&user={encoded_user}&is_new_user={is_new}&origin={origin}"  # line 120
   ```

   Both tokens ride in `?tokens=...`. The error paths (lines 79–80, 86, 129–130, 133–134) carry only error text, so the leak is specific to successful sign-ins.

2. **Frontend accepts the tokens from the URL and never scrubs it** — `client/src/views/Auth/OAuthCallback.vue:43-77`. `route.query.tokens` / `route.query.user` are parsed and stored via `authStore.setToken(tokens.access, tokens.refresh)`. No `history.replaceState` call exists anywhere in the file, so the token-bearing URL survives in the address bar and history after the redirect.

## How to reproduce

1. Configure Google OAuth (dev or prod) and click "Continue with Google".
2. Observe the redirect URL: `?tokens=%7B%22access%22%3A%22eyJ...%22%2C%22refresh%22%3A%22eyJ...%22%7D&user=...` — both JWTs, percent-encoded.
3. Check the nginx/Django access log for that request; the full URI including the token query string is logged in plaintext.

## Blast radius

- **Every Google sign-in in every environment.**
- **Refresh token is the prize:** access lifetime is 1 day per `SIMPLE_JWT`; the leaked refresh token can mint new access tokens indefinitely — account takeover.
- **Access logs:** nginx and Django log the request line including the query string; tokens land on disk and flow to log aggregation/retention systems.
- **Browser history:** the URL persists (and syncs via Chrome sync) long after the session.
- **Referer leakage:** any third-party resource the callback page loads (fonts, analytics, error trackers) receives the full token-carrying URL.
- **User-influenced redirect target:** `redirect_to` is taken from the request (`views.py:22`) and echoed into `success_url`, widening the exfiltration surface.

## Likely cause commit

**Pre-existing.** The defect lives in `apps/accounts/views.py` (Google OAuth callback) and `client/src/views/Auth/OAuthCallback.vue`, both predating the recent master history (CI workflow, formatting, and docs commits only). Trigger: any successful Google sign-in. Matches incident doc `docs/incidents/785cd6ee6d3241ee.md` (fingerprint `a91f4e2c7b3d5f08`).

## Suggested fix

1. **Best (still open):** keep the code exchange server-side but never put tokens in the URL — return them in the JSON response body of `GoogleAuthTokenView` (`views.py:137-189`) or set the refresh token as an `HttpOnly; Secure; SameSite=Lax` cookie, returning only the short-lived access token in the body.
2. **Frontend hardening (applied here):** scrub the query string on mount with `history.replaceState({}, "", window.location.pathname)` so the tokens leave the address bar and history the moment the callback reads them. Independent of #1 and shippable on its own.

## Applied fix

Two files changed:

- **`client/src/views/Auth/OAuthCallback.vue`** — immediately after reading the query params into locals, the component now calls `history.replaceState({}, "", window.location.pathname)` before any async work or navigation. Runs on success and error paths alike, so even a parse failure cannot leave the JWT pair sitting in the URL. The params are read into `const`s first, so the scrub does not lose the data the component needs.
- **`docs/incidents/785cd6ee6d3241ee.md`** — "Applied fix" section updated: #3 shipped, #1 (tokens out of the URL entirely) remains open and should ship next.

External requirement: none for the applied change. The remaining backend-side fix (#1) requires no env var either — it is a code change to `apps/accounts/views.py` / `GoogleAuthTokenView` and the store call, deliberately left out of this patch to keep the change reviewable.
