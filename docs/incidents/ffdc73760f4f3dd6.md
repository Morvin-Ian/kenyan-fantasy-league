# `apps/kpl/tasks/scorers.py` reports a handled no-active-gameweek result as a worker error

## Verdict
defect — the task intentionally returns a handled failure when no gameweek is active, but logs that expected result at error severity, creating a false deployment error alert.

## What happened
Celery Beat invoked `scrape_top_scorers()` without a gameweek ID through the Monday schedule in `config/settings/base.py:387-390`. With no active `Gameweek` in the production database, the task returned `{"success": False, "error": "No active gameweek found"}` rather than scraping or writing `TopcorerData`. No user request or worker process crashed, but the handled condition appeared as the reported `[ERROR]` event.

## Root cause
The defect was at `apps/kpl/tasks/scorers.py:193-195`:

```python
if not gameweek:
    logger.error("No active gameweek found for scraping scorers")
    return {"success": False, "error": "No active gameweek found"}
```

The task deliberately handles a missing active gameweek by returning a failure dictionary, but the `logger.error(...)` call classifies that controlled outcome as an operational worker error. The assumption that every no-active-gameweek outcome is an error does not hold: `apps/kpl/tasks/fixtures.py:437-449` can deliberately leave no gameweek active when neither fixtures nor date ranges yield a suitable gameweek.

The repository does not explain why production had no active gameweek at the reported time. The missing evidence is the production `Gameweek` data and preceding `update_active_gameweek` logs from `apps/kpl/tasks/fixtures.py:428-453`.

## How to reproduce
Ensure no `Gameweek` has `is_active=True`, then invoke `apps.kpl.tasks.scorers.scrape_top_scorers()` with no `gameweek_id`. Before the change, it returned the handled failure while emitting the error-level message; it now emits the same result at warning severity.

## Blast radius
Every scheduled top-scorer run during a period with no active gameweek was previously surfaced as a `docker:worker` error through `config/settings/base.py:387-390`. Explicit `gameweek_id` calls and runs with an active gameweek retain the existing scraping and persistence path at `apps/kpl/tasks/scorers.py:197-248`.

Unclear — none of the supplied commits can be connected to the inspected `apps/kpl/tasks/scorers.py` logging line without commit-to-line provenance.

## Applied fix
- `apps/kpl/tasks/scorers.py:194` now logs the already-handled missing-active-gameweek outcome with `logger.warning(...)` instead of `logger.error(...)`; the return value and scraper control flow are unchanged.
- `tests/test_scorers_task.py:1-13` was added to assert that this exact handled condition is logged as a warning and cannot regress to error severity.
