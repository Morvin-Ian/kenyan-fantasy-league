# `docker-compose.prod.yml` leaves corrected nginx Host rejection unloaded for up to six hours

## Verdict
defect — nginx’s reload loop allowed a changed bind-mounted edge configuration to remain inactive for up to six hours, during which unknown hostnames could still be proxied to Django and generate `DisallowedHost` errors.

## What happened
A request using `Host: staff.fantasykenya.com` reached Django, whose `CommonMiddleware` rejected the hostname and logged `DisallowedHost` before any application view executed. The checked-in nginx configuration rejects that hostname before proxying, so the running instance had not yet loaded its current bind-mounted nginx configuration. The existing compose command only reloaded nginx every six hours.

## Root cause
`docker-compose.prod.yml:66-67` mounted the repository nginx file into the running container but delayed loading changes:

```yaml
# Reload every 6h so renewed certs get picked up without a manual restart.
command: /bin/sh -c 'while :; do sleep 6h & wait $${!}; nginx -s reload; done & nginx -g "daemon off;"'
```

The nginx configuration at `docker/production/nginx/nginx.conf:14-24` has an explicit TLS default server returning `444`, and `:47-51` separately returns `444` when `$host` is not `fantasykenya.com` or `www.fantasykenya.com`. However, the compose configuration assumed a six-hour delay was acceptable for a bind-mounted nginx configuration change. That assumption does not hold: until nginx reloads, `staff.fantasykenya.com` can continue following the prior proxy routing to Django.

Django’s rejection is correct: `config/settings/production.py:45-54` allows only `fantasykenya.com` and `www.fantasykenya.com`. The Django dependency files named in the supplied traceback are outside this repository and could not be read.

## How to reproduce
Deploy a running nginx container that has an older configuration without the current unknown-host rejection, then update the bind-mounted `docker/production/nginx/nginx.conf` without recreating the container. Before the former six-hour reload interval elapsed, request a proxied path with:

```http
GET /api/v1/ HTTP/1.1
Host: staff.fantasykenya.com
```

The old in-memory nginx configuration can forward the request to Django, which emits the supplied `DisallowedHost` error.

## Blast radius
Any unknown hostname sent to `/api/v1` or `/guardian` during the configuration-reload delay could reach Django and create the same error. Requests to the configured KFL domains continue through the intended proxy routes; `mogul.fantasykenya.com` is served separately by `docker/production/nginx/mogul.conf:27-90`.

## Likely cause commit
27cbf1f (`feat: serve mogul.manager from the shared nginx edge`) most plausibly introduced the underlying unsafe default-host behavior: `docker/production/nginx/mogul.conf:9-11` documents that KFL remained the default server for unmatched hostnames. The later nginx rejection configuration is present in this checkout, while the stale six-hour reload behavior at `docker-compose.prod.yml:66-67` allowed its deployment to lag.

## Applied fix
- `docker-compose.prod.yml:66-68` now validates and reloads nginx every five minutes rather than every six hours. The loop runs `nginx -t && nginx -s reload`, so invalid mounted configuration does not replace the last known-good active configuration.
- `tests/test_allowed_hosts.py:119-127` now asserts that the production compose command uses the five-minute interval and validates nginx before reloading, preventing the prolonged stale-configuration window from being restored.

Verify by deploying the compose change, then changing the mounted nginx configuration and confirming a reload occurs within five minutes. Request `/api/v1/` with `Host: staff.fantasykenya.com`; nginx should return `444` and no corresponding `django.security.DisallowedHost` entry should appear. I could not run the test suite or inspect/reload the live deployment because this environment has no command-execution or server access.
