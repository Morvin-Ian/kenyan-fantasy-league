# `docker/production/nginx/nginx.conf` relies on default-vhost selection to reject `plesk.fantasykenya.com`

## Verdict
defect — Django correctly rejects the unserved hostname, but the rejection escaped from the API because the production edge had no hostname-specific rule guaranteeing that Plesk traffic is stopped before proxying.

## What happened
A request carrying `Host: plesk.fantasykenya.com` reached Django’s `CommonMiddleware`, where `request.get_host()` raised `DisallowedHost` before any application endpoint ran. Users or automated Plesk probes received an error response, and the API container logged a Django exception instead of nginx rejecting the unsupported hostname at the edge. The production configuration already intends to stop unknown hosts before Django, but the live error shows default-server selection alone did not achieve that for this hostname.

## Root cause
The edge configuration at `docker/production/nginx/nginx.conf:8-24` only rejected unmatched hosts through `default_server` virtual hosts:

```nginx
server {
    listen 80 default_server;
    server_name _;
    return 444;
}
```

```nginx
server {
    listen 443 ssl default_server;
    ...
    server_name _;
    ...
    return 444;
}
```

This assumed nginx’s default server would always be the configuration that handles `plesk.fantasykenya.com`. That assumption does not hold in the deployment that produced the API log: the request reached Django despite `config/settings/production.py:45-54` intentionally limiting `ALLOWED_HOSTS` to `fantasykenya.com` and `www.fantasykenya.com`.

The Django dependency files named in the traceback are installed in the running container and are not available in this checkout. The repository cannot establish which live included configuration or ingress path superseded the expected default virtual host.

## How to reproduce
Deploy an nginx configuration where another included virtual host becomes the listener’s default, then send an HTTP or HTTPS request with `Host: plesk.fantasykenya.com` to an API route such as `/api/v1/`. Before this change, that request could be handled by the application virtual host and forwarded with `proxy_set_header Host $host` at `docker/production/nginx/nginx.conf:98-100`, causing Django to reject it.

## Blast radius
Any hostname that bypasses the expected default virtual host can reach Django and produce the same API-side `DisallowedHost` log. This change specifically protects the observed `plesk.fantasykenya.com` hostname on both port 80 and port 443; generic unknown-host handling remains covered by the existing default servers and HTTPS `$host` guard.

## Likely cause commit
27cbf1f `feat: serve mogul.manager from the shared nginx edge` — the current `docker/production/nginx/mogul.conf:9-11` adds another included nginx configuration and explicitly discusses server-selection ordering, making it the most plausible listed change to affect the assumption that the default virtual host always catches this hostname.

## Applied fix
- `docker/production/nginx/nginx.conf:26-43` now defines explicit HTTP and HTTPS virtual hosts for `plesk.fantasykenya.com`, each returning nginx status `444` before any request can reach the API. The HTTPS block uses the existing `fantasykenya.com` certificate solely so nginx can complete TLS configuration and reject the request.
- `tests/test_allowed_hosts.py:74-90` now verifies that both explicit Plesk virtual hosts exist and return `444`, independently of `default_server` selection.

I could not run the test suite because this environment provides no command-execution tool. Verification is to run the project’s pytest suite, then deploy/reload nginx and request both HTTP and HTTPS endpoints with `Host: plesk.fantasykenya.com`; nginx should close the request with `444` and no corresponding `django.security.DisallowedHost` entry should appear in the API logs.
