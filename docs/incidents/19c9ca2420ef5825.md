# Postmortem: Incident-documentation audit — which documented fixes are actually in the code

## What happened

The six incident records under `docs/incidents/` were re-read and each documented defect was checked against the current repository state. Most fixes are in place and verified, but two incidents are only partially applied — most importantly `config/celery.py` still hardcodes the **development** settings module for Celery in production, exactly the defect documented in `f6fce3d5db94b95b.md`, and neither compose file has the Postgres healthcheck / restart policy recommended in `7e4a9c1b2d3f4a5b6c7d8e9f0a1b2c3d.md`.

## Findings, per incident record

### 1. `7e4a9c1b2d3f4a5b6c7d8e9f0a1b2c3d.md` — `api` exits 1; entrypoint can't reach PostgreSQL

The record documents six defects and states "Not yet applied". Current state is mixed:

- ✅ **Entrypoint heredoc / `connect_timeout` / env-passing — APPLIED.** Both `docker/local/django/entrypoint` and `docker/production/django/entrypoint` now use a quoted heredoc (`<<'END'`), read `POSTGRES_DB`/`PG_USER`/`PG_PASSWORD`/`PG_HOST`/`PG_PORT` via `os.environ[...]`, and pass `connect_timeout=5`. The regression test `tests/test_entrypoint.py` exists and asserts exactly this contract.
- ❌ **Healthcheck + restart — NOT APPLIED.** Neither `docker-compose.yml` nor `docker-compose.prod.yml` gives `postgres-db` a `healthcheck` or `api` a `restart:` policy. `depends_on` is still bare (`postgres-db`, `redis`), so `api` can still start before Postgres accepts connections and stay `Exited (1)` permanently. Only `client`/`nginx`/`selenium`/`certbot` have restart policies.
- ❌ **Real `.env.example` — NOT APPLIED.** `.env.example` is still a credential-protected placeholder; the five required `PG_*`/`POSTGRES_DB` variables remain undocumented.
- ❌ **`init-db.sql` — STILL PRESENT.** Dead weight with hardcoded `Babyna3*.` password, never mounted into `/docker-entrypoint-initdb.d/`.

### 2. `85310d7c84665436.md` — `FATAL: password authentication failed for user "postgres"`

- ✅ **APPLIED and verified.** Both entrypoints match the suggested fix (quoted heredoc, environment-passed credentials, `connect_timeout=5`), and `tests/test_entrypoint.py` guards against regression. The volume-drift variant (`.env.prod` password vs. initialized `postgres_data` volume) is server state, not code, and remains an operational caveat.

### 3. `f6fce3d5db94b95b.md` — Celery on development settings; `watchmedo` in prod images; `runserver` in prod

The record is truncated mid-sentence ("Django's `runserver` is" — no surviving "Applied fix" section). Checking the three documented defects:

- ✅ **Worker/beat no longer run under `watchmedo` — APPLIED.** `docker/production/django/celery/worker/start` is `exec celery -A config worker --loglevel=info`; `docker/production/django/celery/beat/start` is `exec celery -A config.celery beat ...`. No dev file-watcher in the prod worker/beat paths.
- ✅ **Prod `api` uses gunicorn — APPLIED.** `docker/production/django/start` runs `gunicorn config.wsgi:application --bind 0.0.0.0:8000 --workers ...` (no `runserver`).
- ❌ **`config/celery.py` still unconditionally loads development settings — NOT APPLIED.** Line 11 is unchanged:

  ```python
  app.config_from_object("config.settings.development", namespace="CELERY")
  ```

  This is the exact defect the record describes: `os.environ.setdefault(...)` at line 8 would let `DJANGO_SETTINGS_MODULE` win, but the unconditional `config_from_object` hardcodes the dev module, so the prod worker/beat read `CELERY_*` from `config/settings/development.py` regardless of `.env.prod`/compose env. `development.py` and `production.py` are still near-identical, which is why nothing has failed yet — the documented "latent divergence trap" is still live.
- ⚠️ **Flower prod script still uses `watchmedo`** (`docker/production/django/celery/flower/start`), though flower is not in the prod compose, so impact is limited.

### 4. `cdc28cfb67e2100a.md` — Users force-logged-out when backend is temporarily down

- ✅ **APPLIED and verified.** `client/src/stores/auth.ts:210-211`, `refreshUserProfile()` catch block now just `throw error;` — no `this.logout()`. Token destruction only happens in the axios interceptor on 401 + failed refresh.

### 5. `8d1cb9306432e8a3.md` — "Profile not found" for Google-auth users

- ✅ **APPLIED and verified.** `apps/profiles/views.py:37` uses `Profile.objects.get(user=self.request.user)` in `UpdateProfileAPIView.patch`, ignoring the URL `uuid`. Fixes the Google flow and closes the IDOR hole.

### 6. `bb1261de30d1dac3.md` — Site-wide improvement review (DEBUG, ALLOWED_HOSTS, duplicated request)

- ✅ **DEBUG boolean — APPLIED.** `config/settings/base.py:47`: `DEBUG = env("DEBUG", "false").lower() == "true"`.
- ✅ **ALLOWED_HOSTS env-driven — APPLIED.** `config/settings/base.py:58-60` parses `ALLOWED_HOSTS` with a `"*"` default, so production can pin its real domains.
- ✅ **Duplicate standings fetch removed — APPLIED.** `StandingsView.vue` has only the immediate `watch` calling `fetchStandings()`; `onMounted` no longer triggers the fetch.
- ⚠️ **Minor observations (explicitly marked "not changed" in the record) — all still present, as documented:** `console.log(response)` at `auth.ts:173`, `console.log("Ok")` at `auth.ts:148`, `console.log('Lineup uploaded successfully')` at `FixturesView.vue:221`, unguarded `error.response.data.detail` at `auth.ts:228`, and `SIMPLE_JWT.ACCESS_TOKEN_LIFETIME` still 1 day (`base.py:211`).

## Unresolved — action needed

1. **HIGH (production-affecting, unfixed)** — `config/celery.py:11`: stop hardcoding `config.settings.development` in `config_from_object`. Either drop the argument so Celery reads `django.conf:settings` (the module already set by `DJANGO_SETTINGS_MODULE`), or point it at the env-selected module. Until then, any future divergence between `development.py` and `production.py` (broker URL, task routing, logging, timezone) silently applies only to the `api` container and never to worker/beat.
2. **MEDIUM** — Add the Postgres `pg_isready` healthcheck and `restart: unless-stopped` to `api` (and worker/beat) in both compose files, with `depends_on: condition: service_healthy`, per `7e4a9c1b` §3.
3. **LOW** — `.env.example` still doesn't document the five `PG_*`/`POSTGRES_DB` vars; `init-db.sql` remains dead weight with a hardcoded password; `docker/production/django/celery/flower/start` still uses `watchmedo`; leftover `console.log`s and the unguarded `error.response.data.detail` in `auth.ts:228` remain.

## Verification

No execution environment was available; every claim above was verified by reading the current files: both entrypoints, both compose files, `config/celery.py`, `config/settings/{base,development,production}.py`, `docker/production/django/start`, worker/beat/flower start scripts, `tests/test_entrypoint.py`, `client/src/stores/auth.ts`, `client/src/views/StandingsView.vue`, `apps/profiles/views.py`, and `init-db.sql`.
