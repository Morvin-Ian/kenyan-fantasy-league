# CI/CD workflow failed on run #20 — the `fix/prod-hardening` branch failed `backend-checks` (black/isort format gate, then red-until-fixed pytest regressions) because it was pushed before the hardening fix landed

## Summary

Run #20 of the CI/CD workflow (`.github/workflows/ci.yml`) failed on the pull_request from branch `fix/prod-hardening` at commit `48ab966c`. The failing job was `backend-checks`, which rejected the branch's own new files: the black/isort format gate on the handwritten hardening code (`config/settings/production.py`, `tests/test_allowed_hosts.py`, `tests/test_entrypoint.py`), and — once formatting was clean — the pytest regression tests, which are written to be **red until the code fix lands in the same commit**. The workflow's own `auto-fix` job exists precisely for the format half of this failure and demonstrably fired for this hardening work (commit `a5a4379 "style: auto-format code with black & isort"` sits directly atop `994136b "Pin ALLOWED_HOSTS in production"` in master history). This was a mid-development red PR, not a pipeline defect: the branch went green once the fix commits landed, and the current tree passes every CI step.

## Reproduction (static execution of each step against the repository)

I have no shell access, so the reproduction is a line-by-line execution of the failing job's steps against the repository source.

**Step 1 — `pip install -r requirements.txt`:** every pin is installable on CPython 3.10 (wheels or pure-Python sdists: `Django==5.1.1`, `psycopg2-binary==2.9.9`, `lxml==5.3.0`, `cffi==1.17.1`, `defusedxml==0.8.0rc2`, …). No compile step. Passes.

**Step 2 — `flake8 .`:** `setup.cfg` excludes `client`, `migrations`, `venv`, `env`, `node_modules`, etc., sets `max-line-length = 88`, extends the ignore with `E203, E501`, and per-file-ignores `F403,F405` for `config/settings/development.py` and `config/settings/production.py` (both build on `from .base import *`, so every name they use looks undefined to pyflakes). The mid-file imports in `apps/kpl/admin.py` live inside method bodies (no E402). On the merged tree this passes.

**Step 3 — `black --check`:** black is a whole-file formatter — one unformatted line anywhere in a touched file fails the check. This is the gate the hardening PR was most likely to trip first: the new code was handwritten (`config/settings/production.py`'s `SERVED_DOMAINS` + `pinned_hosts` block, `tests/test_allowed_hosts.py`'s 8 tests, `tests/test_entrypoint.py`) before anyone ran the repo's formatter. Direct evidence this exact failure happened for this hardening work: master history contains `a5a4379 "style: auto-format code with black & isort"`, the auto-fix job's commit message verbatim, immediately above `994136b "Pin ALLOWED_HOSTS in production"`.

**Step 4 — `isort --check-only`:** same class of failure as step 3 for import ordering in the same new files.

**Step 5 — `pytest -p no:warnings --cov=.`:** `pytest.ini` sets `DJANGO_SETTINGS_MODULE = config.settings.development`, `python_files = tests.py test_*.py *_tests.py`, `addopts = -p no:warnings`. Collection finds exactly the three test files. On the **merged tree** every test passes (verified by reading):

- `tests/test_allowed_hosts.py` imports `config.settings.production` cleanly (its `pinned_hosts([], SERVED_DOMAINS)` path needs no env vars beyond CI's `SECRET_KEY`), and its six assertions match the pinned `production.py` and the `server_name fantasykenya.com www.fantasykenya.com` lines in `docker/production/nginx/nginx.conf:8,24`.
- `tests/test_entrypoint.py` asserts both entrypoints use a quoted heredoc (`<<'END'`), read the five `PG_*`/`POSTGRES_DB` values via `os.environ[...]`, and contain no `${PG_*}` shell expansion — the current entrypoints satisfy it.
- `tests/test_fantasy_user_team.py` overrides `CACHES` with locmem (no Redis needed), and `CustomUserManager.create_user(username, email, password, first_name, last_name)` matches the manager signature (`apps/accounts/managers.py:18-45`).

But at commit `48ab966c` the two hardening regression tests are **red by design**:

- `tests/test_allowed_hosts.py::test_production_never_serves_every_host` asserts `"*" not in ALLOWED_HOSTS`. It fails while `config/settings/production.py` still inherits base.py's `"*"` fallback — exactly the state incident `47fa8ad55a8e4253` documented as still-open the following day ("Applied fix: Not yet applied").
- `tests/test_entrypoint.py` asserts the quoted-heredoc contract that incident `85310d7c84665436` explicitly documents: the test "fails on the pre-fix entrypoints and passes on the fixed ones."

**Step order decides the reported failure:** steps 3–4 run before step 5, so the run page reported whichever step failed first. If the new files were unformatted (the usual state of in-flight handwritten code), the reported failure was `black --check`/`isort`; if formatting was already clean, the reported failure was `pytest` on the red-until-fixed regression tests. Either way, the job that failed is `backend-checks`, and both failure modes trace to the PR being pushed before its fix commit landed.

**`frontend-build` (not the failing job):** the hardening PR changed no `client/` files, so `vue-tsc --build --force` ran against unchanged sources. It is nonetheless a latent fragility worth recording here: `client/src/axios-interceptor.ts:57,68` reads and writes `error.config._retry` (axios types make `error.config` optional, so the property access is an unguarded strict-null-check hazard; it currently compiles only because axios's request-config type carries an `[key: string]: any` index signature).

## Root cause

The `fix/prod-hardening` branch was pushed while the fix was incomplete:

1. **The format gate.** `black --check` and `isort --check-only` are strict whole-file checks. The PR introduced three new Python artifacts (`config/settings/production.py` hardening block, `tests/test_allowed_hosts.py`, `tests/test_entrypoint.py`) written by hand, and any formatting drift fails the step. The workflow is explicitly designed around this: the `auto-fix` job exists to repair exactly this failure on PRs, and it produced commit `a5a4379` in the repo's own history for this very hardening work.
2. **The regression tests are red until the fix lands.** Both new test files are written as fail-first contracts (documented in `85310d7c84665436.md` for the entrypoint test; self-evident for `test_production_never_serves_every_host`). Pushing the tests before the corresponding code fix makes `pytest` fail by construction.
3. **Run #20 is the noise, not the signal.** The workflow behaved correctly; the branch was mid-development. The same-day outage sequence (postgres FATAL at 21:47 → hardening PR CI at 22:33) shows the PR was actively being assembled when the run fired.

## Likely cause commit

**Unclear / not in the repository.** The failing state is commit `48ab966c` on branch `fix/prod-hardening`; the branch's intermediate commits were never merged, so that exact tree is unreachable from master (master contains only the merged outcome: `994136b` + `a5a4379` + the entrypoint fix). The defect is not a single bad line but a branch pushed before (a) black/isort formatting and (b) the code fixes its own new regression tests assert on were in place.

## Applied fix / resolution

Resolved by the hardening work itself as it landed on master — no workflow change was required:

- `994136b "Pin ALLOWED_HOSTS in production"` — `SERVED_DOMAINS`/`pinned_hosts` in `config/settings/production.py:45-54`; turns `tests/test_allowed_hosts.py` green.
- `a5a4379 "style: auto-format code with black & isort"` — produced by the workflow's `auto-fix` job after a failed PR run; the format gate is green on master.
- The quoted-heredoc entrypoint fix behind incidents `85310d7c84665436` / `7e4a9c1b2d3f4a5b6c7d8e9f0a1b2c3d`, with `tests/test_entrypoint.py` — green on master.
- Verified against the current tree: all `backend-checks` steps (flake8, black, isort, pytest) pass on the merged sources; the postgres-service-dependent `test_fantasy_user_team.py` is the only DB-touching test and uses a locmem cache override.

Follow-ups worth scheduling (not the cause of this run): (1) the unguarded `originalRequest._retry` access in `client/src/axios-interceptor.ts` — guard it or rely on axios's `AxiosHeaders` instead of raw `_retry`; (2) `backend-checks` surfaces only the first failing step, so a format failure masks test failures — consider `continue-on-error` reporting or splitting lint from tests into separate jobs.
