# Google OAuth login leaks JWT access and refresh tokens in the browser URL

## What happened

Every user who signs in with "Continue with Google" gets their freshly minted JWT pair placed **in the URL query string** of the redirect back to the frontend. The tokens are then parsed out of `window.location` and stored. Anyone who can see the URL — server access logs, browser history, a Referer header, a shoulder-surfer — obtains credentials that can be used to take over the account.

## Root cause

Two ends of the same flow:

1. **Backend builds the success redirect with the tokens embedded.** In `apps/accounts/views.py:104-125`, the Google callback generates the JWTs and URL-encodes them into the redirect target:

   ```python
   tokens = UserAuthService.generate_tokens(user)                  # line 105
   encoded_tokens = urllib.parse.quote(                            # line 109
       json.dumps({"access": tokens["access"], "refresh": tokens["refresh"]})
   )
   success_url = (                                                  # line 120
       f"{redirect_to}?auth_success=true&auth_message=success"
       f"&tokens={encoded_tokens}&user={encoded_user}"
       f"&is_new_user={is_new}&origin={origin}"
   )
   return redirect(success_url)
   ```

   Both the access token **and the refresh token** ride in `?tokens=...`. The error paths (lines 79-80, 86, 129-130, 133-134) only carry error text, so the leak is specific to successful sign-ins.

2. **Frontend accepts the tokens from the URL.** `client/src/views/Auth/OAuthCallback.vue:44-62` reads `route.query.tokens` and `route.query.user`, `JSON.parse`es them, and stores them:

   ```typescript
   const tokens = JSON.parse(decodeURIComponent(tokensParam));  // line 58
   authStore.setToken(tokens.access, tokens.refresh);           // line 61
   authStore.setUser(userData);                                 // line 62
   ```

   Nothing ever scrubs the URL (`history.replaceState` is not called), so the tokens stay visible in the address bar and in history after the redirect.

## How to reproduce

1. Configure Google OAuth for the app (dev or prod).
2. Sign in via "Continue with Google".
3. Observe the redirect URL — it contains `?tokens=%7B%22access%22%3A%22eyJ...%22%2C%22refresh%22%3A%22eyJ...%22%7D` (both JWTs, percent-encoded).
4. Check the API/nginx access log for the same request; the full URI including the token query string is logged in plaintext.

## Blast radius

Every Google sign-in, in every environment, leaks both tokens:

- **Access logs** — the reverse proxy (nginx) and Django log the request line, which includes the query string. Tokens land on disk in plaintext and are typically shipped to log aggregation/retention systems.
- **Browser history** — the URL persists in history and in synced history (e.g. Chrome sync), outliving the session by months.
- **Referer leakage** — any third-party resource the callback page loads (fonts, analytics, error trackers) receives the full URL, including the tokens, in the `Referer` header.
- **Refresh token is the prize** — the refresh token outlives the short access token (access lifetime is 1 day per `SIMPLE_JWT` in this repo) and can mint new access tokens, so a leaked URL equals account takeover, not just a temporary session.
- Secondary: `redirect_to` is taken from the request (`views.py:22`) and echoed into `success_url`, so the token-carrying redirect target is user-influenced input — widening the exfiltration surface if that value is ever attacker-controlled.

## Likely cause commit

**Pre-existing.** The defect lives in `apps/accounts/views.py` (Google OAuth callback) and `client/src/views/Auth/OAuthCallback.vue`, both of which predate the recent master history (CI workflow, black/flake8/isort formatting, and docs commits only). The trigger is any successful Google sign-in.

## Suggested fix

Prefer not putting tokens in the URL at all:

1. **Best:** Keep the code exchange server-side but hand the tokens to the frontend through a channel that isn't the URL — e.g. POST the Google code to `GoogleAuthTokenView` (`views.py:137-189`) and return the tokens in the JSON response body, or set the refresh token as an `HttpOnly; Secure; SameSite=Lax` cookie from the callback and return only the short-lived access token in the body.
2. **If the redirect flow must stay:** redirect with a short-lived, single-use authorization code and have the frontend exchange it for tokens via POST — never the tokens themselves.
3. **Frontend hardening regardless:** on mount, immediately scrub the query string with `history.replaceState({}, "", window.location.pathname)` so the tokens leave the address bar and history, and prefer `sessionStorage`/HttpOnly cookies over `localStorage` (the current `setToken` writes to `localStorage`, which is XSS-readable).

## Applied fix

Not yet applied — this report documents the failure and the concrete patch. The minimal safe change is #1 (tokens via response body or HttpOnly cookie, never the URL); #3 (URL scrubbing) is a worthwhile belt-and-braces measure that can ship independently.
