# Google OAuth success redirects carry JWT access + refresh tokens in the URL query string (`?tokens=...`)

## Summary

Every successful "Continue with Google" sign-in ends with the backend issuing a
`302` whose Location header contains **both JWTs** (access *and* refresh) plus
the full user object as URL-encoded query parameters. The frontend parses them
out of `window.location` and never scrubs the URL, so valid credentials for the
next 1–7 days sit in the browser address bar, history, sync, Referer headers,
and every reverse-proxy/Django access log on disk.

## What happened

1. User clicks "Continue with Google".
2. Backend callback exchanges the Google code server-side, mints the JWT pair,
   and redirects to the SPA with the tokens embedded in the query string.
3. SPA reads `route.query.tokens`, stores both tokens in `localStorage`, and
   navigates home — leaving the token-bearing URL in history/address bar.
4. Anyone/anything that sees that URL (logs, history, Referer, shoulder-surf)
   holds a working refresh token → account takeover.

## Root cause

Two ends of the same flow, verified line-by-line against current code:

### 1. Backend embeds tokens in the redirect target

`apps/accounts/views.py` — `GoogleAuthCallbackView.get()`:

```python
# views.py:105-125
tokens = UserAuthService.generate_tokens(user)          # :105
...
encoded_tokens = urllib.parse.quote(                    # :109-116
    json.dumps({"access": tokens["access"], "refresh": tokens["refresh"]})
)
encoded_user = urllib.parse.quote(json.dumps(user_data))  # :117

success_url = (                                          # :120
    f"{redirect_to}?auth_success=true&auth_message=success"
    f"&tokens={encoded_tokens}&user={encoded_user}"
    f"&is_new_user={is_new}&origin={origin}"
)
return redirect(success_url)                             # :125
```

The error paths (`views.py:79-80`, `86`, `129-130`, `133-134`) only carry
`auth_success=false&auth_message=...` — no tokens — so the leak is specific to
**successful** sign-ins.

The repo already ships the safe alternative and doesn't use it:
`GoogleAuthTokenView.post()` (`views.py:137-189`) returns the identical payload
(`access`, `refresh`, `user`, `is_new_user`) **in a JSON response body**
(`views.py:171-180`) — proving the redirect-with-tokens design is unnecessary,
not load-bearing.

### 2. Frontend accepts tokens from the URL and never scrubs it

`client/src/views/Auth/OAuthCallback.vue` (route `/auth/callback`,
`client/src/router/index.ts:22-25`):

```typescript
const tokensParam = route.query.tokens as string;            // :47
const userParam   = route.query.user   as string;            // :48
...
const tokens   = JSON.parse(decodeURIComponent(tokensParam)); // :58
const userData = JSON.parse(decodeURIComponent(userParam));   // :59

authStore.setToken(tokens.access, tokens.refresh);            // :61
authStore.setUser(userData);                                  // :62
```

`setToken` persists both values to `localStorage`
(`client/src/stores/auth.ts:47-61`). No `history.replaceState` /
`router.replace` call anywhere in the component removes the query string, so
the raw JWTs stay visible after sign-in completes.

### Why the refresh token makes this account takeover, not a nuisance

`config/settings/base.py:209-219`:

```python
SIMPLE_JWT = {
    "ACCESS_TOKEN_LIFETIME": timedelta(days=1),
    "REFRESH_TOKEN_LIFETIME": timedelta(days=7),
    ...
}
```

A leaked URL yields a credential valid for up to **7 days**, and with
`ROTATE_REFRESH_TOKENS=True` the thief can mint fresh access tokens
indefinitely within that window — even after the legitimate user's session
looks "over".

## How to reproduce

1. Configure Google OAuth (`GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`) and run
   the stack (`make build`).
2. Sign in via "Continue with Google".
3. Watch the address bar during the callback hop: it flashes
   `…/auth/callback?auth_success=true&auth_message=success&tokens=%7B%22access%22%3A%22eyJ…%22%2C%22refresh%22%3A%22eyJ…%22%7D&user=…`.
4. After landing on Home, open browser history → the full token URL is saved.
5. `docker compose logs nginx api` (prod: the VPS access log) → the same request
   line with the token query string is logged in plaintext.

## Blast radius

- **Access logs**: nginx and Django request logging persist the full URI
  (query string included) to disk and any log aggregation/retention pipeline.
- **Browser history + Chrome/Safari sync**: the URL outlives the session by
  months and replicates to every device on the account.
- **Referer leakage**: any third-party resource loaded by the callback page
  (fonts, analytics, error trackers) receives the full URL in `Referer`.
- **Refresh token is the prize**: 7-day lifetime (vs 1-day access) means one
  leaked URL ≈ account takeover, not a temporary session.
- **Secondary — open-redirect-ish echo**: `redirect_to` originates from the
  request (`views.py:22`), is stored unsigned in `state`
  (`views.py:29-34`), and is reused verbatim as the token-carrying redirect
  target (`views.py:60-67`, `120`). If that value is ever attacker-influenced,
  the victim's freshly minted tokens are delivered to the attacker's origin.
  The `state` parameter also carries no CSRF nonce and no signature, so it
  provides none of OAuth's usual CSRF protection.

## Suggested fix

Prefer not putting tokens in the URL at all:

1. **Best:** keep the code exchange server-side but deliver tokens through a
   channel that isn't the URL:
   - set the refresh token as an `HttpOnly; Secure; SameSite=Lax` cookie from
     the callback and return only the short-lived access token in the response
     body, **or**
   - have the frontend POST the Google `code` to the already-existing
     `POST /api/v1/auth/google/token/` (`GoogleAuthTokenView`,
     `urls.py:16`) and read tokens from the JSON body.
2. **If the redirect flow must stay:** redirect with a short-lived single-use
   authorization code and exchange it via POST — never the tokens themselves.
3. **Frontend hardening regardless of #1/#2:**
   - immediately scrub the query string on mount:
     `history.replaceState({}, "", window.location.pathname)` before any
     further processing;
   - move tokens out of `localStorage` (XSS-readable) toward HttpOnly cookies;
   - sign/validate `state` (random nonce stored server-side or in a signed
     cookie) and stop echoing request-supplied `redirect_to`.

## Applied fix

Not yet applied — this report documents the failure and the concrete patch.
The minimal safe change is #1 (tokens via response body or HttpOnly cookie,
never the URL); #3 (URL scrubbing + state hardening) can ship independently as
belt-and-braces.
