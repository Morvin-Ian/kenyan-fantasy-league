# `config/settings/production.py` trusts an unvalidated `X-Forwarded-Host` header for Django host validation

## Verdict
defect — production accepts the client-controlled `X-Forwarded-Host` header as the request host even though nginx only validates and overwrites `Host`.

## What happened
A request reached Django with `ufficio.fantasykenya.com` selected as its host, and Django rejected it before a view ran with `DisallowedHost`. The production nginx configuration rejects unknown `Host` values at the edge (`docker/production/nginx/nginx.conf:8-24`) and forwards its validated `$host` upstream (`:75-89`), but it does not overwrite `X-Forwarded-Host`. `config/settings/production.py` told Django to prefer that untrusted forwarded header instead.

## Root cause
At `config/settings/production.py:57-64`, production enabled forwarded-host trust:

```python
SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")
USE_X_FORWARDED_HOST = True
```

`USE_X_FORWARDED_HOST = True` makes Django select `HTTP_X_FORWARDED_HOST` when resolving the host. Nginx’s API proxy locations set `Host $host` but do not set or clear `X-Forwarded-Host` (`docker/production/nginx/nginx.conf:75-89`), so the configuration assumed that header had already been validated by a trusted proxy. That assumption does not hold: a client can supply it, or an upstream proxy can forward it unchanged. Django then correctly rejects `ufficio.fantasykenya.com`, which is absent from the pinned production host list at `config/settings/production.py:45-54`.

The Django dependency files named in the traceback are outside the checked-out repository and could not be read. The supplied traceback confirms that `CommonMiddleware` called `request.get_host()`; the exact origin of the `X-Forwarded-Host` value is not logged and cannot be determined from this repository.

## How to reproduce
Send a request to a Django-proxied production route using a valid nginx host but an invalid forwarded host:

```http
GET /api/v1/ HTTP/1.1
Host: fantasykenya.com
X-Forwarded-Host: ufficio.fantasykenya.com
```

Before this change, nginx forwards the unmodified `X-Forwarded-Host` header and Django uses it because `USE_X_FORWARDED_HOST` is enabled, producing `DisallowedHost`.

## Blast radius
Every Django-proxied `/api/v1` or `/guardian` request with a client- or upstream-supplied `X-Forwarded-Host` outside `ALLOWED_HOSTS` can produce this error, including requests whose normal `Host` is valid. The independent nginx unknown-`Host` rejection remains covered by `docker/production/nginx/nginx.conf:8-24` and `:47-51`.

## Likely cause commit
Unclear — none of the listed commits can be shown, using the available repository-reading tools, to have changed `config/settings/production.py`’s `USE_X_FORWARDED_HOST` setting.

## Applied fix
- `config/settings/production.py:57-64` now sets `USE_X_FORWARDED_HOST = False`, so Django uses nginx’s `Host` header, which the proxy explicitly sets from validated `$host`, rather than an unvalidated forwarded-host header.
- `tests/test_allowed_hosts.py:98-103` now asserts that production does not enable `USE_X_FORWARDED_HOST`, preventing this trust boundary from being restored accidentally.
