# Production deployment review: Celery still loads the *development* settings module, and a dev file-watcher remains baked into the production image

## What happened

A review of the production deployment path (`docker-compose.prod.yml`, the `docker/production/django/*` scripts, `config/celery.py`, `config/wsgi.py`, `config/asgi.py`) found three concrete defects. **Two of the three were already fixed in a previous pass; the most dangerous one — the Celery settings hardcode — is still present**, and the review surfaced two new production-readiness gaps (missing `restart` policies, and a settings-module default that still points at development).

Current state, verified by reading the code:

| # | Defect (from the original review) | Status |
|---|---|---|
| 1 | Production Celery loads the *development* settings module | **STILL BROKEN** |
| 2 | `watchmedo auto-restart` runs production Celery | Worker/beat **FIXED**; flower **STILL BROKEN** |
| 3 | Production API serves traffic with `runserver` | **FIXED** (gunicorn) |

## Root cause

### 1. STILL BROKEN — Celery unconditionally reads `CELERY_*` from `config.settings.development`

`config/celery.py:8-11`:

```python
os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings.development")

app = Celery("config")
app.config_from_object("config.settings.development", namespace="CELERY")
```

The second line is decisive: `config_from_object("config.settings.development", ...)` is **unconditional**. The production compose (`docker-compose.prod.yml:77-78, 95-96`) correctly sets `DJANGO_SETTINGS_MODULE=config.settings.production` for `celery_worker` and `celery_beat`, so the `setdefault` on line 8 is a no-op there — but the Celery app object still reads every `CELERY_*` setting from the **development** module regardless of the environment.

This is a latent divergence trap, and the masking has partially worn off: `config/settings/development.py` and `config/settings/production.py` are **no longer identical** — `production.py:32-47` adds `SECURE_PROXY_SSL_HEADER`, `USE_X_FORWARDED_HOST`, `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`, and HSTS. The `CELERY_BROKER_URL`/`CELERY_RESULT_BACKEND` values happen to still be identical (both read `CELERY_BROKER`/`CELERY_BACKEND` from env), which is the only reason nothing has failed yet. Any future edit that makes production's broker URL, task routing, timezone, logging, or email config differ will apply to the `api` container but **never to background tasks**, and `beat` will keep scheduling on dev settings.

The same dev-first default also appears in `manage.py:9` and `config/wsgi.py:14` (`setdefault("config.settings.development")`), and `config/asgi.py:14` defaults to `"config.settings"` — the package, whose `__init__.py` is empty, so any ASGI entrypoint would crash on import. All of these are `setdefault`, so the compose `environment:` entries save the running stack today, but **nothing in the production image, entrypoint, or start scripts enforces production settings** — correctness depends entirely on the gitignored `.env.prod` and the compose overrides being kept in sync.

**Fix:** make Celery read settings from the active Django module instead of hardcoding a name:

```python
# config/celery.py
os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings.production")
app = Celery("config")
app.config_from_object("django.conf:settings", namespace="CELERY")
```

`django.conf:settings` always resolves to whatever module `DJANGO_SETTINGS_MODULE` points at — one line, and the dev/prod hardcode disappears for good. Apply the same default to `manage.py`/`wsgi.py`/`asgi.py` (or at minimum make the production image set the module in its `ENV` so a bare `docker run` can't silently boot dev settings).

### 2. PARTIALLY FIXED — `watchmedo auto-restart` (a dev hot-reload tool) is still in the production image

`docker/production/django/celery/worker/start` and `.../beat/start` **have been fixed** — both now `exec celery ...` directly, giving correct PID-1 signal handling (graceful shutdown on SIGTERM, no deploy-time hot restarts):

```bash
# docker/production/django/celery/worker/start:5
exec celery -A config worker --loglevel=info
```

But `docker/production/django/celery/flower/start:6-7` **still** runs under `watchmedo`:

```bash
watchmedo auto-restart -d config/ -p "*.py" -- \
  celery --broker="redis://redis:6379/0" -A config.celery flower --port=5555
```

and the production `Dockerfile` still bakes it in as `/start-flower` (`docker/production/django/Dockerfile:32-34`), which pulls `watchdog` into the production image via `requirements.txt`. Flower is not currently in `docker-compose.prod.yml`, so this is dormant — but the moment anyone adds flower to prod (the script exists precisely for that), it inherits the same two harms the worker/beat fix eliminated: SIGTERM not reliably forwarded to the Celery child (dropping in-flight task state on restarts) and hot-restart racing the `git pull` in the deploy (`ci.yml:118`).

**Fix:** mirror the worker/beat change — `exec celery -A config.celery flower --port=5555` — and consider dropping `watchdog` from the production image entirely.

### 3. FIXED — Production API now runs gunicorn, not `runserver`

`docker/production/django/start:13-18`:

```bash
exec gunicorn config.wsgi:application \
  --bind 0.0.0.0:8000 \
  --workers "${GUNICORN_WORKERS:-3}" \
  --timeout "${GUNICORN_TIMEOUT:-60}" \
  --access-logfile - \
  --error-logfile -
```

The dev server is gone from production. Note the `migrate`/`collectstatic` calls were also moved out of `start` into the CI deploy (`ci.yml:125-138`), which removes the old double-migrate race.
