# docker-compose.prod.yml delays nginx Host-header guard deployment for six hours

## Verdict
defect — the repository bind-mounts nginx configuration but reloads it only every six hours, leaving a running deployment able to forward unrecognised hosts to Django long after the checked-in edge rejection is available.

## What happened
A request with `Host: manager.fantasykenya.com` reached the API container, where Django’s `CommonMiddleware` rejected it with `DisallowedHost` before any application endpoint ran. The repository nginx configuration already rejects that host at the edge, but `docker-compose.prod.yml` scheduled the process reload only every six hours. As a result, a configuration correction mounted into the running nginx container could remain inactive for up to six hours.

## Root cause
The defect was in `docker-compose.prod.yml:66-67`:

```yaml
# Reload every 6h so renewed certs get picked up without a manual restart.
command: /bin/sh -c 'while :; do sleep 6h & wait $${!}; nginx -s reload; done & nginx -g "daemon off;"'
```

The production compose file bind-mounts `./docker/production/nginx/nginx.conf` at `/etc/nginx/conf.d/default.conf` in `docker-compose.prod.yml:49-58`, including the unknown-host rejection at `docker/production/nginx/nginx.conf:47-51`:

```nginx
if ($host !~ ^(fantasykenya\.com|www\.fantasykenya\.com)$) {
    return 444;
}
```

The command assumed that a six-hour configuration-reload delay was acceptable because it was intended for certificate renewal. That assumption does not hold for an active Host-header routing correction: until nginx reloads, its worker processes continue using the prior configuration and can proxy `manager.fantasykenya.com` to Django. Django correctly rejects it because `config/settings/production.py:45-54` permits only `fantasykenya.com` and `www.fantasykenya.com`.

The Django package files named in the traceback are outside this repository and could not be read here; the traceback identifies `CommonMiddleware` calling `request.get_host()` as the surfacing path. I also could not determine whether this event occurred before the fixed configuration was deployed, during the former six-hour reload window, or through an unrecorded route that bypasses nginx.

## How to reproduce
1. Start the production compose stack with an nginx configuration that proxies unknown hostnames.
2. Update the mounted `docker/production/nginx/nginx.conf` to include the existing rejection at lines 47-51 without recreating nginx.
3. Before its scheduled reload, send:

```http
GET /api/v1/ HTTP/1.1
Host: manager.fantasykenya.com
```

Before the fix, the old nginx workers could continue to proxy the request until the six-hour reload. Django then raises the reported `DisallowedHost`.

## Blast radius
Any mounted nginx configuration correction, including the rejection of arbitrary hosts on `/api/v1` and `/guardian`, could previously remain unapplied for up to six hours. The same delayed-reload behavior also affected TLS certificate renewal; nginx now validates and reloads both configuration and certificates every five minutes.

## Likely cause commit
39412aa (`maajun: incident report for Production nginx forwards unrecognised Host headers to Djang…`) most plausibly exposed this gap: it added the nginx-side rejection in `docker/production/nginx/nginx.conf`, while the existing production command in `docker-compose.prod.yml` still allowed old worker configuration to persist for six hours.

## Applied fix
- `docker-compose.prod.yml:66-68` now checks the mounted nginx configuration and reloads nginx every five minutes instead of every six hours. The command uses `nginx -t && nginx -s reload`, so an invalid mounted configuration does not replace the active configuration.
- `tests/test_allowed_hosts.py:119-128` now asserts that the production compose command reloads promptly and validates the configuration before reload, preventing this extended stale-configuration window from returning.

Verify by deploying the updated compose file and observing a successful `nginx -t` and reload within five minutes. Then request `/api/v1/` with `Host: manager.fantasykenya.com`; nginx should close the request with `444` and no corresponding `django.security.DisallowedHost` entry should appear in the API log. I could not execute tests or interact with the running deployment because this environment provides no command-execution access.
