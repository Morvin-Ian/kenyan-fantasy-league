# HTTPS outage on fantasykenya.com — certificate expired and silently never renewed (`NET::ERR_CERT_DATE_INVALID`)

## What happened

Users visiting `https://fantasykenya.com` or `https://www.fantasykenya.com` got a hard browser block: `NET::ERR_CERT_DATE_INVALID` / "Your connection is not private — this server could not prove that it is fantasykenya.com; its security certificate expired." The site was unreachable over HTTPS even though every production container reported healthy:

- `docker compose -f docker-compose.prod.yml ps` shows `nginx` **Up**, `api` **Up**, `certbot` **Up**, `postgres-db` **Up**.
- `docker compose logs nginx` shows normal access logs — nginx is serving, but serving an **expired** certificate.
- `docker compose logs certbot` is empty of errors — `certbot renew --quiet` has been silently no-op'ing for months.
- The CI deploy (`ci.yml:115-137`) still succeeds: it pulls, rebuilds, migrates, collectstatic — nothing checks certificate expiry, so the deploy pipeline is green while the site is dead for every user.

## Root cause

The certificate lifecycle is wired in `docker-compose.prod.yml` and `docker/production/nginx/nginx.conf`, and it has five concrete, verifiable defects. None of them is in the deploy pipeline, which is why nothing failed loudly:

### 1. Nothing in the repo ever *issues* the certificate — only `renew` exists

`docker-compose.prod.yml:103-115` runs only `certbot renew --webroot -w /var/www/certbot --quiet` in a loop. There is no `certbot certonly` step anywhere (confirmed: zero matches for `certonly`/`init-cert` in the repo). `nginx.conf:29-30` hard-codes:

```nginx
ssl_certificate /etc/letsencrypt/live/fantasykenya.com/fullchain.pem;
ssl_certificate_key /etc/letsencrypt/live/fantasykenya.com/privkey.pem;
```

So the certificate must have been created by hand on the VPS at some point. `renew` only works if the renewal config in `/etc/letsencrypt/renewal/fantasykenya.com.conf` (host-side, gitignored) matches `--webroot`; if the original issuance used any other method, `certbot renew --webroot` **skips that cert with an error** — which is invisible here (see #2). On a fresh host (or if `/etc/letsencrypt` is ever wiped) there is **no path in the repo to bootstrap a certificate at all**: nginx fails `-t` on the missing files and the container exits, taking the whole site down.

### 2. Renewal failures are inaudible — `--quiet` + a loop that swallows exit codes

`docker-compose.prod.yml:110`:

```yaml
entrypoint: /bin/sh -c 'trap exit TERM; while :; do certbot renew --webroot -w /var/www/certbot --quiet; sleep 12h & wait $${!}; done'
```

- `--quiet` suppresses every diagnostic. A failed renew logs nothing.
- The `while :;` loop has no `set -e`, no `|| exit 1`, no healthcheck. The container has `restart: always`, so a crashing renew would restart — but a *failing* renew doesn't crash the loop; it just retries silently every 12 hours until the cert is 90 days past due.
- There is no alerting anywhere: no expiry check in CI, no healthcheck on `certbot`, no monitoring. `grep` for `checkend`/`s_client`/`deploy-hook` finds nothing in the repo.

### 3. Renewed certificates are picked up only by a fixed 6-hour timer, with no deploy hook

`docker-compose.prod.yml:63` reloads nginx every 6 h; there is no `--deploy-hook "nginx -s reload"` on `certbot renew`. This is the *good* path (worst case 6 h staleness) but it also means there is no immediate activation on renewal, and nothing that ever verifies the served cert matches the freshly renewed one.

### 4. nginx serves an expired cert with no validation

nginx loads whatever is at the fixed path in `nginx.conf:29-30`, expired or not, and the reload loop never checks `x509 -checkend`. An expired certificate is served indefinitely — which is exactly what users saw.

### 5. HSTS + preload turns the expiry into a *hard* outage with no HTTP fallback

`config/settings/production.py:43-45`:

```python
SECURE_HSTS_SECONDS = 31536000
SECURE_HSTS_INCLUDE_SUBDOMAINS = True
SECURE_HSTS_PRELOAD = True
```

Browsers that have ever seen this HSTS header (or that resolve it from the preload list, since the domain is preloaded) refuse plain-HTTP fallback. The port-80 server (`nginx.conf:6-18`) 301s to HTTPS, so the redirect plus the expired cert is a **hard connection failure** — users cannot downgrade to the working HTTP site. The app itself (JWT auth, Google OAuth callback against `https://...`, `CSRF_TRUSTED_ORIGINS` at `base.py:69-70`, `ALLOWED_HOSTS` via env) is entirely unreachable.

## How to reproduce

1. **Expiry path:** let a renewal cycle fail silently for ~90 days — e.g. remove `certbot` from the compose file, or break the webroot renewal (issue the original cert with a different authenticator so `renew --webroot` skips it), or let the VPS firewall stop answering HTTP-01 on port 80. The `certbot` container keeps "running" and logging nothing; the cert expires; browsers show `NET::ERR_CERT_DATE_INVALID`; `docker compose ps` and the CI deploy stay green.
2. **Fresh-host path:** on a new VPS with no `/etc/letsencrypt`, run `make up-prod` (or the CI deploy). `nginx.conf` references `fullchain.pem`/`privkey.pem` that don't exist → `nginx -t` fails → the `nginx` container exits → nothing serves ports 80/443. There is no `certbot certonly` step in the repo to recover.

## Blast radius

- **All users of the production site** — the API, JWT login, Google OAuth, and the Vue app are all behind the TLS-terminating nginx; an expired cert takes the entire product offline for the whole certificate window.
- **No graceful degradation** — HSTS preload (`production.py:43-45`) removes the plaintext escape hatch.
- **Silent by design** — every container is healthy and the deploy passes, so the first signal is a browser security warning; this is the classic "everything is fine until the users scream" failure.
- **Dev environments unaffected** — `docker-compose.yml`'s nginx listens on `:8080` with no TLS (`VITE_API_BASE_URL: http://localhost:8080/api/v1`, `docker-compose.yml:72`), so the bug is production-only.

## Likely cause commit

**Unclear — and that is the point.** Recent master history (`cbf2fb0` prod-hardening merge, `48ab966` "Fix DisallowedHost and harden the production deployment", `773b854`, `670cc99`, `ad28383`) touched settings, CI, entrypoints, and docs — none of it altered `docker-compose.prod.yml`'s certbot service or `nginx.conf`. The certificate lifecycle has been wired this way since before those commits. The *trigger* is server-side operational state (a renewal that silently stopped succeeding), and the *reason nobody noticed* is the repo-level defects in #1–#5. The repo's contribution is the missing issuance path, the swallowed exit codes, and the absence of any expiry check.

## Suggested fix

1. **Add an initial-issuance path.** A one-shot certbot target that issues (not renews) and validates nginx before activating:

   ```bash
   # Makefile
   init-cert: ## First-time issuance (run once on a fresh host)
   	docker compose -f docker-compose.prod.yml --env-file .env.prod run --rm certbot \
   		certonly --webroot -w /var/www/certbot \
   		-d fantasykenya.com -d www.fantasykenya.com \
   		--email ops@fantasykenya.com --agree-tos --no-eff-email
   	docker compose -f docker-compose.prod.yml --env-file .env.prod exec nginx nginx -t
   ```

2. **Make renewal loud and fail-closed.** In `docker-compose.prod.yml`:

   - Drop `--quiet` so renew diagnostics land in the container logs.
   - Add `--deploy-hook "nginx -s reload"` so a successful renewal activates immediately instead of waiting up to 6 h.
   - Fail the loop on renew failure so `restart: always` makes it visible in `docker compose ps`:

     ```yaml
     entrypoint: /bin/sh -c 'trap exit TERM; while :; do certbot renew --webroot -w /var/www/certbot --deploy-hook "nginx -s reload" || exit 1; sleep 12h & wait $${!}; done'
     ```

   - Add a healthcheck that fails when the cert is close to expiry:

     ```yaml
     healthcheck:
       test: ["CMD-SHELL", "openssl x509 -in /etc/letsencrypt/live/fantasykenya.com/cert.pem -noout -checkend 864000 || exit 1"]
       interval: 1h
       timeout: 10s
       retries: 3
     ```

3. **Add expiry monitoring.** A scheduled check — e.g. a CI cron or a Makefile target using `openssl s_client -connect fantasykenya.com:443 -servername fantasykenya.com | openssl x509 -noout -dates` — so a certificate within N days of expiry fails a check loudly instead of surfacing as a browser warning. Document `docker compose -f docker-compose.prod.yml --env-file .env.prod exec certbot certbot certificates` as the manual inspection command.

4. **Write the recovery runbook** (in the report itself, below): how to force-renew, and how to re-issue from scratch when the files are missing.

## Applied fix

Not yet applied in this branch — this report documents the failure and the concrete patch. The highest-value code changes are #2 (loud, fail-closed renewal with `--deploy-hook`) and #1 (the missing issuance path), both confined to `docker-compose.prod.yml` and `Makefile`.

## Recovery runbook (for the operator)

1. **Force renewal now** (if the webroot renewal config is intact): `docker compose -f docker-compose.prod.yml --env-file .env.prod exec certbot certbot renew --force-renewal --webroot -w /var/www/certbot`, then `docker compose -f docker-compose.prod.yml --env-file .env.prod exec nginx nginx -s reload` (or wait ≤6 h for the timer).
2. **Re-issue from scratch** (if `/etc/letsencrypt` is missing or the renewal config is broken): run the `make init-cert` target from Suggested fix #1, then `docker compose -f docker-compose.prod.yml --env-file .env.prod up -d nginx`.
3. **Verify:** `openssl s_client -connect fantasykenya.com:443 -servername fantasykenya.com | openssl x509 -noout -dates` shows a future `notAfter`, and the browser loads `https://fantasykenya.com` without warnings.
4. **Prevent recurrence:** apply Suggested fixes #2–#3 so the next renewal failure is loud and the next expiry is caught while there are still days left.
