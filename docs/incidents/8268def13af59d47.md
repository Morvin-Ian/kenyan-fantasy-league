# nginx proxy trusts client-supplied X-Forwarded-Host in `docker/production/nginx/nginx.conf`

## Verdict
defect — Django is configured to use `X-Forwarded-Host`, but nginx validates only `Host` and forwards a client-supplied forwarded-host header unchanged.

## What happened
A request reached Django with `X-Forwarded-Host: ufficio.fantasykenya.com`, causing Django’s `CommonMiddleware` to reject the host before any application view ran. The public nginx host guard accepts only `fantasykenya.com` and `www.fantasykenya.com`, but it did not overwrite the separate forwarded-host header that Django prefers.

## Root cause
`config/settings/production.py:61` enables Django’s forwarded-host handling:

```python
USE_X_FORWARDED_HOST = True
```

However, the Django proxy locations in `docker/production/nginx/nginx.conf:75-81` and `:84-90` previously set only `Host`:

```nginx
proxy_set_header Host $host;
```

Nginx therefore passed any client-provided `X-Forwarded-Host` upstream. The failed assumption was that validating and rewriting `Host` also controlled the header Django reads when `USE_X_FORWARDED_HOST` is enabled. It does not; a request with a valid `Host` but `X-Forwarded-Host: ufficio.fantasykenya.com` reaches Django with the latter value, which is absent from `ALLOWED_HOSTS` at `config/settings/production.py:45-54`.

The Django dependency files named in the traceback are not available in this repository, so their exact source could not be read. The traceback establishes that `CommonMiddleware` called `request.get_host()` and Django rejected `ufficio.fantasykenya.com`.

## How to reproduce
Send an HTTPS request through the production nginx `/api/v1` or `/guardian` route with a permitted `Host` and a forged forwarded host:

```http
GET /api/v1/ HTTP/1.1
Host: fantasykenya.com
X-Forwarded-Host: ufficio.fantasykenya.com
```

Before the change, nginx forwarded the supplied `X-Forwarded-Host`; with `USE_X_FORWARDED_HOST=True`, Django rejected it as a `DisallowedHost`.

## Blast radius
Every request to `/api/v1` or `/guardian` could supply an arbitrary `X-Forwarded-Host` despite the existing `$host` allowlist. Other nginx proxy call sites are limited to `docker/production/nginx/mogul.conf:73-90`, which belongs to the separate mogul upstream and does not proxy to this Django application.

## Likely cause commit
Unclear — the available repository inspection identifies the relevant settings and proxy-header configuration, but does not establish which listed commit introduced either line.

## Applied fix
- `docker/production/nginx/nginx.conf:75-90` now sets `X-Forwarded-Host` to nginx’s validated `$host` in both Django proxy locations, replacing any client-supplied value before it reaches Django.
- `tests/test_allowed_hosts.py:119-136` now verifies that both Django proxy locations overwrite `X-Forwarded-Host` with `$host`.

Verify by running `tests/test_allowed_hosts.py`, reloading the production nginx configuration, and sending the reproduction request above. Django should receive `fantasykenya.com` as the forwarded host and should not log `DisallowedHost`. I could not execute tests or reload nginx because this environment has no command-execution tool.
