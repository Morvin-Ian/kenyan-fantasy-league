# Standings sync leaves the cached first page empty in apps/kpl/tasks/sync.py

## Verdict
defect — `bulk_create()` bypasses the `Standing` save signals that invalidate the cached standings response, so valid zero-point rows remain hidden behind an earlier cached empty result.

## What happened
When the standings endpoint is requested before the league table is populated, `StandingViewSet` caches its empty page-one response for 24 hours. The later standings sync successfully writes the zero-stat rows to the database, but the frontend receives that cached empty `results` list from `/kpl/standings/`. Both the full standings page and homepage consume that same store response, so neither renders the rows.

## Root cause
`apps/kpl/tasks/sync.py:292-294` replaces standings using a bulk insert:

```python
with transaction.atomic():
    Standing.objects.all().delete()
    Standing.objects.bulk_create(snapshot)
```

`apps/kpl/signals.py:51-53` is intended to invalidate `standings_list_page_*` on ordinary `Standing` saves/deletes, but Django does not emit `post_save` for `bulk_create()`. The assumption that the model signal clears the endpoint cache after the snapshot is written does not hold. Meanwhile, `apps/kpl/views.py:60-70` returns a cached page-one response for up to 86,400 seconds, including an empty result.

## How to reproduce
1. With no `Standing` rows, make an authenticated `GET /kpl/standings/`, which caches `{"results": []}` under `standings_list_page_1`.
2. Run `sync_standings` with valid provider rows for all teams, with every result statistic and point total set to `0`.
3. Make the same request again within 24 hours. It returns the stale empty cached response despite the database containing the standings; the homepage and standings view then render no rows.

## Blast radius
Any successful standings snapshot written through `sync_standings` after page one was cached is affected, not only pre-season zero-point tables. The client only requests the unqualified endpoint, and the configured page size is 50 (`config/settings/base.py:198-199`), so all current standings fit in the stale first page.

## Applied fix
- `apps/kpl/tasks/sync.py:292-295` now registers `transaction.on_commit(lambda: cache.delete("standings_list_page_1"))` after the snapshot replacement. This explicitly clears the endpoint page consumed by the client only after the database transaction commits.
- `tests/test_sync_tasks.py:102-115` added a regression test that caches an empty first standings page, syncs a valid zero-point standing, and asserts that the cached response is removed.

Verification is provided by the added regression test; code execution was not available in this investigation environment.
